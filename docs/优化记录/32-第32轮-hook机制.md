# 第 32 轮：生命周期 hook

> 日期：2026-11-12
> 版本：0.10.2（未动版本号，与第 26 轮起一致）
> 触发：想要 Claude Code 那种「会话启动 / 工具调用前 / 准备结束」挂 shell 的能力
> 教训：**模型的约束是概率性的，hook 的意义就是把它变成确定性的——所以 hook 自己绝不能"有时生效有时不生效"**

---

## 一、一句话方案

四个事件 + 一份用户级配置 + 一个执行器。命令通过 stdin 拿 JSON，用退出码说话：

| 事件 | 时机 | 能拦 | stdout 去哪 |
|---|---|---|---|
| `SessionStart` | 会话建立后、系统提示词生成前 | 不能 | 拼进系统提示词 |
| `PreToolUse` | 工具调用前、**权限确认之前** | **能（exit 2）** | 拒绝原因回给模型 |
| `PostToolUse` | 工具成功执行后 | 半能 | 追加到工具结果 |
| `SessionEnd` | 进程退出前（含 Ctrl+C） | 不能 | 打给用户 |

配置（`~/.thinker/settings.json`）：

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "cmd_runner",
        "hooks": [{ "type": "command", "command": "python C:/hooks/guard.py", "timeout": 30 }] }
    ]
  }
}
```

## 二、和 Claude Code 对齐了什么、故意不同在哪

**对齐**（目的是让现成脚本能直接搬）：

- `settings.json` 的 `hooks.<Event>[{matcher, hooks:[{type, command, timeout}]}]` 结构；
- stdin 字段名：`session_id` / `cwd` / `hook_event_name` / `tool_name` / `tool_input`；
- 退出码：0 继续、2 阻断、其它非阻断；
- `matcher` 语法：空或 `*` 全部、`a|b` 多选、`mcp__.*` 正则、大小写敏感；
- 也认 exit 0 + `{"decision":"block"}` 与 `hookSpecificOutput.additionalContext`。

**故意不同**（每条都有代价，写在这里免得以后有人"顺手改成和 Claude Code 一样"）：

| 差异 | Claude Code | thinker | 为什么 |
|---|---|---|---|
| 项目级配置 | `.claude/settings.json` 生效 | **只读用户级，项目级忽略并提示** | 克隆仓库就能在你机器上执行 shell，这个口子不该开。做团队共享得先有"内容哈希批准"（见第七节） |
| 多 hook 执行 | 并行跑完再合并（deny 优先） | **串行，遇 exit 2 即停** | 单线程交互里并行只省几十毫秒，却让日志交错、没法"前一个结果影响后一个" |
| 默认超时 | 60s（上限 600s） | 30s（上限 300s） | 这里是"敲完命令等它跑"的场景，30 秒还没结果用户已经在怀疑卡死 |
| handler 类型 | command / http / mcp_tool / prompt / agent | 只有 command | 后面几种要么要再调一次模型（花钱），要么要连 MCP，属于另一套东西 |

## 三、挂点：四个方法集中在一个区块

全部在 `core/conversation.py`，互相挨着：

```
_hook_payload()            拼 stdin 内容
_run_session_start_hooks() start_conversation 里，build_system_message 之前
_pre_tool_hooks()          单条路径在权限确认之前；批量路径在 run_one 里逐条
_post_tool_hooks()         _execute_tool 成功后 / run_one 成功后
_run_session_end_hooks()   shutdown() 最前面
```

两个关键设计：

**1. `PreToolUse` 必须在权限确认之前。**
用户按下"同意"之后才被告知"hook 不让干"，那次确认白点了；放前面还有个附带好处——被拦掉的调用连高危提示都不会出现，屏幕更干净。

代价是路径分开：单条走 `_handle_tool_calls`，批量走 `_execute_tools_parallel.run_one`。为什么批量要单独过一遍——收集批次时 `_collect_parallel_batch` 只判断了"能不能并发"（同步），没跑 hook（异步），所以批里每条都必须自己过。

**2. 拒绝用异常（`HookBlocked`），不新造消息类型。**
批量路径里每条调用在自己的协程里跑，异常天然做到"只中断这一条、其他照常完成"。异常最终被现有的 `except Exception` 兜住，变成一条工具失败消息给模型——第 14.2 轮建的那条自纠错链路直接复用。

## 四、SessionStart 的输出怎么进提示词

`PromptManager` 是单例（`/resume`、子 agent 共用），往里塞会话级状态会串味。所以：

1. `_run_session_start_hooks()` 把 stdout 存进 `Conversation._hook_context`；
2. `build_system_message()` 在 `get_system_prompt()` 的结果末尾拼一段：

```
## 会话启动时注入的信息（hook 生成）
<这里>
```

放末尾而不是开头：环境信息本来就该排在提示词尾部（第 11 轮的判断），hook 给的 `git status` / TODO 列表正是同一类内容。没有 hook 输出时，拼接结果和以前一字不差。

## 五、踩到的坑：Windows 上中文全变问号

第一次实测，`echo 工作区干净` 进到上下文里是 `'�������ɾ�'`。

根因有两层：

1. `create_subprocess_shell` 在 Windows 走 `cmd.exe`，它按**控制台代码页**（简体中文 cp936）输出；
2. 而 `locale.getpreferredencoding(False)` 在本机返回 `"utf-8"`（Anaconda 环境开了 UTF-8 模式）——按它解码正好是错的。

修法（`_decode_output`）：先严格 UTF-8（过得去就一定是 UTF-8），失败再按 `oem` → `mbcs` → locale 依次尝试。同时给子进程设 `PYTHONIOENCODING=utf-8`，让用户的 Python 脚本统一输出 UTF-8。

测试里专门留了一条 `cmd echo 的中文正常`（Windows 限定），改解码逻辑前先看它。

## 六、容错：哪些错必须说、哪些可以静默

| 情况 | 行为 | 理由 |
|---|---|---|
| `settings.json` 不存在 | 完全静默 | hooks 是可选功能，没配的人不该每次启动都看到提示 |
| JSON 坏了 | 一行黄字（带行列号），不加载 | 配置坏了不该让 CLI 起不来；但绝不能静默——"配了没生效"最难查 |
| 未知事件名（`PretoolUse`） | 一行黄字，跳过 | 十有八九是拼写错误，也可能是抄了没实现的事件 |
| 不支持 handler 类型 | 一行黄字，跳过该条 | |
| `timeout` 写错 | 退回 30s，不报错 | 一个数字不该废掉整条 hook |
| 正则写错 | 当不匹配，静默 | 加载期没法验证；真写错的表现是"hook 不生效"，比每次启动报正则错误好查 |
| 超时 | 杀进程 + 黄字，**不阻断** | 一条记日志的 hook 卡住，不该把用户的工具调用也拦下来 |
| 退出码非 0 非 2 | 黄字，继续 | |

## 七、验证

`python test/test_hooks.py` —— 35 条断言，全部用临时目录里的脚本，不碰真实配置：

- 解析：不认识的类型/事件/空 command 各一条提示；`timeout` 被压到上限；缺省 `type` 按 command；
- 坏 JSON：不抛异常、提示带行号；
- `matcher`：空 / `*` / 精确 / `|` / 正则 / 大小写敏感；
- 执行：stdin 与环境变量到位、exit 0 的 stdout 进 context、exit 2 的 stderr 当原因、JSON `decision=block`、exit 1 非阻断、超时不阻断；
- **串行短路**：第一个 exit 2 之后，第二个 hook 的脚本没有产生副作用（用文件是否被创建来验证）；
- 中文：Python 脚本 + `cmd echo` 两条路都不乱码。

端到端冒烟（假 Conversation，不调模型）：`SessionStart` 的 `echo workspace=clean` 确实拼进了系统提示词；`PreToolUse` 对 `dir` 放行、对 `rm -rf /` 返回拒绝原因；`SessionEnd` 正常执行。

回归：`test_mcp_cli.py` 52/52、`test_mcp_status.py` 23/23、`test_compress_boundary.py` 37/37。

## 七点五、第 32.1 轮补记：两个上限

上线当天复盘出两个"迟早出事"的缺口，补在同一轮。

**1. hook 输出没有上限。** `SessionStart` 的 stdout 直接进系统提示词，`PreToolUse` 的进工具结果。一条 `git log` 或 `npm ls` 能吐几千行——等于把上下文预算和钱包一起交出去，而且每一轮都要为它重付一次输入费用。
现在 `_clamp_text()`：上下文单条截到 **4000 字符**，阻断原因截到 **1000**，末尾注明「已截断 N 字符」。为什么不闷声截断：用户拿着缺尾的日志去对问题，永远对不上。

**2. 失败提示没有节流。** 一条写坏的 hook（语法错、路径写错）会在**每次**工具调用前失败。原来每次都打一行黄字，一次对话能刷几十行完全相同的提示；用户会逐渐学会无视它——那比不提示更糟。
现在每个「事件:命令」最多报 **3 次**，第 4 次改说「之后不再提示」，之后安静。**失败本身仍然被吞掉、不阻断流程**，变的只有提示频率。

测试从 35 条涨到 42 条，新增 7 条专门盯这两件事：超长 context、超长阻断原因、连续失败 5 次的提示曲线（1 / 1 / 1 / 1+说明 / 0），以及"被节流之后仍然不阻断"。

## 八、没做的事

- **`Stop` / `SubagentStop` / `UserPromptSubmit`**：`Stop` 要能"让模型继续"，涉及主循环的 continue 语义和防死循环，单独一轮做。
- **项目级配置 + 哈希批准**：设计里写过（`.thinker/hooks.approved` 记 sha256，仓库改了自动失效），这一轮按选择只做用户级。
- **`allow` 跳过权限确认**：`PreToolUse` 现在只能"拒绝"，不能"批准"。允许它批准等于让配置绕过权限系统，是新的风险面。
- **`updatedInput`（改写工具参数）**：比拒绝更危险——脚本可以悄悄把 `file_read` 的路径换掉。P3 再说。
- **`/hooks` 列表命令**：现在只能靠启动时的一行提示确认"配置读到了"。要做成 `/mcp` 那样的一屏清单，是下一轮的小活。
