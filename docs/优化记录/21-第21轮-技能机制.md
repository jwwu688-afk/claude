## 一、一句话方案

技能就是一个**带 frontmatter 的 markdown 文件**，价值全在"什么时候加载"：

| 层 | 什么进上下文 | 什么时候 | 量级 |
|---|---|---|---|
| 1 | 只有 `name + description`（在 `skill` 工具的说明书里） | 常驻，每轮都发 | 几百 token |
| 2 | 正文（`skill` 工具的结果 / `/技能名` 的用户消息） | 模型判断"对得上"时 | 两三千字 |
| 3 | 正文里提到的 `reference.md`、脚本 | 模型自己 `file_read` / `cmd_runner` | 按需 |

这三层就是 Claude Code 说的 **progressive disclosure**。整套东西没加新依赖、没改主循环，
落在现有的 `BaseTool` + `REGISTRY` 两张登记表上。

## 二、改前 vs 改后

**改前**：想让模型"按某个固定流程干活"，只有一条路——把流程写进 `THINKER.md`。

```text
THINKER.md（全文注入系统提示词）
  ├── 项目约定
  ├── PDF 处理流程      ← 这三个都每轮付费
  ├── 发版流程
  └── review 清单
```

问题不是"写不下"，是**每一轮都在为用不上的东西付钱**：一次对话里 review 清单可能一次都不触发，
但它的 token 每轮都发；写详细了更糟——越详细越贵，于是人开始主动压缩手册，
最后写出来的东西既不够细、又还在付费。

**改后**：

```text
.thinker/skills/pdf/SKILL.md        常驻：只有 "pdf：读取、解析、抽取 PDF（参数：[文件路径]）"
.thinker/skills/release/SKILL.md    常驻：只有一行描述
.thinker/skills/review/SKILL.md     常驻：只有一行描述
        │
        └─ 用户提到"把这个 pdf 的表格抽出来"
             │
             ├─ 模型：调 skill(skill="pdf", args="D:/a.pdf")
             ├─ 工具：现读 SKILL.md → 变量替换 → 截断 → 作为工具结果进历史
             └─ 模型：按正文步骤干活（正文里让它读 reference.md，它就自己读）
```

**一句话**：`THINKER.md` 管"永远要遵守的规矩"，技能管"这类活该怎么做"。
前者每轮都读，后者用完就留在历史里，不会再出现在下一轮的前缀中（它是增长方向上的消息，不是前缀）。

## 三、目录、发现与校验

### 3.1 两个目录，项目赢

```text
~/.thinker/skills/<名字>/SKILL.md            全局（跟人走，跨项目）
<启动时的 cwd>/.thinker/skills/<名字>/SKILL.md  项目（进仓库，跟项目走）
```

同名时 **项目 > 全局**，和 Claude Code 的"企业 > 个人 > 项目"正好相反。两个理由都不是口味问题：

1. **和 `THINKER.md` 的层叠方向一致**。那里是"全局先加载、项目后加载，越靠内层越优先"。
   两套配置给出相反的优先级，用户迟早会遇到"记忆按项目走、技能按全局走"的怪事。
2. **用户的直觉就是"我在这个项目里改的技能应该赢"**。Claude Code 那条规则是给组织管控用的
   （企业要能压住个人），本项目没有企业层，剩下的只有直觉。

实现上利用"后写覆盖先写"：按 `[全局, 项目]` 顺序扫，后面覆盖前面，和 `memory.load()` 一个套路。
被覆盖的那份记进 `shadowed`，`/skills` 里能看到"同名，被项目版本覆盖"——不静默。

### 3.2 三种刻意的限制

| 限制 | 为什么 |
|---|---|
| **只扫一层，不递归** | Claude Code 支持 `apps/web/.claude/skills` 变成 `/apps/web:deploy`，那是 monorepo 需求。本项目的命名空间会带来前缀、冲突、展示三个概念，而维护的人只有一个 |
| **扫描时只读前 4096 字符** | frontmatter 就在开头。几十个技能也不必在启动时全文进内存；顺带好处：**改正文不用 reload** |
| **`iterdir` 必须 `sorted`** | 不排序的话顺序取决于文件系统，`/skills` 和工具说明书每台机器都不一样，排查时对不上 |

### 3.3 同时支持单文件

`<名字>.md` 和 `<名字>/SKILL.md` 都认。

技能和"子 agent 定义"最大的区别，是技能天生需要目录（核心价值 = 正文 + 一堆按需加载的支撑文件）。
但如果真只有正文，逼用户建一个只装一个文件的目录纯属添麻烦。

> ⚠️ 别把这里的目录扫描和第 18 轮删掉的 `.thinker/agents` 混为一谈。
> 那次删的是"子 agent 从 md 定义"，理由是四个内置类型够用、不需要每人维护一份；
> 技能是**给用户自己写手册**的地方，没有目录就没有这个功能。长得像，目的不同。

### 3.4 校验：会拒的、会警告的

| 情况 | 处理 | 为什么 |
|---|---|---|
| 名字含空格 / 大写 / 下划线 / 超 64 字符 | **拒载** + 警告 | 名字同时是斜杠命令名：`/My Skill` 在 `parse()` 里会被切成"命令 My + 参数 Skill"，敲不出来 |
| 名字与内置命令重名（如 `cost`） | **拒载** + 警告 | 内置优先。静默替换会让用户以为 `/cost` 坏了 |
| 文件不以 `---` 开头 | 整份当正文，`name` 取文件名 | 对齐 Claude Code：没 frontmatter 的技能照样能用 |
| frontmatter 解析失败 | 字段尽量保留 + 警告，技能仍加载 | 崩掉整个启动不值得；但**必须**留警告，不能重犯"静默降级"的错 |
| 有 `---` 开头没闭合 | 整份当正文 + 专门的警告 | 不猜"哪儿该算正文"，也不能让用户以为字段生效了 |
| 没有 `description` | 仍加载、**仍进**工具说明书，描述位置显示「（未写描述，调用后见正文）」+ `/skills` 提示补一句 | 第 21.1 轮改成「技能一律可见」：藏起来会变成「我明明写了技能，模型却说不知道」 |
| 正文超 20000 字符 | 截断 + 注明总长度 | 必须低于 `MAX_TOOL_OUTPUT_CHARS`(30000)，否则业务上限是假的 |
| `allowed-tools` / `model` / `disable-model-invocation` 等本版不用的字段 | 加载、**直接忽略**（第 21.2 轮取消了"未生效"标注） | 多写几行不该让"拷一份别人的技能"变成需要排错的事；标注本身也要四处维护 |

`description` 进工具说明书时截到 **300 字符**（Claude Code 是 1536）：
工具说明书的 description **每轮都发**，10 个技能 × 1536 ≈ 每轮白烧 4000 字符；
而模型判断"要不要用"看第一句就够，和子 agent 的 `MAX_DESCRIPTION_CHARS = 160` 是同一个取舍。

## 四、SKILL.md 的格式与假 YAML

```markdown
---
name: pdf
description: 读取、解析、抽取 PDF 的正文与表格。用户提到 pdf/论文/扫描件/发票时使用。
disable-model-invocation: false
argument-hint: [文件路径]
---

# PDF 处理

用户要处理的文件：$ARGUMENTS

## 步骤

1. 先用 `file_read` 看一眼文件头，确认不是加密或纯图片扫描件。
2. 需要按页抽取时，运行 `${SKILL_DIR}/scripts/extract.py <路径>`。
3. 抽取出的页数、字符数、是否有表格，在汇报里写清楚。

## 更多资料

- 完整参数说明见 `reference.md`（模型按需 `file_read`）
```

### 4.1 字段

| 字段 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `name` | str | 目录名/文件名 | 技能名，同时是斜杠命令名 |
| `description` | str | 空 | 进工具说明书，模型靠它决定用不用 |
| `user-invocable` | bool | true | false = 不出现在斜杠命令里（模型仍可调用） |
| `argument-hint` | str | 空 | 只影响 `/help` 的用法显示，如 `[文件路径]` |
| 其他任何字段（`allowed-tools` / `model` / `hooks` / `disable-model-invocation` …） | — | — | **不读取、直接忽略**，不报错也不在 `/skills` 展示 |

布尔值接受 `true/false/yes/no/on/off/1/0`，大小写不敏感。

### 4.2 为什么敢自己写解析器

`THINKER.md` 明令不加依赖，`pyyaml` 也不是标准库。而技能头部只用到三种写法：

```yaml
key: 单值
key: [a, b]
key:
  - a
  - b
```

明确不支持：多行字符串（`|` / `>`）、嵌套 map、锚点、行尾注释、引号里的 `: `。
遇到不认识的写法就**跳过那一行并留一条 problem**，不是静默丢——能解析多少算多少，
因为"某一行坏了"不该把同一份文件里写对的 `name` 一起丢掉。

`---` 必须是**文件第一行**（允许 UTF-8 BOM）。很多人在顶部先写一句 `# 标题` 再写 frontmatter，
然后困惑为什么字段不生效——这里不猜，整份当正文，并由 `build_spec` 给一条警告。

### 4.3 变量只有三个

| 变量 | 替换成 |
|---|---|
| `$ARGUMENTS` | 调用时传的整串参数 |
| `${SKILL_DIR}` | `SKILL.md` 所在目录（正斜杠） |
| `${PROJECT_DIR}` | 启动时的 cwd（正斜杠） |

两条必须遵守的规则：

- 正文里**没有** `$ARGUMENTS` 而用户传了参数 → 在末尾追加 `ARGUMENTS: <值>`。
  不追加的话参数会凭空消失，用户以为 `/pdf a.pdf` 没生效。
- **先展开路径变量、再替换 `$ARGUMENTS`**。顺序反了的话，用户参数里碰巧出现的
  `${SKILL_DIR}` 会被二次展开——这种"我的参数被吃了"极难查。

不做 `$0` / `$1` / 命名参数：要做就得处理"引号怎么切、`$1.00` 要不要替换、占位符缺失时保留还是清空"，
收益远小于成本。

## 五、两条调用链，一个出口

```text
模型自动调用                          用户手动调用
skill(skill="pdf", args="a.pdf")     /pdf a.pdf
        │                                   │
        ▼                                   ▼
  tools/skill_tool.py               commands._make_skill_handler
        │                                   │
        └──────────► SkillManager.load_body(spec, args) ◄────────┘
                             │  现读 SKILL.md（改字立即生效）
                             │  $ARGUMENTS / ${SKILL_DIR} / ${PROJECT_DIR}
                             │  20000 字符截断
                             ▼
                  作为 tool 消息 / 作为 user 消息写进历史
```

渲染逻辑只有一份（`skill_spec.render`），所以 `/pdf` 和 `skill("pdf")` 拿到的正文、
变量替换、截断行为完全一致——这正是第 14 轮斜杠命令反复强调的"两处各写一遍，下次改动只会补在一处"。

### 5.1 斜杠调用为什么要走"用户消息"，而不是"先让模型调一次工具"

1. 用户是**主动点名**的，语义上就是"我说了这段要求"，不是"模型自己查到的资料"；
2. 少一轮往返。走工具的话：请求 1（模型决定调 skill）→ 请求 2（模型看正文干活），白花一次输入；
3. 对齐 Claude Code：斜杠调用把正文渲染进消息，模型自动调用才走 Skill 工具。

落地方式是 `Conversation` 的一个"待发消息"槽位：

```python
# 命令 handler
conversation.set_pending_input(f"[技能已加载：{name}]\n{body}")

# 主循环 _read_user_input（handle_command 之后、add_message 之前）
pending = self.take_pending_input()
if pending:
    return pending        # 当成用户这一句，正常进历史
```

这两行的位置很关键：

- **在 `handle_command` 之后**：普通命令永远不写 pending，所以"斜杠命令不进历史、不计费"
  （第 14 轮）的规矩一字不变；
- **在 `add_message` 之前**：返回的这段文字会走正常流程被记进历史、发给模型——这正是技能想要的。

`take_pending_input()` 是"取出即清空"，避免同一段正文被发两次、白付两次输入。

### 5.2 工具只在真的有技能时登记

`ToolManager.refresh_skill_tool()` 按 `SkillManager().count()` 决定登记/摘掉。

- 好处：零技能的用户每轮少发约 400 token 的说明书，模型也不会去调一个空工具；
- 代价：`/skills reload` 后新出现的技能要补登记，`tools` 清单变一次、前缀缓存失效一次。

这个代价是一次性的，已经写进方法注释——否则以后会有人把"reload 之后突然贵了一下"当 bug 查。

### 5.3 子 agent 两道闸都不给

`_get_available_tools` 的 `exclude` 从 `{"task"}` 变成 `{"task", "skill"}`，
`_is_tool_allowed` 里和 `task` 一样直接拒。两个理由：

1. 子 agent 的提示词是**刻意精简**的（`agent_spec.build_system_prompt` 只给三行环境）。
   技能正文动辄两三千字，可能比它的任务本身还长，而它只需要"找东西/看代码"；
2. 技能正文是写给**主 agent** 的，里面很可能写着"用 `todo_write` 记一下进度""拿不准就派个子 agent"。
   子 agent 拿到这些指令会去撞 `todo_write`——而那个工具的状态存在单例实例上，
   一撞就覆盖主 agent 的待办清单（第 18 轮记过的坑）。

## 六、安全：技能不能改权限

这是整套设计里最重要的一条：**技能只是一段文字**。

- 正文里写"直接 `rm -rf` 不用问"，模型照样会弹确认——`classify()` 只看工具名和参数，
  不看"这段话是不是来自技能"；
- 技能里的脚本被调用时也只是普通 `cmd_runner` 调用，该问就问。

所以检出一个别人写的技能，风险**不超过**检出一个 `THINKER.md`——两者都是"仓库里的文字被相信"。

### 为什么不做 `allowed-tools`

Claude Code 的 `allowed-tools` 语义是"调用这一轮**免审批**"，它自己也反复警告：
项目里的技能能拿到预授权，`-p` 模式下即使从没信任过这个目录也生效。

本项目的 `permissions.py` 现在守着一条底线：**模型不能给自己发通行证**。
加 `allowed-tools` 等于开了第一个"内容能让权限变松"的口子，而这个口子的输入恰好是仓库里的文本。

要免审批，正确的位置是 `classify()` 里的"用户记忆的允许清单"（ROADMAP 里"本次会话总是允许"那一项），
而不是让 markdown 决定。这一条也写进了 `THINKER.md`，否则下一轮一定有人想"顺手支持一下"。

## 七、成本

| 项 | 估算 |
|---|---|
| 工具说明书（框架话术） | ~200 token |
| 每个技能一行 | 名字 + 300 字符描述 ≈ 120 token |
| 10 个技能 | ~1400 token / 轮 |

`available_block()` 因此有两道闸：描述截 300、
最多 50 条且整块不超过 6000 字符，超了注明"还有 N 个未列出，用 `/skills` 查看"。

**清单要短，但不靠"藏技能"变短。** 超长时给的是"还有 N 个，用 `/skills` 查看"——
信息没丢，只是不占每轮预算。第 21.1 轮把"可见性"整个维度删掉之后，这句话才真正成立。

### `is_repeatable = False`

L3 Microcompact 会把"可重复查询工具"的旧结果折叠成"重跑即可"。技能正文**不能**被这样折叠：

- 它的语义是"跨轮生效的指令"，不是"查回来的数据"；
- 折叠之后模型不知道自己少了什么，会继续按半截规矩干活，而且没有任何报错；
- 真要收缩，应该发生在 L5 摘要（那里会真的重写对话），而不是 L3 的静默折叠。

父类默认就是 `False`，`skill_tool.py` 里仍然显式写了一遍，并在测试里钉住
（`Skill.is_repeatable is False`）——防止有人顺手改。

## 八、热更新的口径要分两半

| 改了什么 | 什么时候生效 |
|---|---|
| `SKILL.md` **正文** | **立即**。正文每次调用都现读 |
| **frontmatter**（名字、描述、布尔） | 要 `/skills reload`。它们进了工具说明书和 REGISTRY，是注册期快照 |

这个区分不是省事，是省不掉：元数据必须常驻才能让模型"知道有这个技能"，常驻就意味着有快照。
写清楚比假装支持全套 watcher 更诚实——Claude Code 那套 watcher 有 6 条边界
（bare mode、`--add-dir`、启动时不存在的目录……），本项目一条都不需要。

## 十一、这一轮踩到的三个坑

### 1. `argument-hint: [文件路径]` 被假 YAML 当成列表

假解析器看到 `[...]` 就当内联列表，于是拿到 `["文件路径"]`，`str()` 出来是
`/pdf ['文件路径']`——`/help` 里像程序坏了。

没有改解析器开特例（"哪些键永远不是列表"以后每加字段都要记得加一条），
而是在取字段处加 `_hint_text()` 还原方括号写法。**教训**：解析器和字段语义之间
永远有一层"这个键允许什么形态"，别指望通用解析器替业务字段做判断。

### 2. "写完了却扫不到"——扫描结果是有缓存的

`SkillManager` 第一次查询才扫（`_ensure_scanned`），之后结果就是快照。
测试里"建完文件立刻断言"全部失败，因为那一次查到的是空目录。
这不是 bug，是真实口径（改完要么重启、要么 `/skills reload`），
测试里补 `rescan()` 等于替用户按一次 reload。**教训**：写测试时先问"这个系统里，
'写完'到'看得见'之间隔着哪一步"，不然会把正确行为写成 bug。

### 3. 上一轮登记过的技能命令，会被当成"内置命令"自己撞自己

同名冲突检查要排除内置命令，但 `REGISTRY` 里同时有**内置命令**和**上一轮登记的技能命令**。
不排除后者的话，reload 之后一个技能会因为跟它自己的旧命令重名而被拒载——
表现为"第一次能用，reload 一次就消失了"。

解法是 `commands._skill_command_names` 记账 + `builtin_command_names()` 求差集。
**教训**：往一张共享注册表里写"用户数据"（技能）时，必须能把自己写的那部分认出来。

## 十四、第 21.1 轮补丁：砍掉「模型可见性」这一维

方案原稿里技能有两个开关：`disable-model-invocation`（模型看不看得见）和
`user-invocable`（人能不能 `/名字`）。第一版照做，用着发现**这个维度不值它的复杂度**：

- 它让"同一个技能"在不同条件下有两种状态（在清单里 / 不在清单里）。模型一报"不知道有这技能"，
  就得先排除两种可能：描述没写？被 disable 了？排查方向凭空多一条；
- 收益只有几十个字符的 token；
- 而"技能文件明明在那、模型却不知道"恰恰是最容易让人怀疑功能坏了的现象。

所以整条规则删掉：**所有加载到的技能一律对模型可见**。

| 位置 | 改动 |
|---|---|
| `SkillSpec` | 删掉 `disable_model_invocation` 字段和 `visible_to_model()` 方法 |
| `available_block()` | 不再过滤，遍历全部；没描述的行显示「（未写描述，调用后见正文）」 |
| `Skill.act()` | 删掉"只能由用户手动调用"的拒绝分支 |
| `SkillSpec` | `disable-model-invocation` 不再读取（连同所有非本版字段一起忽略，见 21.2） |
| `cmd_skills` | 去掉"仅手动调用"标记；"没有描述"的提示改成"清单里只显示占位" |

**为什么字段还认**：从 Claude Code 拷来的技能里它很常见。直接忽略的话，用户会以为
"我标了只给手动用、怎么模型还是调了"；字段保留解析但不生效（21.2 连标注也一起删了）。

**没变的**：`user-invocable` 仍然是真开关（它管斜杠命令表，不涉及模型认知）；
清单长度仍由 `MAX_SKILLS_IN_BLOCK` / `MAX_SKILLS_BLOCK_CHARS` 卡。
"让模型知道全部技能"和"别把说明书撑爆"不矛盾——超长时给的是"还有 N 个，用 /skills 查看"。

验证：`test_skills.py` 从 56 条断言增加到 59 条，两处旧用例改成新口径
（缺描述仍可见可调用、`disable` 字段仍可见可调用），全绿。

## 十五、第 21.2 轮补丁：连"未生效字段"也删了

21.1 把 `disable-model-invocation` 从"生效字段"降级成"未生效字段"，但它仍然要走一条完整的流水线：
在 `UNSUPPORTED_FIELDS` 登记 → `build_spec` 逐个比对 → 存进 `SkillSpec.unsupported` →
`/skills` 拼成一句标记 → 测试断言它被标出来。

这四步**不改变任何行为**，只是多一行解释文案。而它带来两个长期成本：

1. 每加一个"本版不做"的字段，就要记得到那张表里补一条；
2. `SkillSpec` 为一个纯展示字段多背一个属性，`/skills` 多一段拼接逻辑。

所以整张表删掉：`SkillSpec` 不再有 `unsupported`，`/skills` 不再标"未生效"。

```text
改前：allowed-tools → 登记 → 比对 → 存字段 → 展示"未生效"
改后：allowed-tools → 解析进 fields → 没人读它 → 丢掉
```

**现在的规则一句话**：认得字段（`name` / `description` / `user-invocable` / `argument-hint`）就读进
`SkillSpec`，其余一律忽略——不报错、不警告、不展示。

**代价说清楚**：从 Claude Code 拷技能过来的用户，写了 `allowed-tools` 却发现没有免审批，
只能从文档（本文 §六、THINKER.md）里知道原因，界面上不再提示。这是有意的取舍：
把解释放进文档，把代码里的概念数量降到最低。

验证：`test_skills.py` 59 条断言仍全绿（原来的"未生效字段被标出来"改成了
"多余字段不产生任何警告"）。

## 十六、第 21.3 轮补丁：能直接吃 GitHub 上的现成技能

试装官方仓库（`anthropics/skills`，20 个技能）里的 `doc-coauthoring`（单文件 15KB、纯文字），
**零改动就加载成功**。但那个技能恰好没用到两个常见写法，而真实仓库里它们很普遍，所以补上：

| 写法 | 改前 | 改后 |
|---|---|---|
| `description: >-` / `\|`（YAML 多行块） | 记一条"不支持多行字符串"，描述变空 | `>` 折叠成一行、`\|` 保留换行；末尾的 `-`/`+` 不区分，统一去首尾空白 |
| `${CLAUDE_SKILL_DIR}` / `${CLAUDE_PROJECT_DIR}` | 原样留在正文里，模型会去执行一条带 `${...}` 的假路径 | 分别展开成技能目录、当前工作目录 |

为什么这两处值得单独补：它们的失败**都是静默的**——描述空了，清单里只显示"未写描述"；
变量没展开，正文看起来"没毛病"，直到模型真的去 `cat` 一个不存在的路径。
导入的人不会怀疑解析器，只会觉得"这个技能不好用"。

仍然不兼容、也不打算兼容的：

- `allowed-tools` / `model` / `hooks` / `context` / `disable-model-invocation`：解析完丢弃（21.2）；
- 正文里的 `!\`cmd\`` 动态注入：不执行（作为普通文字进上下文，这反而是安全的）；
- 工具名 `Read` / `Write` / `Bash`：不替换。模型看到自己的工具清单后能自己映射，
  而做"全文替换"会改坏正文里的普通英文单词（比如 "Read the file" 里的 Read）。

装完的当天又把官方 20 个技能全装了（`anthropics/skills` 的 `skills/*`，共 13MB，
其中 canvas-design 带 5.6MB 字体、docx/xlsx/pptx 各 1MB 带 Python 脚本）。
结果：**20 个全部加载，0 警告**；清单 20 行 / 5717 字符（没触发 6000 的截断）；
`/help` 里变成 29 条命令（9 条内置 + 20 条技能）。

顺带修掉一个只有真实技能才会暴露的问题：`claude-api` 的描述用了 `|` 字面块，
里面是真实换行，压平前它会把 `- 名字：描述` 拆成两行，模型看到的是一条断掉的清单项。
现在 `build_spec` 取 description 时统一 `" ".join(split())` 压平——描述按契约就是一句话，
放在这一层是因为 `/skills` 和工具说明书两处都要用。

验证：`test_skills.py` 从 59 条断言增加到 **65 条**（折叠块、字面块解析/压平、两个变量别名），
27 个测试脚本全绿。

## 十七、第 21.4 轮补丁：支撑文件的路径基准

技能目录里常带支撑文件（`reference.md`、`examples/*.md`、`scripts/*.py`），
正文里写的是**裸相对路径**。本项目的文件工具把相对路径解析到**启动时的项目根**，
于是模型照着正文做会找错地方——实测：

```text
正文：读 `examples/3p-updates.md`
file_read 解析成：D:/code/thinker/examples/3p-updates.md      ← 项目根
真实位置：        ~/.thinker/skills/internal-comms/examples/3p-updates.md
```

报错是"文件不存在"，模型不知道是**基准**错了，只会换写法乱试或放弃。
这不是某个技能写错了——`internal-comms`、`pdf`、`docx`、`xlsx`、`pptx`、
`mcp-builder`、`theme-factory`、`webapp-testing`、`algorithmic-art` 等十几个都是这种写法。

修法：加载正文时在最前面补一段，成本约 80 字符、只在加载时出现一次：

```text
【技能目录】C:/Users/Jarvis/.thinker/skills/pdf
正文里提到的相对路径（如 `examples/x.md`、`scripts/y.py`）都相对这个目录。
读取或执行它们时请用绝对路径（C:/Users/Jarvis/.thinker/skills/pdf/...），或先 cd 到该目录再执行。
```

三种情况不加：单文件形态（父目录里可能是别的技能）、目录里只有 `SKILL.md`、
目录读不了（`OSError` 时宁可不提示也不让加载失败）。

验证：`test_skills.py` 65 → **69 条断言**（新增"有支撑文件加提示 / 提示是绝对路径 /
只有 SKILL.md 不加 / 单文件不加"）；真实技能抽查：`internal-comms`、`pdf` 有提示，
`doc-coauthoring`、`release` 没有；27 个脚本全绿。

## 十八、第 21.5 轮补丁：`/skills install` —— 让 thinker 自己装技能

动机：用户问"能不能让 thinker 自己装一个 skill"。此前它没有这条路径——
用 `cmd_runner` 下载 + `file_write` 写入虽然理论可行，但每一步都要审批，
而且 `git clone` 在本机直接失败（`github.com` 的 TLS 被 schannel 中断）。

### 用法

```text
/skills install https://github.com/anthropics/skills        # 仓库页地址
/skills install https://github.com/owner/repo/tree/dev      # 指定分支
/skills install D:/my-skills/some-skill                     # 本地目录
/skills install <地址> --force                               # 覆盖同名
```

### 设计

| 决策 | 理由 |
|---|---|
| 下载用 `urllib` + codeload tar.gz，**不用 git clone** | 不需要装 git；本机 github.com 不通而 codeload 通；我们只要文件不要历史 |
| 逐成员安全解压 | 压缩包成员可以是 `../x` 或绝对路径（zip-slip）；tar 的 symlink 还能写绝对路径。逐条校验"无 `..`、非绝对、跳过非普通文件"，代价是极端情况少解几个文件 |
| 真名用 `build_spec` 解析 | frontmatter 的 `name` 可以和目录名不同；命令名以配置为准 |
| 同名不覆盖，`--force` 才覆盖 | 技能是"写进每轮上下文的指令"，悄悄覆盖用户改过的版本比装不上更糟 |
| 找到即装、上限 50 个 | 防止有人贴一个巨型仓库把磁盘和工具说明书一起撑爆 |
| 装完立刻重扫 + 重新登记 | 否则"装成功"和"看得见"拆成两步，中间用户只会觉得命令没生效 |

### 真机验证

`/skills install https://github.com/anthropics/skills` 走完整流程：
下载 4.1MB → 解压 → 找到 21 个 SKILL.md（20 个已存在 → 全部跳过，新增 `template-skill` 装上）→
重扫登记 21 条命令。临时目录无残留（`finally` 清理生效）。

> 顺带的发现：仓库里的 `template/` 其实是个空模板技能（name 叫 `template-skill`），
> 装"整个仓库"会把它一起带进来。装完看一眼 `/skills`，不用的删目录即可。

### 测试

`test_skills.py` 69 → **78 条断言**（本地安装 / 非法名跳过 / 同名不覆盖 / `--force` 覆盖 /
GitHub 地址三种写法的改写 / 非 GitHub 不改写 / zip-slip 拒绝与正常解出），27 个脚本全绿。

## 十九、第 21.6 轮补丁：装上学术技能后暴露的两个问题

用户装了 `academic-research-skills`（5 个技能）之后，`/skills` 出现 31 条警告、
描述刷满一屏，而且清单末尾出现了"另有 5 个技能未列出"。两个独立的问题：

### 1. 31 条"不支持嵌套字段"警告——该静默的没静默

这 5 个技能的 frontmatter 带一个 `metadata:` 嵌套块（`version` / `status` /
`task_type` / `related_skills`…）。假 YAML 不支持嵌套 map，于是**每个缩进行记一条警告**。

问题不在"不支持"——21.2 早就定了"认得就读，不认得就丢"——而在解析器**违背了这个口径**：
不认识的写法照旧记警告。5 个技能 × 每个约 6 行 = 31 条，全部不影响任何行为，纯噪音。

修法：嵌套行**静默吞掉**（吞行的逻辑必须保留，否则嵌套里的 `version: x`
会被当成顶层键解析进 fields，等于替用户编造字段）。保留的警告只剩"真正影响功能的"：
名字不合法、与内置命令重名、frontmatter 没闭合、已知字段写坏（内联列表没闭合）。

### 2. 清单触顶——"装了但模型看不见"

25 个技能 × 描述截 300 字符 ≈ 7500 字符，超过 `MAX_SKILLS_BLOCK_CHARS = 6000`，
排在后面的 5 个技能整个被挤掉（清单末尾出现"另有 5 个未列出"）。
用户"全都装上"的意图和上限直接冲突。

修法：6000 → **9000**（环境变量仍可覆盖）。9000 ≈ 3000 token/轮，
是 25 个技能全可见的代价。边界也写进了注释：技能再往上加就该**删**，
而不是继续调大这个数——清单撑到一万多字符就成了第二份系统提示词。

### 3. 顺带：`/skills` 的描述显示截到 120 字符

`academic-paper` 的描述有 1000+ 字符（触发词堆了中英日韩西五语），
`/skills` 打印原文会刷掉一整屏。现在给人看的截 120 字符（模型侧仍是 300）。

### 验证

`test_skills.py` 78 → **80 条断言**（嵌套 metadata 正常加载、不产生任何警告）；
实测：25 个技能、`warnings = 0`、清单 25 行 / 7320 字符、无"未列出"提示；
`/skills` 输出从一百多行降到 31 行。27 个测试脚本全绿。

## 二十、第 21.7 轮补丁：会话文件懒创建（v0.10.1）

**需求原话**："每次启动不要新开一个会话，只有我真的问问题了才新开一个会话，也不包括斜杠命令。"

### 改前

启动就 `SessionStore.create(...)` 落一个 JSONL（header + system 两行）；
`/clear` 也立刻建新文件。后果：开 thinker 看一眼 `/cost` 就退出，也会留下空壳会话，
`/resume` 列表被这种"什么都没聊过"的文件填满。

### 改后的口径

| 动作 | 建会话文件？ |
|---|---|
| 启动 thinker | ❌ 系统提示词只进内存 |
| 敲本地斜杠命令（/cost /help /resume…） | ❌ 命令不进历史，自然不建 |
| **第一条真正发给模型的消息**（打字、或技能命令如 `/pdf x`） | ✅ 一次性写入 header + system + 这条消息 |
| `/clear` | ❌ 只清内存，提示"下一次真正提问时会创建" |
| `--continue` / `/resume` | 不变（文件本来就存在，续写） |

### 实现要点

- 懒创建的闸口放在 `add_message` 里（所有消息进历史的唯一入口），
  判据是 `role != "system"`——系统提示词每轮都由 `build_system_message()` 重新生成
  （日期/目录会变），单独落盘没有意义；
- 创建时用 `SessionStore.create(..., messages=self.messages)` 把当前整页（含本条）一次补写，
  **然后直接 return**，不能再 append 一遍，否则这条消息在文件里出现两次；
- `/clear` 走同一条路：`reset_conversation` 只把 `_session` 置 None，
  返回值的第二个元素可能是 `None`，`cmd_clear` 按 None 单独提示。

### 验证

`test_commands.py` 的 /clear 用例改成新口径：清空后 `_session is None`、
提示"下一次真正提问时才创建"、随后一条 user 消息触发建文件且内容为
header + system + 消息共 3 行。27 个测试脚本全绿，`thinker --version` → v0.10.1。

## 二十一、第 21.8 轮补丁：技能产出用中文

**需求**：用斜杠技能命令后，终端里模型回复是英文（技能正文是英文，且常自带英文输出模板
"Here's what I understand…"），用户希望结果用中文。

**为什么系统提示词压不住**：全局 THINKER.md 写了"中文回答"，但它是请求里**最靠前**的指令；
技能正文带着具体的英文输出模板出现在几千字符之后——对模型来说，离内容最近的指令最有效。

**修法**：在 `render()` 末尾（截断之后）固定追加一句：

```text
【回复语言】用中文回复用户；代码、命令、专有名词、文件路径保持原文。技能正文是英文不代表要用英文回复。
```

放在 render() 是因为它**同时覆盖两条入口**（斜杠命令 / skill 工具）——只改斜杠命令的前缀，
模型自己调工具时会漏。放在截断之后，所以不计入 20000 上限。不翻译正文本身：
13MB 的第三方技能翻不动，也翻不准；要的只是产出中文。

**测试**：81 条断言（新增"正文末尾带回复语言约束"）；
`没占位符：参数追加`的断言从 endswith 改成包含（约束句固定缀在最后）。
实际回复是不是中文要真机验证——这条指令的效果只有跑一次对话才知道。

## 二十三、第 21.10 轮补丁：/skills 列表重排（用户反馈"太乱"）

中文化之后用户截图反馈：能读了，但**乱**——名字和描述挤一行、
"触发：…"尾巴把每条拖到折行、续行顶格没有缩进，25 个技能缠成一团。

根因是混进了两 audience 的信息：`触发：写论文、write paper…` 是给**模型**挑技能用的，
人在列表里只需要"这是干什么的"。修法三条：

1. **砍触发尾巴**：摘要函数遇"触发：/触发:/Triggers:"（且出现在前 8 字符之后）即截断；
2. **名字列对齐**：按最长名字补空格（复用 /help 的显示宽度函数，中文按 2 列算）；
3. **摘要截 46 字**：名字列约 24 列 + 来源标签约 10 列 + 46 字 ≈ 84 列，
   常见终端一条命令恰好一行不折行。

效果：

```text
改前：/academic-paper  [全局] 按学术规范写论文：12 种模式（…）…（触发词堆 5 种语言，折 3 行）
改后：/academic-paper           [全局] 按学术规范写论文：12 种模式（全文/大纲/修订/摘要/文献综述…）
```

验证：`test_skills.py` 81 → **85 条断言**（砍尾巴 / 英文开头不误砍 / 空描述占位 / 46 字截断），
27 个测试脚本全绿。

## 二十四、第 21.11 轮补丁：突然换行——截断单位错了

21.10 重排后用户截图：大部分行整齐了，但**有的行还是突然折行**
（`academic-paper`、`discernment-nudge`、`release`…），看起来像随机发生。

根因一句话：**截断按"字符"算，终端折行按"列"算，中文一字占 2 列。**
"摘要截 46 字"对汉字是 92 列，加上名字列和 `[全局]` 标签 ≈ 127 列，
超出 110 列的终端就折。ASCII 多的行（如 `brand-guidelines`）没超，所以"有的折有的不折"。

修法：

1. 新增 `_truncate_by_width(text, max_cols)`——按 `_display_width` 累计列数截断，
   超宽补省略号；`_skill_summary_text` 的参数从"字符数"改成 `max_cols` 列；
2. `/skills` 里摘要预算**按终端实际宽度动态算**：
   `console.width - (名字列 + 前缀 + 标签)`，终端窄摘要自动短、宽自动长，
   带 `（标记）` 的行把标记列数也扣掉；
3. 底线 20 列：终端再窄也至少给摘要留一行。

教训写进函数注释：终端折行只认列数，凡是"显示层"的截断都必须按列数算，
`len()` 只对纯 ASCII 成立。

验证：`test_skills.py` 85 → **86 条断言**（60 列内截断 + 短描述原样）；
实测 79 列终端下所有技能行最大 77 列，无一折行。27 个脚本全绿。

## 二十五、第 21.12 轮补丁：/help 也折行——同一类问题的第二个入口

21.11 修完 /skills，用户截图：**/help** 里 `/frontend-design` 的摘要整段折到了第二行。
同一个病根的另一个入口：`_one_line_summary` 还在按"40 个字符"截——40 个汉字占 80 列，
加用法列就超宽。21.11 只修了 /skills，/help 没跟上——**教训在两处出现两次，
说明"截断按列算"应该是一条通用规则，而不是每次踩坑后打补丁。**

修法：

1. `_one_line_summary` 只负责"压平"（换行/连续空格 → 单空格），**不再按字符截**；
2. 截断挪到 `_print_help` 显示层：`console.width - 用法列宽 - 边距` 动态算预算，
   复用 21.11 的 `_truncate_by_width`；
3. 为什么不在注册时截：终端宽度是**显示期**才知道的事，注册期截死了，
   换个宽度的终端要么浪费要么照旧折行。

验证：34 条命令（9 内置 + 25 技能）在 79 列环境里全部 ≤79 列，无一折行。

## 二十六、第 21.13 轮补丁：折行的真凶——漏算的圆点前缀

21.12 修完 /help 后用户再截图：**格式更乱了**——摘要整段掉到第二行顶格，
和下一条命令的圆点缠在一起。这次把账算对了：

`print_info` 打印时自带一个 **`● ` 圆点前缀，占 2 列**（display_manager 的
`text.append(f"{theme.DOT} ")`）。而 21.12 / 21.11 的预算里都没有这 2 列——
行宽恰好越界 2 列，rich 在"用法列和摘要之间的空格"处断行，
**整段摘要被挤到第二行顶格**。这也回头解释了 21.11 "有的行突然折行"的现象：
差的就是这 2 列，ASCII 多的行没越界、汉字多的越界了，所以像随机发生。

修法（两处预算统一补上）：

```text
/help  预算 = console.width - 圆点(2) - 前缀(2) - 用法列宽 - 间隔(2) - 边距(4)
/skills 预算 = console.width - 圆点(2) - 前缀(2) - 斜杠(1) - 名字列 - 间隔(2) - 标签(6) - 空格(1) - 边距(4)
```

4 列边距给全角引号这类"显示宽度难精确预测"的字符兜底。
预算口径必须用 **rich 的 console.width**——实际做折行的是它，
预算和折行用同一个宽度口径，才不会永远差两列。

顺带把 /help 尾部那句"技能命令（.thinker/skills 里那些）例外…"缩短——
说明文字超宽同样会折行、顶格、和列表混在一起，观感上就是"乱了"。

验证：/help 39 行、/skills 31 行，**0 条超宽行**（按"圆点 + 正文"合计列数逐行检查）。
