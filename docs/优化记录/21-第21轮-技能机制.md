## 一、一句话方案

技能就是一个**带 frontmatter 的 markdown 文件**，价值全在"什么时候加载"：

| 层 | 什么进上下文 | 什么时候 | 量级 |
|---|---|---|---|
| 1 | 只有 `name + description`（在 `skill` 工具的说明书里） | 常驻，每轮都发 | 几百 token |
| 2 | 正文（`skill` 工具的结果 / `/技能名` 的用户消息） | 模型判断"对得上"时 | 两三千字 |
| 3 | 正文里提到的 `reference.md`、脚本 | 模型自己 `file_read` / `cmd_runner` | 按需 |

这三层就是 Claude Code 说的 **progressive disclosure**。整套东西没加新依赖、没改主循环，
落在现有的 `BaseTool` + `REGISTRY` 两张登记表上。

## 二、改前 vs 改后

**改前**：想让模型"按某个固定流程干活"，只有一条路——把流程写进 `THINKER.md`。

```text
THINKER.md（全文注入系统提示词）
  ├── 项目约定
  ├── PDF 处理流程      ← 这三个都每轮付费
  ├── 发版流程
  └── review 清单
```

问题不是"写不下"，是**每一轮都在为用不上的东西付钱**：一次对话里 review 清单可能一次都不触发，
但它的 token 每轮都发；写详细了更糟——越详细越贵，于是人开始主动压缩手册，
最后写出来的东西既不够细、又还在付费。

**改后**：

```text
.thinker/skills/pdf/SKILL.md        常驻：只有 "pdf：读取、解析、抽取 PDF（参数：[文件路径]）"
.thinker/skills/release/SKILL.md    常驻：只有一行描述
.thinker/skills/review/SKILL.md     常驻：只有一行描述
        │
        └─ 用户提到"把这个 pdf 的表格抽出来"
             │
             ├─ 模型：调 skill(skill="pdf", args="D:/a.pdf")
             ├─ 工具：现读 SKILL.md → 变量替换 → 截断 → 作为工具结果进历史
             └─ 模型：按正文步骤干活（正文里让它读 reference.md，它就自己读）
```

**一句话**：`THINKER.md` 管"永远要遵守的规矩"，技能管"这类活该怎么做"。
前者每轮都读，后者用完就留在历史里，不会再出现在下一轮的前缀中（它是增长方向上的消息，不是前缀）。

## 三、目录、发现与校验

### 3.1 两个目录，项目赢

```text
~/.thinker/skills/<名字>/SKILL.md            全局（跟人走，跨项目）
<启动时的 cwd>/.thinker/skills/<名字>/SKILL.md  项目（进仓库，跟项目走）
```

同名时 **项目 > 全局**，和 Claude Code 的"企业 > 个人 > 项目"正好相反。两个理由都不是口味问题：

1. **和 `THINKER.md` 的层叠方向一致**。那里是"全局先加载、项目后加载，越靠内层越优先"。
   两套配置给出相反的优先级，用户迟早会遇到"记忆按项目走、技能按全局走"的怪事。
2. **用户的直觉就是"我在这个项目里改的技能应该赢"**。Claude Code 那条规则是给组织管控用的
   （企业要能压住个人），本项目没有企业层，剩下的只有直觉。

实现上利用"后写覆盖先写"：按 `[全局, 项目]` 顺序扫，后面覆盖前面，和 `memory.load()` 一个套路。
被覆盖的那份记进 `shadowed`，`/skills` 里能看到"同名，被项目版本覆盖"——不静默。

### 3.2 三种刻意的限制

| 限制 | 为什么 |
|---|---|
| **只扫一层，不递归** | Claude Code 支持 `apps/web/.claude/skills` 变成 `/apps/web:deploy`，那是 monorepo 需求。本项目的命名空间会带来前缀、冲突、展示三个概念，而维护的人只有一个 |
| **扫描时只读前 4096 字符** | frontmatter 就在开头。几十个技能也不必在启动时全文进内存；顺带好处：**改正文不用 reload** |
| **`iterdir` 必须 `sorted`** | 不排序的话顺序取决于文件系统，`/skills` 和工具说明书每台机器都不一样，排查时对不上 |

### 3.3 同时支持单文件

`<名字>.md` 和 `<名字>/SKILL.md` 都认。

技能和"子 agent 定义"最大的区别，是技能天生需要目录（核心价值 = 正文 + 一堆按需加载的支撑文件）。
但如果真只有正文，逼用户建一个只装一个文件的目录纯属添麻烦。

> ⚠️ 别把这里的目录扫描和第 18 轮删掉的 `.thinker/agents` 混为一谈。
> 那次删的是"子 agent 从 md 定义"，理由是四个内置类型够用、不需要每人维护一份；
> 技能是**给用户自己写手册**的地方，没有目录就没有这个功能。长得像，目的不同。

### 3.4 校验：会拒的、会警告的

| 情况 | 处理 | 为什么 |
|---|---|---|
| 名字含空格 / 大写 / 下划线 / 超 64 字符 | **拒载** + 警告 | 名字同时是斜杠命令名：`/My Skill` 在 `parse()` 里会被切成"命令 My + 参数 Skill"，敲不出来 |
| 名字与内置命令重名（如 `cost`） | **拒载** + 警告 | 内置优先。静默替换会让用户以为 `/cost` 坏了 |
| 文件不以 `---` 开头 | 整份当正文，`name` 取文件名 | 对齐 Claude Code：没 frontmatter 的技能照样能用 |
| frontmatter 解析失败 | 字段尽量保留 + 警告，技能仍加载 | 崩掉整个启动不值得；但**必须**留警告，不能重犯"静默降级"的错 |
| 有 `---` 开头没闭合 | 整份当正文 + 专门的警告 | 不猜"哪儿该算正文"，也不能让用户以为字段生效了 |
| 没有 `description` | 仍加载、**仍进**工具说明书，描述位置显示「（未写描述，调用后见正文）」+ `/skills` 提示补一句 | 第 21.1 轮改成「技能一律可见」：藏起来会变成「我明明写了技能，模型却说不知道」 |
| 正文超 20000 字符 | 截断 + 注明总长度 | 必须低于 `MAX_TOOL_OUTPUT_CHARS`(30000)，否则业务上限是假的 |
| `allowed-tools` / `model` / `disable-model-invocation` 等本版不用的字段 | 加载、**直接忽略**（第 21.2 轮取消了"未生效"标注） | 多写几行不该让"拷一份别人的技能"变成需要排错的事；标注本身也要四处维护 |

`description` 进工具说明书时截到 **300 字符**（Claude Code 是 1536）：
工具说明书的 description **每轮都发**，10 个技能 × 1536 ≈ 每轮白烧 4000 字符；
而模型判断"要不要用"看第一句就够，和子 agent 的 `MAX_DESCRIPTION_CHARS = 160` 是同一个取舍。

## 四、SKILL.md 的格式与假 YAML

```markdown
---
name: pdf
description: 读取、解析、抽取 PDF 的正文与表格。用户提到 pdf/论文/扫描件/发票时使用。
disable-model-invocation: false
argument-hint: [文件路径]
---

# PDF 处理

用户要处理的文件：$ARGUMENTS

## 步骤

1. 先用 `file_read` 看一眼文件头，确认不是加密或纯图片扫描件。
2. 需要按页抽取时，运行 `${SKILL_DIR}/scripts/extract.py <路径>`。
3. 抽取出的页数、字符数、是否有表格，在汇报里写清楚。

## 更多资料

- 完整参数说明见 `reference.md`（模型按需 `file_read`）
```

### 4.1 字段

| 字段 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `name` | str | 目录名/文件名 | 技能名，同时是斜杠命令名 |
| `description` | str | 空 | 进工具说明书，模型靠它决定用不用 |
| `user-invocable` | bool | true | false = 不出现在斜杠命令里（模型仍可调用） |
| `argument-hint` | str | 空 | 只影响 `/help` 的用法显示，如 `[文件路径]` |
| 其他任何字段（`allowed-tools` / `model` / `hooks` / `disable-model-invocation` …） | — | — | **不读取、直接忽略**，不报错也不在 `/skills` 展示 |

布尔值接受 `true/false/yes/no/on/off/1/0`，大小写不敏感。

### 4.2 为什么敢自己写解析器

`THINKER.md` 明令不加依赖，`pyyaml` 也不是标准库。而技能头部只用到三种写法：

```yaml
key: 单值
key: [a, b]
key:
  - a
  - b
```

明确不支持：多行字符串（`|` / `>`）、嵌套 map、锚点、行尾注释、引号里的 `: `。
遇到不认识的写法就**跳过那一行并留一条 problem**，不是静默丢——能解析多少算多少，
因为"某一行坏了"不该把同一份文件里写对的 `name` 一起丢掉。

`---` 必须是**文件第一行**（允许 UTF-8 BOM）。很多人在顶部先写一句 `# 标题` 再写 frontmatter，
然后困惑为什么字段不生效——这里不猜，整份当正文，并由 `build_spec` 给一条警告。

### 4.3 变量只有三个

| 变量 | 替换成 |
|---|---|
| `$ARGUMENTS` | 调用时传的整串参数 |
| `${SKILL_DIR}` | `SKILL.md` 所在目录（正斜杠） |
| `${PROJECT_DIR}` | 启动时的 cwd（正斜杠） |

两条必须遵守的规则：

- 正文里**没有** `$ARGUMENTS` 而用户传了参数 → 在末尾追加 `ARGUMENTS: <值>`。
  不追加的话参数会凭空消失，用户以为 `/pdf a.pdf` 没生效。
- **先展开路径变量、再替换 `$ARGUMENTS`**。顺序反了的话，用户参数里碰巧出现的
  `${SKILL_DIR}` 会被二次展开——这种"我的参数被吃了"极难查。

不做 `$0` / `$1` / 命名参数：要做就得处理"引号怎么切、`$1.00` 要不要替换、占位符缺失时保留还是清空"，
收益远小于成本。

## 五、两条调用链，一个出口

```text
模型自动调用                          用户手动调用
skill(skill="pdf", args="a.pdf")     /pdf a.pdf
        │                                   │
        ▼                                   ▼
  tools/skill_tool.py               commands._make_skill_handler
        │                                   │
        └──────────► SkillManager.load_body(spec, args) ◄────────┘
                             │  现读 SKILL.md（改字立即生效）
                             │  $ARGUMENTS / ${SKILL_DIR} / ${PROJECT_DIR}
                             │  20000 字符截断
                             ▼
                  作为 tool 消息 / 作为 user 消息写进历史
```

渲染逻辑只有一份（`skill_spec.render`），所以 `/pdf` 和 `skill("pdf")` 拿到的正文、
变量替换、截断行为完全一致——这正是第 14 轮斜杠命令反复强调的"两处各写一遍，下次改动只会补在一处"。

### 5.1 斜杠调用为什么要走"用户消息"，而不是"先让模型调一次工具"

1. 用户是**主动点名**的，语义上就是"我说了这段要求"，不是"模型自己查到的资料"；
2. 少一轮往返。走工具的话：请求 1（模型决定调 skill）→ 请求 2（模型看正文干活），白花一次输入；
3. 对齐 Claude Code：斜杠调用把正文渲染进消息，模型自动调用才走 Skill 工具。

落地方式是 `Conversation` 的一个"待发消息"槽位：

```python
# 命令 handler
conversation.set_pending_input(f"[技能已加载：{name}]\n{body}")

# 主循环 _read_user_input（handle_command 之后、add_message 之前）
pending = self.take_pending_input()
if pending:
    return pending        # 当成用户这一句，正常进历史
```

这两行的位置很关键：

- **在 `handle_command` 之后**：普通命令永远不写 pending，所以"斜杠命令不进历史、不计费"
  （第 14 轮）的规矩一字不变；
- **在 `add_message` 之前**：返回的这段文字会走正常流程被记进历史、发给模型——这正是技能想要的。

`take_pending_input()` 是"取出即清空"，避免同一段正文被发两次、白付两次输入。

### 5.2 工具只在真的有技能时登记

`ToolManager.refresh_skill_tool()` 按 `SkillManager().count()` 决定登记/摘掉。

- 好处：零技能的用户每轮少发约 400 token 的说明书，模型也不会去调一个空工具；
- 代价：`/skills reload` 后新出现的技能要补登记，`tools` 清单变一次、前缀缓存失效一次。

这个代价是一次性的，已经写进方法注释——否则以后会有人把"reload 之后突然贵了一下"当 bug 查。

### 5.3 子 agent 两道闸都不给

`_get_available_tools` 的 `exclude` 从 `{"task"}` 变成 `{"task", "skill"}`，
`_is_tool_allowed` 里和 `task` 一样直接拒。两个理由：

1. 子 agent 的提示词是**刻意精简**的（`agent_spec.build_system_prompt` 只给三行环境）。
   技能正文动辄两三千字，可能比它的任务本身还长，而它只需要"找东西/看代码"；
2. 技能正文是写给**主 agent** 的，里面很可能写着"用 `todo_write` 记一下进度""拿不准就派个子 agent"。
   子 agent 拿到这些指令会去撞 `todo_write`——而那个工具的状态存在单例实例上，
   一撞就覆盖主 agent 的待办清单（第 18 轮记过的坑）。

## 六、安全：技能不能改权限

这是整套设计里最重要的一条：**技能只是一段文字**。

- 正文里写"直接 `rm -rf` 不用问"，模型照样会弹确认——`classify()` 只看工具名和参数，
  不看"这段话是不是来自技能"；
- 技能里的脚本被调用时也只是普通 `cmd_runner` 调用，该问就问。

所以检出一个别人写的技能，风险**不超过**检出一个 `THINKER.md`——两者都是"仓库里的文字被相信"。

### 为什么不做 `allowed-tools`

Claude Code 的 `allowed-tools` 语义是"调用这一轮**免审批**"，它自己也反复警告：
项目里的技能能拿到预授权，`-p` 模式下即使从没信任过这个目录也生效。

本项目的 `permissions.py` 现在守着一条底线：**模型不能给自己发通行证**。
加 `allowed-tools` 等于开了第一个"内容能让权限变松"的口子，而这个口子的输入恰好是仓库里的文本。

要免审批，正确的位置是 `classify()` 里的"用户记忆的允许清单"（ROADMAP 里"本次会话总是允许"那一项），
而不是让 markdown 决定。这一条也写进了 `THINKER.md`，否则下一轮一定有人想"顺手支持一下"。

## 七、成本

| 项 | 估算 |
|---|---|
| 工具说明书（框架话术） | ~200 token |
| 每个技能一行 | 名字 + 300 字符描述 ≈ 120 token |
| 10 个技能 | ~1400 token / 轮 |

`available_block()` 因此有两道闸：描述截 300、
最多 50 条且整块不超过 6000 字符，超了注明"还有 N 个未列出，用 `/skills` 查看"。

**清单要短，但不靠"藏技能"变短。** 超长时给的是"还有 N 个，用 `/skills` 查看"——
信息没丢，只是不占每轮预算。第 21.1 轮把"可见性"整个维度删掉之后，这句话才真正成立。

### `is_repeatable = False`

L3 Microcompact 会把"可重复查询工具"的旧结果折叠成"重跑即可"。技能正文**不能**被这样折叠：

- 它的语义是"跨轮生效的指令"，不是"查回来的数据"；
- 折叠之后模型不知道自己少了什么，会继续按半截规矩干活，而且没有任何报错；
- 真要收缩，应该发生在 L5 摘要（那里会真的重写对话），而不是 L3 的静默折叠。

父类默认就是 `False`，`skill_tool.py` 里仍然显式写了一遍，并在测试里钉住
（`Skill.is_repeatable is False`）——防止有人顺手改。

## 八、热更新的口径要分两半

| 改了什么 | 什么时候生效 |
|---|---|
| `SKILL.md` **正文** | **立即**。正文每次调用都现读 |
| **frontmatter**（名字、描述、布尔） | 要 `/skills reload`。它们进了工具说明书和 REGISTRY，是注册期快照 |

这个区分不是省事，是省不掉：元数据必须常驻才能让模型"知道有这个技能"，常驻就意味着有快照。
写清楚比假装支持全套 watcher 更诚实——Claude Code 那套 watcher 有 6 条边界
（bare mode、`--add-dir`、启动时不存在的目录……），本项目一条都不需要。

## 十一、这一轮踩到的三个坑

### 1. `argument-hint: [文件路径]` 被假 YAML 当成列表

假解析器看到 `[...]` 就当内联列表，于是拿到 `["文件路径"]`，`str()` 出来是
`/pdf ['文件路径']`——`/help` 里像程序坏了。

没有改解析器开特例（"哪些键永远不是列表"以后每加字段都要记得加一条），
而是在取字段处加 `_hint_text()` 还原方括号写法。**教训**：解析器和字段语义之间
永远有一层"这个键允许什么形态"，别指望通用解析器替业务字段做判断。

### 2. "写完了却扫不到"——扫描结果是有缓存的

`SkillManager` 第一次查询才扫（`_ensure_scanned`），之后结果就是快照。
测试里"建完文件立刻断言"全部失败，因为那一次查到的是空目录。
这不是 bug，是真实口径（改完要么重启、要么 `/skills reload`），
测试里补 `rescan()` 等于替用户按一次 reload。**教训**：写测试时先问"这个系统里，
'写完'到'看得见'之间隔着哪一步"，不然会把正确行为写成 bug。

### 3. 上一轮登记过的技能命令，会被当成"内置命令"自己撞自己

同名冲突检查要排除内置命令，但 `REGISTRY` 里同时有**内置命令**和**上一轮登记的技能命令**。
不排除后者的话，reload 之后一个技能会因为跟它自己的旧命令重名而被拒载——
表现为"第一次能用，reload 一次就消失了"。

解法是 `commands._skill_command_names` 记账 + `builtin_command_names()` 求差集。
**教训**：往一张共享注册表里写"用户数据"（技能）时，必须能把自己写的那部分认出来。

## 十二、明确不做的事

| 不做 | 理由 |
|---|---|
| `allowed-tools` / `disallowed-tools` | 见 §六。权限放松必须走 `classify()`，不能由仓库里的文本决定 |

## 十四、第 21.1 轮补丁：砍掉「模型可见性」这一维

方案原稿里技能有两个开关：`disable-model-invocation`（模型看不看得见）和
`user-invocable`（人能不能 `/名字`）。第一版照做，用着发现**这个维度不值它的复杂度**：

- 它让"同一个技能"在不同条件下有两种状态（在清单里 / 不在清单里）。模型一报"不知道有这技能"，
  就得先排除两种可能：描述没写？被 disable 了？排查方向凭空多一条；
- 收益只有几十个字符的 token；
- 而"技能文件明明在那、模型却不知道"恰恰是最容易让人怀疑功能坏了的现象。

所以整条规则删掉：**所有加载到的技能一律对模型可见**。

| 位置 | 改动 |
|---|---|
| `SkillSpec` | 删掉 `disable_model_invocation` 字段和 `visible_to_model()` 方法 |
| `available_block()` | 不再过滤，遍历全部；没描述的行显示「（未写描述，调用后见正文）」 |
| `Skill.act()` | 删掉"只能由用户手动调用"的拒绝分支 |
| `SkillSpec` | `disable-model-invocation` 不再读取（连同所有非本版字段一起忽略，见 21.2） |
| `cmd_skills` | 去掉"仅手动调用"标记；"没有描述"的提示改成"清单里只显示占位" |

**为什么字段还认**：从 Claude Code 拷来的技能里它很常见。直接忽略的话，用户会以为
"我标了只给手动用、怎么模型还是调了"；字段保留解析但不生效（21.2 连标注也一起删了）。

**没变的**：`user-invocable` 仍然是真开关（它管斜杠命令表，不涉及模型认知）；
清单长度仍由 `MAX_SKILLS_IN_BLOCK` / `MAX_SKILLS_BLOCK_CHARS` 卡。
"让模型知道全部技能"和"别把说明书撑爆"不矛盾——超长时给的是"还有 N 个，用 /skills 查看"。

验证：`test_skills.py` 从 56 条断言增加到 59 条，两处旧用例改成新口径
（缺描述仍可见可调用、`disable` 字段仍可见可调用），全绿。

## 十五、第 21.2 轮补丁：连"未生效字段"也删了

21.1 把 `disable-model-invocation` 从"生效字段"降级成"未生效字段"，但它仍然要走一条完整的流水线：
在 `UNSUPPORTED_FIELDS` 登记 → `build_spec` 逐个比对 → 存进 `SkillSpec.unsupported` →
`/skills` 拼成一句标记 → 测试断言它被标出来。

这四步**不改变任何行为**，只是多一行解释文案。而它带来两个长期成本：

1. 每加一个"本版不做"的字段，就要记得到那张表里补一条；
2. `SkillSpec` 为一个纯展示字段多背一个属性，`/skills` 多一段拼接逻辑。

所以整张表删掉：`SkillSpec` 不再有 `unsupported`，`/skills` 不再标"未生效"。

```text
改前：allowed-tools → 登记 → 比对 → 存字段 → 展示"未生效"
改后：allowed-tools → 解析进 fields → 没人读它 → 丢掉
```

**现在的规则一句话**：认得字段（`name` / `description` / `user-invocable` / `argument-hint`）就读进
`SkillSpec`，其余一律忽略——不报错、不警告、不展示。

**代价说清楚**：从 Claude Code 拷技能过来的用户，写了 `allowed-tools` 却发现没有免审批，
只能从文档（本文 §六、THINKER.md）里知道原因，界面上不再提示。这是有意的取舍：
把解释放进文档，把代码里的概念数量降到最低。

验证：`test_skills.py` 59 条断言仍全绿（原来的"未生效字段被标出来"改成了
"多余字段不产生任何警告"）。
