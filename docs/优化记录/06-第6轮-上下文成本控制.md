## 一、L6：工具输出在写进历史前就截断

### 1.1 原来的问题

第 2 轮只在**界面层**截断了工具输出（`DisplayManager.shorten` / `preview_lines`）。那只影响"你看到什么"，**模型收到的仍然是全文**。

直观后果：

- 跑一次 `dir /s` 或 `npm install`，输出几万字，一次性吃掉上下文的一大半
- 上下文被这些一次性日志占满，很快就会触发压缩，压缩又要花一次模型调用
- 钱和上下文，两边都在漏

### 1.2 改法

在**唯一**把工具结果写进历史的地方下手：`Conversation._add_tool_response()`。

```python
# 改前
tool_content = [{"type": "text", "text": content}]

# 改后
tool_content = [{"type": "text", "text": self._truncate_tool_output(content)}]
```

新增 `_truncate_tool_output()`，策略是**掐头去尾**：

| 保留 | 比例 | 理由 |
|---|---|---|
| 开头 | 70% | 通常包含"在干什么、有没有报错" |
| 结尾 | 30% | 通常包含最终结果 |
| 中间 | 丢掉 | 大段重复日志恰恰最没用 |

上限由 `MAX_TOOL_OUTPUT_CHARS` 控制，默认 12000 字符，可用环境变量覆盖。

### 1.3 一个容易被忽略的细节：告诉模型怎么取全文

如果只是截断，模型会以为"输出就这么长"，然后基于残缺信息下结论。所以省略处插入了一句提示：

```
... [工具输出过长，中间省略了 38008 个字符。如需完整内容，请分段读取：
例如 `sed -n '开始行,结束行 p' 文件`，或用 `grep` 只取你需要的部分。] ...
```

这句话让模型有机会自己去补——这比"悄悄截断"安全得多。

### 1.4 现在的三层防线

| 层 | 位置 | 上限 | 目的 |
|---|---|---|---|
| 命令层 | `cmd_runner._truncate` | 30000 字符 | 防止一条命令把内存和界面撑爆 |
| 历史层 | `Conversation._truncate_tool_output` | 12000 字符 | **防止模型上下文被吃掉**（本轮新增） |
| 显示层 | `DisplayManager.preview_lines` | 3 行 × 70 字 | 防止刷屏 |

### 1.5 验证

| 用例 | 结果 |
|---|---|
| 短输出原样保留 | 通过 |
| 50008 字符 → 12096 字符 | 通过 |
| 开头 `HEAD` 与结尾 `TAIL` 都保留 | 通过 |
| 说明里含省略字符数 | 通过 |
| 说明里含 `sed -n` / `grep` 提示 | 通过 |
| 非字符串输入不报错 | 通过 |
| **集成**：`_add_tool_response` 写进历史后长度 12096，提醒块仍保留 | 通过 |

## 二、摘要改用小模型（`OPENAI_SUMMARY_MODEL`）

### 2.1 为什么

第 2 轮做的摘要式压缩，调用的是**主模型**。但"把一段对话总结成 400 字"这件事，不需要和写代码同级别的模型——用便宜的小模型完全够，成本可能只有十分之一。

### 2.2 改法

**`api_client.py`**：

```python
self.summary_model = os.getenv("OPENAI_SUMMARY_MODEL") or self.model
# 没配就退回主模型，行为和以前完全一样
```

`get_completion()` 新增可选参数：

```python
def get_completion(self, request_params, model: Optional[str] = None):
    request_params["model"] = model or self.model
```

**`conversation.py`** 的摘要调用传入小模型：

```python
message, token_usage = await loop.run_in_executor(
    None, self._api_client.get_completion, request, self._api_client.summary_model
)
```

注意 `run_in_executor` 支持额外位置参数，所以不用 `functools.partial`。

### 2.3 配置

```ini
# 留空则沿用 OPENAI_MODEL
OPENAI_SUMMARY_MODEL=
```

建议填一个便宜的小模型（比如 `gpt-4o-mini`、`claude-3-5-haiku` 之类，看你的服务商提供什么）。

### 2.4 验证

| 用例 | 结果 |
|---|---|
| 配了 `OPENAI_SUMMARY_MODEL` 时能读到 | 通过（读到 `cheap-summary-model`） |
| 主模型不受影响 | 通过 |
| 未配置时回退主模型 | 通过（另起进程验证，避开单例） |
| `get_completion(model=...)` 真的把模型名传给了接口 | 通过（拦截入参确认） |

## 三、缓存打点修正

### 3.1 原来的两个问题

```python
# 改前：只给最后一条消息打一个点，而且不分接口
messages[-1]["content"][-1]["cache_control"] = {"type": "ephemeral"}
```

**问题一：不分接口，可能直接把请求发挂。**
`cache_control` 是 Anthropic 的私有字段。如果 `OPENAI_BASE_URL` 指向 OpenAI 官方接口，这个字段会让请求返回 400（`Unrecognized request argument`）——不是"没效果"，是直接不能用。

**问题二：只打一个点，浪费了命中率最高的部分。**
系统提示词每轮都一模一样，是最该被缓存的一段。只标最后一条消息，等于每次都在缓存一个"刚刚变化过"的尾部。

### 3.2 改法

**先判断要不要打标记**（`_detect_prompt_cache`）：

```
1. 环境变量 ENABLE_PROMPT_CACHE 写了 1/0 → 听它的
2. 接口地址含 anthropic → 开
3. 模型名含 claude → 开
4. 其他 → 关（宁可不缓存，也不要请求报错）
```

**再打两个断点**：

| 断点 | 位置 | 命中特征 |
|---|---|---|
| ① 系统提示词 | 第一条 system 消息的最后一个内容块 | 每轮内容完全相同 → 稳定命中 |
| ② 最后一条消息 | 消息列表末尾 | 对话在变长 → 每轮增量命中 |

最多 4 个（Anthropic 的上限），并且不会重复标记同一条。

**顺带修掉一个隐患**：原来直接写 `messages[-1]["content"][-1]`，如果 `content` 是字符串会抛 `TypeError`。现在统一包成内容块列表再标：

```python
if isinstance(content, str):
    content = [{"type": "text", "text": content}]
    message["content"] = content
```

### 3.3 验证

| 用例 | 结果 |
|---|---|
| 开启时打 2 个断点 | 通过 |
| 第 1 个在系统提示词上 | 通过 |
| 第 2 个在最后一条消息上 | 通过 |
| 中间消息没有被误标 | 通过 |
| 关闭时一个字段都不加 | 通过 |
| 只有系统消息时只打 1 个点（不重复） | 通过 |
| 字符串 content 能被正确包装后标记 | 通过 |
| 标记不污染原始历史（深拷贝隔离） | 通过 |

### 3.4 真机结果：你的服务本来就有自动缓存

跑真实对话时，状态行出现了新字段：

```
⎿ 上下文 3.5% · 花费 $0 · 缓存命中 7040
⎿ 上下文 3.8% · 花费 $0 · 缓存命中 14272
```

这说明当前服务商**自己就做了服务端缓存**，我们不发 `cache_control` 也能命中。所以：

- 对当前配置：缓存打点修正是"安全兜底"，实际收益主要来自服务商自己的机制
- 对 Anthropic 官方接口：两个断点会真实生效

顺便做了个探测：向当前服务发一个带 `cache_control` 的请求，**没有被拒绝**（返回正常）。所以你想强制打开也可以，在 `.env` 里加：

```ini
ENABLE_PROMPT_CACHE=1
```

但我没有替你改成默认开启——如果哪天你换成 OpenAI 官方接口，这行会导致请求报 400。保持自动判断更安全。

### 3.5 新增：缓存命中量可见

`api_client` 里新增 `cached_tokens` 累计值：

- Anthropic 风格：读 `usage.cache_read_input_tokens`
- OpenAI 风格：读 `usage.prompt_tokens_details.cached_tokens`

只有大于 0 时才显示在状态行，避免平时多一段噪音。
