# 第 25 轮：L5 摘要从「压最老一轮」改成「按边界一次压完」

日期：2026-11-11
版本：0.10.1 → 0.10.2

## 怎么发现的

看 `_compress_multiple_sessions` 时觉得它压得太少：它只压
`messages[:user_indices[1]]`，也就是第一条用户消息加上它的全部后续，一次只处理最老的一轮。
95% 的水位下，一轮对话通常只占窗口的 3~8%，压完还在 90% 以上。

于是写了个脚本连续压三次，结果比"压得少"严重得多：

```
第 1 次：41 条 → 压 8 条 → 34 条                       ✓
第 2 次：34 条 → 压 1 条（上次的公告）→ 34 条           ✗ 条数不变、token 不变
第 3 次：34 条 → 压 1 条（上次的公告）→ 34 条           ✗
```

第二次送进摘要器的唯一一条原料，是上次压缩留下的公告本身：

```
Role.USER: [为节省上下文空间，之前的对话已被压缩。以下是被压缩部分的摘要：]
            【摘要1】前面做了第 1 到第 N 件事。
```

**即在"摘要的摘要"，条数不降、token 不降，但每次都真花一次模型调用。**
水位卡在 95% 下不来，最后照样撞 400。

原因：公告的 role 是 `USER`，`_get_user_message_indices()` 会把它算成一条用户消息，
于是下次的"第二老用户消息"前面只剩这条公告，压它等于什么也没压。

## 改成什么

对齐 Claude Code 的 full compaction：**保留 system + 最近 N 条，边界之前整段一次压完。**

新增 `_compress_by_boundary(messages, keep_recent=None)`，四步定边界：

| 步骤 | 做什么 | 挡的是哪类事故 |
|---|---|---|
| 1 | `cut = total - keep_recent` | 用条数不用轮数：一轮可能 2 条，也可能 80 条 |
| 2 | `align_top_cut(messages, cut)` | 刀口落在 tool 结果上会拆散申请与结果 → 400 |
| 3 | `cut = min(cut, 最后一个用户消息下标)` | 用户最新指令进了压缩区，模型会忘了当前要做什么 |
| 4 | `cut > 第一条非 system 消息` | 否则没有实质内容可压（单轮场景） |

三处行为变化：

1. **防套娃**：待压内容里如果只剩"上次的公告"，直接返回 `only_previous_summary`，
   **不调模型**。判断靠 `_is_compression_notice()` 的文本前缀，不加自定义字段
   （未知字段有被上游接口拒掉的风险）。
2. **失败就不压**：原实现在摘要失败时插一条无摘要公告，等于把一大段历史静默删掉。
   以前只删一轮损失有限，现在一次删几十条，所以改成一条都不动，并把原因返回给调用方。
3. **账本重算**：压完立即把 `history_token_usage[-1]` 重算成压缩后的估值。
   不重算的话状态行和 `/cost` 还显示压缩前的占用，用户会以为没压。

`_compress_multiple_sessions` 和 `_compress_single_session` 两个方法已删除。
后者本来处理"只有一轮、后面全是工具调用"的场景，但那个场景正确的手段是 L3 折叠工具结果，
不是摘要——把唯一的用户指令压掉等于把任务弄丢。现在这种情况返回 `nothing_to_compress`。

## 效果

15 轮对话（151 条，每轮 4 次工具调用），窗口设成让水位正好 95%：

```
压前：151 条 / 19,771 token / 20,811 窗口 → 95.0%
压后： 12 条 /  1,397 token / 20,811 窗口 →  6.7%
释放：18,374 token（93%）
第二次：compressed=False，reason=only_previous_summary
```

压得比 Claude Code 的 95%→40% 更狠，是因为测试数据里每条消息都很小（约 140 token），
保留 10 条只占 1400 token。真实会话里最近 10 条常含大段工具输出，保留区会大得多。

## 测试

新增 `test/test_compress_boundary.py`（10 组、31 条断言，全部用假摘要器，不调模型）：

- 第二次压缩必须 `compressed=False` 且**摘要器只被调用 1 次**（钉住套娃 bug）
- 压完 `tool_call` 配对零断裂
- 摘要失败时历史逐字节不变
- 用户最新指令一定还在
- 只有一轮对话时不压
- 账本等于压缩后的估算值
- `keep_recent` 调小 → 保留更少
- 两种公告前缀都能识别、普通消息不误判
- 公告后面又攒了新内容 → 允许再压，并把旧摘要一起重压

```
🎉 所有测试通过（31/31）
```

## 一处仍在的风险

保留区是"最近 N 条"而不是"最近 N 轮"。如果最后 10 条恰好全是工具结果、
不含任何 assistant 的结论，压完之后模型可能不知道"刚才做到哪一步了"。
这依赖摘要 prompt 里对"当前进展"的覆盖程度，属于下一步该检查的地方
（`Conversation._summarize_messages` 的提示词）。
