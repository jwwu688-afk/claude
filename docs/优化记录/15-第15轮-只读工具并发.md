## 一、动手前先验证了一件事：原来的"异步"是假的

`file_tools.py` 里三个只读工具都是 `async def act(...)`，但**整个文件里一个 `await` 都没有**——函数体全是 `read_text`、`iterdir`、`re.finditer` 这类同步调用。

这意味着：直接把循环改成 `asyncio.gather`，结果会**完全正确、但一点没变快**。协程之间没有让出点，gather 只是把它们挨个跑完。这种"没生效的优化"最难发现——测试全绿、代码也"改了"，唯一不对的是耗时。

所以这一轮实际有两步：

1. 把阻塞段丢进线程池（`asyncio.to_thread`），让多个读真的重叠；
2. 才谈并发调度。

```python
async def act(self, path="", offset=0, limit=MAX_READ_LINES, need_user_approve=False):
    return await asyncio.to_thread(self._act, path, offset, limit)
```

原函数体整体挪进 `_act`（同步），签名不动——`BaseTool` 的契约、工具清单、调用方全都不用改。

> 为什么 `to_thread` 有用：磁盘 IO 期间 GIL 会释放，多个 Python 线程可以同时等各自的读写完成。

## 二、只并"连续的"只读调用

```python
batch, next_index = self._collect_parallel_batch(tool_calls, parsed_args, index)
if len(batch) >= 2:
    await self._execute_tools_parallel(batch, ...)
    index = next_index
    continue
# 否则走单条路径（含审批）
```

### 为什么不把整轮里所有只读的都挑出来一起跑

模型给出的顺序就是它自己排的执行意图：

```
file_read(a.py) → file_edit(a.py) → file_read(b.py)
```

把第三个提前到第一个旁边并发，读到的就是**改动前**的内容——结果看起来完全正常，但那是错的。只并"相邻的一串只读"，是最小惊讶原则。

### 哪些能并：三个条件

| 条件 | 原因 |
|---|---|
| 在 `READ_ONLY_TOOLS` 里 | 只有只读才没有先后依赖 |
| 不需要审批 | 要停下来问人，并行没意义（人只有一个） |
| 不是高危 | 高危必须单独走，否则"回车默认拒绝"的提示会和别的命令挤在一起，用户分不清对应哪条 |

判据直接复用 `core/permissions.py` 的集合，不在这里另写一套判断。

## 三、两个必须守住的顺序

### 3.1 界面：先画完所有头，再统一画结果

边跑边画的话，屏幕上会变成「第二个头 → 第一个结果」的交叉顺序，用户根本对不上哪条结果属于哪次调用。所以先 for 一遍画 `⏺ file_read(a.py)`，再并发，最后按顺序画 `⎿`。

### 3.2 历史：按申请顺序写回，不按完成顺序

并发完成顺序不确定，而历史会被落盘、被下一轮请求读到。真按完成顺序写，同一个会话每次重放的消息顺序都不一样——排查时没法对照，缓存前缀也会随机失效。

（tool 消息之间本来靠 `tool_call_id` 对应，顺序不影响接口合法性；但"稳定"比"合法"更值钱。）

测试里专门造了"第一个慢、第二个快"的场景：完成顺序确实是反的，历史顺序仍是申请顺序。

## 四、失败隔离

第 14.2 轮起 `run_tool` 会真的抛异常。如果直接 `gather`，一条失败会把整批打断——**一个文件读不到，其余四个也不读了**，比串行还糟。

所以让每个任务自己兜住异常：

```python
async def run_one(call, args):
    try:
        return await self._tool_manager.run_tool(...)
    except Exception as e:
        return e   # 返回值是 Exception 就代表这条失败
```

这样语义干净：返回值正常 = 成功，是 `Exception` = 失败，交给统一的 `_finish_tool_call` 收尾（标红 + 写"工具调用失败，原因：…"）。

顺带把串行路径的收尾也并进 `_finish_tool_call`：两条路径共用一份"怎么记录结果"的逻辑，以后改失败提示的措辞不用改两处。

## 五、测试暴露的一个老问题

改完之后 `test_conversation_loop.py` **卡死**。

原因不是新代码有 bug，而是那个用例一直在"侥幸通过"：它构造了**真的** `ToolManager()`，而 `ToolManager.__new__` 会 new 一个 `MCPClient`，后者在 `__init__` 里就 `create_task(_run)` 去连 MCP 服务器。

改前 `file_read` 全程同步、一个 await 都不让出，那个后台任务**还没被调度**，场景就跑完了；`asyncio.run` 收尾时取消一个"从未开始"的任务是瞬间完成的。改成 `to_thread` 之后，任务真的跑起来了，停在 `_ready.wait()` 上等 MCP 连接，收尾时就一直等。

修法是把 MCP 掐掉（两处都要）：

```python
ToolManager._ensure_mcp_registration = lambda self: None
MCPClient._ensure_started = lambda self: None
```

这个用例要验的是"授权分流"，本来就不该起子进程。生产路径不受影响——`main.py` 的 `finally: await conversation.shutdown()` 会正常收尾。

## 六、实测

| 场景 | 结果 |
|---|---|
| 两个各睡 0.3s 的只读调用 | 总耗时 **0.31s**（串行应 ≥0.6s） |
| 一慢一快（0.25 / 0.01） | 完成顺序反了，历史顺序没变 |
| 一条抛异常 | 另一条照常返回，失败那条写明原因 |
| `file_read + file_grep + file_write + file_read` | 批次只收前两条，停在写操作 |

## 七、已知边界

1. **没有并发度上限**。模型一次申请 10 个 `file_read` 就会同时开 10 个线程。默认线程池（`min(32, CPU+4)`）会自动排队，不会爆炸；但要更稳，可以加 `asyncio.Semaphore(4)`。现在先不加——多一个旋钮就多一个要调的参数。
2. **写操作仍然串行**。`file_write` / `file_edit` / `cmd_runner` 之间有真实的先后依赖，并行会把语义搞乱。
3. **跨批不并发**。`read → write → read` 是三段，第一段和第三段不会合并——见第二节的理由。
