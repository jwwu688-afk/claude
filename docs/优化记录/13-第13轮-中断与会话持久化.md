## 一、这两个缺口是成对的

在此之前：

- 模型理解错了，正在写一大段你不要的东西 → **只能 Ctrl+C 杀进程**，上下文全丢
- 电脑崩了、终端被误关 → 半小时的对话归零，重开什么都不记得

第一个是"用户控制不了 agent"，第二个是"工作成果不落地"。只修任何一个，价值都减半——能打断但接不上，等于白打断。

## 二、Esc 中断

### 2.1 为什么用后台线程，而不是在主循环里检查

主循环在 `for chunk in iterator` 里等网络数据，两块数据之间可能隔几百毫秒。在那个循环里查键盘，用户按下 Esc 后要等下一块数据到了才响应，体感是"按了没反应"。

独立线程每 50ms 查一次，按下即置标志，主循环下一块数据到达时立刻看到。

```text
while not self._stop.is_set():
    if self._msvcrt.kbhit():
        if self._msvcrt.getch() == ESC:   # 0x1b
            self._pressed.set()
            return
    self._stop.wait(0.05)
```

三个约束：

| 约束 | 原因 |
|---|---|
| 只管 Esc，其他键丢弃 | `getch()` 会**消费**字符，全读走会让用户别处的输入丢失 |
| 非 tty / 非 Windows 自动降级 | 管道、CI、Linux 下没有 msvcrt，不能让"打断功能"本身导致启动失败 |
| `stop()` 必须 `join` | 否则旧线程活到下一轮，和新线程抢键盘 |

### 2.2 按下之后发生什么

```text
for chunk in iterator:
    if esc.triggered:
        interrupted = True
        break
    ...
```

跳出循环后：

1. `stop_stream_display(show_done=False)` —— **不打 `Cooked for Ns`**，那一轮根本没跑完
2. 已输出的内容存成 assistant 消息，末尾标 `[用户中断]`
3. 主 agent：直接进"等用户输入"，让用户说下一步
4. 子 agent：返回 False，收尾交差

第 2 步的 `[用户中断]` 标记很重要：模型下次读历史时能看出"这是被截断的半截话"，不会误以为那就是完整回答。

第 3 步为什么不 `return True`：外层 `while` 收到 True 会**立刻再请求一次模型**，用户根本没机会改口。所以中断分支里手动走了一遍"等输入 + 加消息"。

## 三、会话持久化

### 3.1 格式：JSONL

第一行 header，之后每行一条消息：

```jsonl
{"type":"header","v":1,"id":"20261107-183024-51ec","started_at":"2026-11-07T18:30:24","cwd":"D:\\code\\thinker","model":"spark-x2.6"}
{"type":"message","ts":1793974368.95,"message":{"role":"user","content":[{"type":"text","text":"你好"}]}}
{"type":"message","ts":1793974370.12,"message":{"role":"assistant","content":[{"type":"text","text":"你好！有什么可以帮你？"}]}}
```

选 JSONL 而不用"一个大 JSON"：

- **追加写**：新消息直接 append 一行，不用把整个文件读出来再写回
- **崩溃安全**：写到一半断电，前面的行还是完整的
- **可读**：出问题能直接 `tail` 看最后几条

格式沿用之前实验留下的 v1（`~/.thinker/sessions/20261106-221248-ee59.jsonl`），老文件可以直接读。

### 3.2 每条消息立即落盘

不是等这一轮结束才写。理由：崩溃往往发生在"正在跑工具"的时刻，等轮次结束再存等于白存。

代价是每条消息开关一次文件。一轮对话几十条，无感。

`ensure_ascii=False`：中文原样存，不要变成 `\u4f60\u597d`，否则排查时一眼全是转义码。

### 3.3 坏行跳过，不整体报废

```text
try:
    obj = json.loads(line)
except json.JSONDecodeError:
    continue   # 半行 / 坏行，跳过
```

会话文件是"尽力保存"的产物，可能因为断电留下半行。为半行坏数据让整个恢复失败，不如丢掉那一行继续——最多丢一条消息，比"完全打不开"好得多。

### 3.4 恢复时替换 system，续写原文件

**替换 system**：系统提示词里带着当前日期、当前目录、项目记忆、工具清单。昨天存的那份今天已经不准了，照搬等于给模型灌过期信息。所以恢复时丢掉旧 system，用新生成的顶上去，user / assistant / tool 原样保留。

**续写原文件**：`--continue` 后直接 `SessionStore(resume_path)` 往原文件追加，不新建。这样一次对话从头到尾在同一个 JSONL 里，翻起来连续，也不会重复存旧消息。

## 四、用法

```bash
thinker              # 新对话
thinker --continue   # 接着本项目最近一次会话
thinker -c           # 同上
```

`--continue` 只找**当前目录**的会话。跨项目恢复会让模型拿着一堆另一个项目的上下文，反而更糊涂。

## 六、遗留

| 编号 | 问题 | 计划 |
|---|---|---|
| I1 | **插话队列没做**：Esc 之后只能重新打字，不能"边生成边排队下一条"。真正的插话需要在生成期间也能收字符，和现有 `input()` 模型冲突 | 要引入 prompt_toolkit 或自管行编辑，成本较高，单独一轮 |
| I2 | 等回复期间用户提前敲的字会被 `getch()` 吞掉 | 同上，做插话队列时一起解决 |
| I3 | 没有多会话列表选择（`--resume` 弹列表） | 斜杠命令那轮给 `/resume` |
| I4 | 会话文件不会自动清理，会越攒越多 | 加个保留期（比如 30 天）或总大小上限 |
| I5 | 子 agent 的中间过程不落盘 | 有意为之：那是草稿，恢复时只会干扰模型 |
