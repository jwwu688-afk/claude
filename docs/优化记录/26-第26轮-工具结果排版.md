# 第 26 轮：工具结果预览改成「按行列排版」

日期：2026-11-11
版本：0.10.2（未发版）

## 怎么发现的

用户在 Anaconda PowerShell Prompt 里连续读了 3 个文件，截图长这样：

```
● file_read(D:/code/thinker/demo/plane/js/game.js)
● file_read(D:/code/thinker/demo/plane/js/effects.js)
● file_read(D:/code/thinker/demo/plane/js/main.js)
  ⎿  1  /===== 战斗核心：固定逻辑坐标与秒制时间，不依赖 DOM。 ===== e  2  * 【2026-11-10】输入交给 main，画面交给 effects; 测试可直接推进时间。 e  3  * 死亡标记在本帧立即生效，帧末统一回收，避免多发子弹重复计分。 e
    （共 108 行）
```

行号和内容散在屏幕各处，`⎿` 后面那一行被终端折成两三段，第二段从第 0 列重新开始，
看起来就是"字全乱了，读不出哪行属于哪个文件"。

## 根因（三处叠加）

1. **几行结果被拼成了一行。** `preview_lines` 用 `" ⏎ ".join(...)` 把 3 行正文拼成一条，
   拼接后长度立刻超过终端宽度，终端只能硬折行。
2. **截断按「字符」而不是「列」。** 原来的 `line[:70] + "…"`，中文一个字占 2 列，
   70 个字符在屏幕上就是 140 列，宽一点的代码行必然折行。
3. **`\t` 没展开。** `file_read` 的行号是 `f"{n:>6}\t内容"`，终端把 `\t` 跳到下一个 8 列边界；
   行号从 9 变 10 时，内容起点跟着跳一列，肉眼看着"行号在抖"。

外加一处小的：plain 模式收尾时无条件补 `\n`，模型回复本身已以换行结束时，
正文和 `Cooked for Ns` 之间会多出整整一行空白。

## 改成什么

| 位置 | 改法 |
|---|---|
| `preview_lines` | 每行**独立成行**返回（`\n` 连接），不再用 `⏎` 拼；`expandtabs(4)` 固定行号列；按显示列截断；`max_width` 默认取 `控制台宽度 - 7` |
| `tool_result` | 支持多行：第一行跟在 `⎿` 后，续行缩进 5 格对齐（正好是 `"  ⎿  "` 的宽度） |
| `shorten` | `limit` 的单位从字符改成列，同样按 `cell_len` 切（它拼在工具标题行后面，超宽一样会折行） |
| `stop_stream_display` | 只有 `_stream_buffer` 不以 `\n` 结尾时才补换行 |

新增两个小工具：`_take_cells`（取不超过 N 列的前缀，不加省略号）、`_clip_to_cells`
（同上，末尾补 `…`）。截断时永远不会把一个中文/emoji 切成半个字。

改完的效果（同一批 3 个文件，120 列终端）：

```
● file_read(D:/code/thinker/demo/plane/js/game.js)
  ⎿       1  /** ===== 战斗核心：固定逻辑坐标与秒制时间，不依赖 DOM。 ===== */
          2   * 【2026-11-10】输入交给 main，画面交给 effects；测试可直接推进时间。
          3   * 死亡标记在本帧立即生效，帧末统一回收，避免多发子弹重复计分。
     …（共 4 行）
```

`（共 N 行）` 因为独立成行、且不再挤在正文尾巴上，一眼能看出"后面还有内容"。

## 验证

用 `Console(width=…)` 把渲染结果抓成纯文本，逐行量 `cell_len`：

```
--- width=80 ---
  78 |  ⎿       1  中文内容很长中文内容很长…（截断到 73 列）
--- width=140 ---
 138 |  ⎿       1  中文内容很长…（截断到 133 列）

shorten(中文 240 列, limit=60) → 输出 50 列
```

没有一行超过终端宽度，即不会再触发终端硬折行。
`py_compile` 通过；`test/` 下现有测试与本次改动无关（没有 pytest 依赖，未跑）。

## 顺带：上游断流不再刷一屏 traceback

用户在同一份输出里还贴了这段：

```
✗ 处理流式响应时出错：Streaming API request failed: peer closed connection without
  sending complete message body (incomplete chunked read)
· 错误类型：Exception
Traceback (most recent call last):
  ... 二十行 httpx / httpcore 调用栈 ...
· 正在改用非流式模式重试……
● 代码已读完。连击系统设计如下：        ← 重试成功了
```

问题是：**这是能自愈的网络抖动，却按"代码崩了"的规格报出来。**

三处改动：

| 位置 | 改法 |
|---|---|
| `api_client.get_completion_stream` | `raise Exception(...)` → `raise StreamReadError(...) from e`，把原始异常挂到 `__cause__` |
| `conversation._classify_transient` | 沿 `__cause__`/`__context__` 收齐整条链的类名，命中网络关键词就判定"可重试"，返回一行中文原因 |
| `conversation._run_one_iteration` 的 except | 网络类：一行暗灰提示 → 静默重试；其他：保持原来的红叉 + traceback |

改后同一场景只剩两行：

```
· 流式响应被中断（上游断开连接），自动改用非流式重试……
● 代码已读完。连击系统设计如下：
```

两个附带决定：

1. **不额外增加重试次数**。流式失败后走非流式重试是原有逻辑，本轮只改"怎么报"，
   没有新增模型调用（多一次重试就多花一次 token，这是用户明确在意的事）。
2. **`full_content` 提前到 try 之外初始化**。它原来是 try 内部第一行之后才赋值的；
   如果 `get_completion_stream()` 在建立连接时就抛异常，except 里
   `full_content.strip()` 会 `NameError`，把一次可自愈的网络抖动升级成真崩溃。

断在回答中途时会多出一行「上面已输出的半截作废，下面这条是完整回答。」——
非流式重试会把整段重打一遍，不解释一句用户会以为程序抽风。

分类验证（不联网、不调模型）：

```
断流     -> (True, '上游断开连接')    链: StreamReadError → RemoteProtocolError
超时     -> (True, '读取超时')
ValueError -> (False, '')             ← 真 bug 仍打完整现场
```

## 仍在的风险

- `（共 N 行）` 里的 N 是**结果文本的行数**，不是文件总行数。`file_read` 的结果尾部
  还有一句"（文件 … 共 108 行，本次显示第 1-108 行…）"，所以可能显示成"共 109 行"，
  和真正的文件行数差 1。要精确得让 `file_read` 把总行数放进结构化字段，属于协议改动，本轮没做。
- 真机（conhost）上的最终观感仍需用户开一次终端确认：本轮的验证是"宽度不超 + 不折行"，
  但字体对 `⎿`、`…` 的渲染宽度只能靠肉眼。
