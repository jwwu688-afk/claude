## 二、逐项详情

### 1. 摘要式压缩（`history_manager.py`）

**改前的问题**：上下文超过 80% 时，直接把旧消息删掉，只塞一句"历史已被压缩"。模型因此真的不知道之前聊过什么，你刚让它改的文件名、它刚刚踩过的坑，全部丢失。

**改后的流程**：

```
上下文超阈值
  → 算出"这次要删掉哪几条"（不含系统消息）
  → 把这批消息交给大模型，生成一段不超过 400 字的摘要
  → 用「摘要公告」替换掉被删的那一段
  → 保留：系统消息 + 摘要公告 + 近期对话
```

**关键实现**：

1）`auto_messages_compression` 改为异步（`history_manager.py:60`）

```python
# 改前
def auto_messages_compression(self) -> None:
    if self._requires_compression():
        self._compress_current_message()

# 改后
async def auto_messages_compression(self) -> None:
    if self._requires_compression():
        await self._compress_current_message()
```

2）删除前先算出「要删的那批」，单独送去摘要（`_compress_multiple_sessions` / `_compress_single_session`，308 / 347）

```python
removed_messages = [msg for msg in messages[:second_oldest_user_index]
                    if self._role_of(msg) != Role.SYSTEM]
summary = await self._summarize_if_possible(removed_messages)
self.messages_history[-1] = system_messages + self._create_compression_notice(messages, summary) + recent_messages
```

3）新增 `_summarize_if_possible()`（320）：三种情况返回 `None`，自动退回老做法

| 情况 | 处理 |
|---|---|
| 没有注入摘要器（如单元测试） | 返回 `None`，走原来的直接删除 |
| 要删的消息为空 | 返回 `None` |
| 调模型失败（无网/无额度/超时） | 打印一行提示，返回 `None`，**对话继续，不卡死** |

4）`_create_compression_notice(messages, summary=None)`（368）：有摘要就在公告里带上摘要，没有就用原来那句。

5）摘要器通过 `set_summarizer()`（117）注入，而不是在历史管理器里直接调模型。这样做的两个原因：

- 分层：历史管理器不该知道 API 密钥、模型名
- 可测：测试里不注入，就永远不会真的花钱调模型

### 2. 摘要生成器（`conversation.py`）

**新增 `SUMMARY_SYSTEM_PROMPT`（31）**，明确列出"必须保留 6 项 / 可以丢弃 4 项"，避免模型写一堆客套话摘要。必须保留的包括：用户目标与约束、关键决定及理由、改过哪些文件、遇到的错误与解决办法、未完成事项、用户偏好。

**新增 `_summarize_messages()`（333 附近）**：

```python
transcript = self._messages_to_transcript(messages)     # 消息 → 可读文字
request = {"messages": [system=压缩指令, user=transcript]}
loop = asyncio.get_running_loop()
message, token_usage = await loop.run_in_executor(None, self._api_client.get_completion, request)
```

这里是本轮一个容易忽略的细节：`get_completion` 是**同步**方法，如果在 `async` 函数里直接调用，会把整个事件循环卡住（界面不动、流式显示停住）。所以丢进线程池执行。

**新增 `_messages_to_transcript()`**：把消息按 `角色: 内容` 拼成文字，并且**把工具调用也记进去**（`assistant -> tool cmd_runner({"command": "ls"})`）——"改了哪些文件"这类信息主要藏在工具调用参数里，不记录的话摘要会丢掉最关键的部分。总长超过 24000 字符时保留头 70% + 尾 30%。

**注入点**（`conversation.py:86`）：

```python
self._history_manager = HistoryManager()
self._history_manager.set_summarizer(self._summarize_messages)
```

### 3. 退出收尾，消除 `cancel scope` 报错（`client.py`）

**改前的问题**：MCP 的连接是用 `AsyncExitStack` 打开的，但从来没关过。结果有两个：

1. 外部服务器进程（weather.py、calculator.py）会变成孤儿进程留在后台
2. 退出时打印 `RuntimeError: Attempted to exit cancel scope in a different task than it was entered in`

**根因**：anyio 规定「在哪个任务里打开的资源，必须在同一个任务里关闭」。原来的结构是「后台任务负责连接，主任务负责退出」，天然违反这条。

**改后**：让一个任务负责完整生命周期（`client.py:52` 的 `_run`）：

```python
async def _run(self):
    try:
        await self._connect_all()      # 连接
    except Exception as e:
        print(f"[MCP] 初始化异常：{e}")
    finally:
        self._ready.set()               # 就绪信号（不管成败都点亮）

    try:
        await self._shutdown.wait()     # 待命
    except asyncio.CancelledError:
        pass
    finally:
        await self._close_stack()       # 在同一个任务里关闭 → 不再报错
```

配套新增：

- `self._ready` / `self._shutdown` 两个 `asyncio.Event`（两个信号灯）
- `aclose()`（135）：点亮停止信号 → 最多等 5 秒 → 超时则取消任务
- `_close_stack()`（149）：`exit_stack.aclose()`，幂等，异常只打印不抛
- `get_sessions()` 改为 `await self._ready.wait()`（等信号灯，而不是等任务结束——任务现在会一直挂着待命，等它结束等于死等）

### 4. 退出链路串起来

```
main.cli()
  └─ asyncio.run(main())
       └─ main: try / finally
            └─ Conversation.shutdown()        conversation.py:407
                 └─ ToolManager.shutdown()    tool_manager.py:120
                      └─ MCPClient.aclose()   client.py:135
```

`main.py:75` 加了 `try/finally`，保证 Ctrl+C 也会走收尾；`main.py:87` 捕获 `KeyboardInterrupt`，不再打印一大段红色堆栈，只输出一行「已退出 QuickStar。」

### 5. 事件循环外创建对象不再报错（`client.py` / `tool_manager.py`）

**现象**（本轮验证时撞到）：在 `async` 环境外写 `Conversation()`，直接抛

```
RuntimeError: no running event loop
RuntimeWarning: coroutine 'MCPClient._run' was never awaited
```

**原因**：`MCPClient.__init__` 和 `ToolManager.__init__` 里都直接调 `asyncio.create_task(...)`，而这个函数要求当前有正在运行的事件循环。

**改后**：两个类都改成「有循环就现在启动，没有就等用到时再启动」。

```python
# client.py:58
self.connect_server_task = None
self._ensure_started()

# client.py:66
def _ensure_started(self):
    if self.connect_server_task is not None:
        return
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        return              # 没有循环，先不启动
    self.connect_server_task = asyncio.create_task(self._run())
```

`ToolManager` 同理由 `_ensure_mcp_registration()`（`tool_manager.py:52`）处理，并在 `get_tools_description()` 里先确保已启动再 `await`。

**行为变化**：`Conversation()` 可以在任何地方创建了；真正开始连 MCP 的时机变成「第一次要工具清单时」。

### 6. 工具输出截断（`display_manager.py` / `ui_manager.py`）

**改前**：`show_tool_execution` 把 `tool_args` 和 `result` 原样打印。跑一次 `npm install`，几千行日志直接刷满屏幕。

**改后**：`DisplayManager.shorten(text, limit)`（`display_manager.py:165`）

- 长度未超限 → 原样返回（短内容保留换行更好读）
- 超限 → 把 `\n` 折叠成 `⏎` 符号，压成一行，截断后附上「共 N 字符，已省略 M」

**应用位置**：

| 位置 | 参数上限 | 结果上限 |
|---|---|---|
| `show_preparing_tool`（155） | 200 字符 | — |
| `show_tool_execution` 成功分支（137） | 200 字符 | 400 字符 |
| `show_tool_execution` 失败分支 | — | 400 字符 |

输出样式也简化为：`Tool cmd_runner ok · args: {...} · result: ...`
