# 第 27 轮：找到"流式每次都断"的根因——httpx 在读系统代理

日期：2026-11-11
版本：0.10.2（未发版）

## 现象

用户的原话是「为什么每次都是有 `处理流式响应时出错：Streaming API request failed:
peer closed connection without sending complete message body (incomplete chunked read)`」。

关键特征是**规律性**，不是偶发：

- 每次都是流式失败、非流式重试立刻成功；
- 失败点在 `for chunk in stream` 的迭代里，即连接已建立、正在读 chunked 响应体；
- 上下文只有 28% 左右，不是"请求体太大被拒"。

第 26 轮只是把它从"一屏红叉 + 20 行堆栈"改成一行暗灰提示，**没有解决它为什么会断**。

## 根因

`httpx` 的 `trust_env=True`（openai SDK 默认值）在 **Windows 上会读注册表**，不只是读
环境变量。实测（把 `HTTP_PROXY` 等全部清空后）：

```python
>>> urllib.request.getproxies()
{'http': 'http://127.0.0.1:65532', 'https': 'http://127.0.0.1:65532', 'ftp': ...}
>>> httpx._utils.get_environment_proxies()
{'http://': 'http://127.0.0.1:65532', 'https://': 'http://127.0.0.1:65532'}
```

而用户机器的注册表里：`ProxyEnable=1, ProxyServer=http://127.0.0.1:65532`（代理软件开着）。
也就是说，**所有到讯飞 MaaS 的请求都在绕一层本地代理**。

为什么只有流式挂：
流式响应的连接寿命很长（模型边想边吐，可能几十秒都在持续传 chunked 数据），
本地代理在转发这种长连接时提前关闭了上游 socket，客户端读到"chunked 没收完就 EOF"，
正是 `incomplete chunked read`。非流式是一次性返回、连接立刻结束，同一个代理下相安无事。

这也解释了为什么"改用非流式重试"从来都能成功——两件事根本不是同一个问题。

## 改法

`APIClient.__init__` 里不再让 SDK 自己造 HTTP 层，改为传入自建的客户端：

```python
http_client=self._build_http_client()   # httpx.Client(trust_env=use_proxy)
```

`OPENAI_USE_PROXY` 开关：

| 值 | 行为 |
|---|---|
| 留空（默认） | `trust_env=False`，直连；忽略环境变量代理，也忽略注册表代理 |
| `1` | `trust_env=True`，恢复旧行为，走系统代理（接口在墙外时才需要） |

默认选直连的理由：thinker 的用户绝大多数接国内接口，直连又快又稳；多绕一层代理
不但没收益，还会把长连接交给一个不由我们控制的中间件。需要代理的场景（OpenAI 官方、
OpenRouter）显式写 `OPENAI_USE_PROXY=1` 即可。

## 验证

零模型调用、不联网：

```
默认        : mounts = {}          trust_env = False
USE_PROXY=1 : mounts = {2 条代理}  trust_env = True
```

`py_compile` 通过。

## 还没证实的一环

"代理掐断长连接"是从**现象 + 配置 + 大量同类案例**推出来的，逻辑闭环但尚未用一次真实
请求坐实（那要花钱调模型）。判定方法很简单：重启 thinker 后再跑同一段工具调用——

- 不再出现 `peer closed connection` → 确认是代理，本轮修复有效；
- 仍然出现 → 说明还有第二层原因（讯飞侧的超时/网关行为），需要抓 SSE 原始字节继续查，
  届时的兜底是"流式失败自动再重试一次流式"，而不是立刻退到非流式。
