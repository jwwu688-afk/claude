# 第 34 轮：压缩结果落盘，resume 不再重复压

日期：2026-11-13
版本：0.12.2 → 0.12.3

## 现象

用户反馈：每次 `/resume` 到同一个会话，第一句话发出去之前都要先弹一次"上下文太长了，正在自动压缩…"。

截图里的数字：

```
2026-11-10 20:59 · 797 条 · 用户消息 7 条
已恢复 796 条消息，按字符估算上下文约 368,142 token
```

窗口是 `MODEL_MAX_TOKENS=200`（204,800），368,142 / 204,800 = **179.8%**。
一恢复就已经 180%，第一个请求前必然触发一次 L5。所以那不是"偶尔压"，是"必然压"。

## 根因：文件与内存分叉

会话文件是 append-only 的：`SessionStore.append_message()` 每写一条就关文件，从不重写。
压缩只做一件事——把内存里的 `messages_history[-1]` 换掉。它**没有任何写回文件的动作**。

于是：

```
resume  → 读文件 796 条 → 估算 180% → 压到 10 条（只在内存里）
                                            ↓
                                      文件还是 796 条
                                            ↓
下次 resume → 又读 796 条 → 又 180% → 又压一次
```

不只是"多压一次"：每次都要**真花一次摘要调用**，而且第二次开始是在摘要"上一次的摘要"
（第一次压完，最老那段已经变成一条公告，再次压缩时送进模型的原料就只剩公告本身）。

`/clear` 的处理方式是"换一个新文件"，所以它天然没有这个问题；只有压缩漏了这一环。

## 改法

往会话文件追加一种新的行类型，resume 时用它重建视图。

```json
{"type": "compaction", "ts": 1763, "keep_from": 786, "summary": "前 12 轮已完成…", "before": 796, "after": 11}
```

`keep_from` 的含义：**文件里第 0~785 条 message 已被这段摘要取代**，786 之后的消息原样保留。
它之后的内容是"压缩后又聊的"，必须留着，否则压缩过的那次会话一 resume，后面的对话全丢。

resume 时：

```python
messages, header, compaction = _read_session(path)
if compaction:
    rebuilt = _apply_compaction(messages, compaction)   # 公告 + messages[keep_from:]
return rebuilt or [m for m in messages if m.get("role") != "system"]
```

三个关键设计：

1. **`keep_from` 是文件坐标，不是内存下标**。resume 之后内存前面会多一条新生成的 system，
   两边永远差一条；用内存下标会整体错位一条，症状是"恢复出来少一条/多一条"，很难往坐标上想。
   所以这个数由持有文件的人现算：`count_messages() - keep_count`，
   `history_manager` 只报告"我留了几条"（它不该知道文件长什么样）。
2. **多条记录只认最后一条**。最后一条描述了"包含前面所有压缩结果"的保留区，
   用更早的记录重建会退回压缩到一半的状态。
3. **记录坏了就退回完整历史**。`keep_from` 缺失、为负、不是数字，一律 `return None`，
   调用方拿到完整历史——宁可让用户多压一次，也不能因为一条坏记录把整段对话弄丢。

兼容性：`type` 不认识的行，老版本的 `load()` 会直接跳过，所以新文件在老版本里能正常打开
（只是没有压缩记录，行为退回改动前）。老文件没有这种行，新版本也照常工作。

## 顺带修：`/resume` 列表的条数

同一个问题的另一半。会话列表原来用 `SessionStore.load()` 数文件行数，于是显示
"803 条"，选中后却只恢复 12 条——用户第一反应是"压缩没生效"或者"数据丢了"。

现在列表用 `inspect_session(path)`，一次读盘同时给出两份：

| 字段 | 用途 | 为什么不能用另一份 |
|---|---|---|
| `raw` | 取预览（第一条用户说了什么） | 压缩后恢复出来的第一条是公告，拿它做预览会显示成 `[为节省上下文空间…`，完全看不出这个会话是干嘛的 |
| `effective` | 显示条数 | 显示文件行数会和恢复后的实际条数打架 |

压缩过的会标「（压缩后）」，免得用户以为原始记录被删了（原始记录仍在文件里）。

顺带统一了一个老口径：列表以前显示的是**含 system** 的行数，而恢复提示里的
"已恢复 N 条"是**不含 system** 的，两边本来就差一条。现在都用不含 system 的。

实测（用户那个真实会话）：`raw = 805`、`effective = 14`，列表显示"14 条（压缩后）"。

## 验证

新增 `test/test_compaction_resume.py`（8 组 31 条断言，全用假摘要器，不调模型）：

| 组 | 钉住什么 |
|---|---|
| 1 | 记录能写能读，`count_messages` 数得准 |
| 2 | 没有记录的老文件，行为逐字节不变 |
| 3 | 有记录时恢复出「公告 + 保留区」，公告里带摘要 |
| 4 | **压缩后新聊的消息不能丢**（`keep_from` 之后的必须保留） |
| 5 | 三种坏记录（缺字段/负数/非数字）都安全退回完整历史 |
| 6 | 多次压缩只认最后一条 |
| 7 | 端到端：压缩 → 落盘 → resume → 占用 < 0.70（连总闸都没到，不会再压） |
| 8 | 没注入落盘回调时压缩照常工作（只是不落盘） |

```
🎉 所有测试通过（31/31）
```

第 7 组是这次修复的核心：它同时断言了"记录写得对""重建条数对""恢复后不再触发压缩"。

## 遗留

- **已有的长会话不会自动变小**。这次改动只对"改动之后发生的压缩"生效；
  那个 796 条的旧会话，下次 resume 仍会压一次，但压完会落盘，再下一次 resume 就不会了。
  想立刻见效可以先 resume 一次（压一次、落盘），或者直接 /clear。
- **`count_messages()` 每次压缩都读一遍文件**（1~2 MB）。压缩是低频操作，实测无感；
  真到了几十 MB 的会话，可以改成维护计数器。
