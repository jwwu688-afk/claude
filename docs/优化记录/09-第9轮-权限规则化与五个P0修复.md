## 一、压缩：从"连环扣费"到"一份用量只压一次"

### 1.1 病灶

`Conversation._run_one_iteration()` 在一轮里会调两次 `auto_messages_compression()`：请求前一次、收到回复后又一次。而 `_compress_current_message()` 压完之后**不会改动** `history_token_usage[-1]`——那个数字还是"上一轮请求用了多少"。

于是 `_requires_compression()` 压完仍然返回 `True`：

```
用量 85% → 压一次（真调一次摘要模型）
        → 判断还是 85% → 再压一次（又调一次）
        → 下一轮迭代 → 还压
```

每一次都真的发一次摘要请求，**每一次都在扣费**，而且会一路把消息删到只剩一条用户消息。

### 1.2 改法：给"这份用量"打个已处理的点

```text
if self._compressed_for_current_usage:   # 这份用量已经压过了
    return
if not self._requires_compression():
    return
await self._compress_current_message()
self._compressed_for_current_usage = True   # 压完立刻打点
```

`update_token_usage()` 收到新的用量数字时把标记清掉——**新数字才是重新判断的依据**。

所以节奏变成：每次真实请求之后最多压一次。如果压完还超线，下一轮会再压一次（这是合理的：说明没腾出足够空间），但绝不会在同一份数据上连打。

### 1.3 实测

```
连续调用 4 次 auto_messages_compression → 摘要器只被调用 1 次   （改前 4 次）
update_token_usage(新用量) 后再调 1 次 → 摘要器累计 2 次
```

## 二、裁剪：不能把工具调用和它的结果拆开

### 2.1 两条会被服务端直接拒绝的规则

OpenAI 消息格式要求 `assistant(tool_calls)` 和紧随其后的 `tool` 结果**成对出现**：

| 切坏了 | 服务端报错 |
|---|---|
| 留下 assistant(tool_calls)，删掉它的 tool 结果 | `An assistant message with 'tool_calls' must be followed by tool messages` |
| 留下 tool 结果，删掉它的 assistant | `messages with role 'tool' must be a response to a preceding message with 'tool_calls'` |

而原来的裁剪全是"按下标硬切"：

```text
cropped_messages = system_messages + current_messages[crop_amount:]   # 顶部
cropped_messages = current_messages[:-crop_amount]                     # 底部
start_index = min(user_index + 1 + delete_message_num, len(messages))   # 自动压缩，+3 硬编码
```

三个入口都可能正好切在一对中间。**上下文一到阈值、一裁剪，下一次请求就 400，整个对话直接结束。**

### 2.2 改法：切之前把刀口挪到安全位置

新增两个对齐函数，方向永远是"多保留一点"：

```text
def align_top_cut(messages, index):
    """从 index 往后保留。若 index 落在一条 tool 上，退到它的 assistant。"""
    while 0 < index < len(messages) and _role(messages[index]) == Role.TOOL:
        owner = _owner_index(messages, index)
        if owner < 0 or owner >= index:
            break
        index = owner
    return index

def align_bottom_cut(messages, index):
    """保留 [0:index]。若最后一条是带 tool_calls 的 assistant，连它一起切。"""
    while 0 < index <= len(messages) and _tool_calls(messages[index - 1]):
        index -= 1
    return index
```

自动压缩（中间切一刀）方向相反——刀口落在 tool 上时要**往后推**，把整组一起删：

```text
while start_index < len(messages) and _role(messages[start_index]) == Role.TOOL:
    start_index += 1
```

`owner < 0` 时选择"不改刀口"，是因为历史里可能存在本来就残缺的数据（测试用的假消息就常见）。不去猜，比猜错安全。

### 2.3 顺带把话术改诚实

少了就是少了，不装作删满：

```
裁剪成功，但为保证工具调用与其结果不被拆开，实际少删了 1 条。
```

### 2.4 实测

| 场景 | 裁剪前 | 裁剪后 |
|---|---|---|
| 顶部删 2 条（刀口落在 tool） | — | `system, assistant, tool, user, assistant` ✅ |
| 底部删 1 条（刀口断在第 4 条申请后） | — | `system, user, assistant, tool` ✅ |
| 单会话压缩删 3 条（有 3 个 tool 结果） | — | `system, user, user(摘要公告), assistant` ✅ |

三个场景都通过同一个断言：序列里没有孤儿 `tool`、没有悬空的 `tool_calls`。

## 三、权限：被判断的人不能自己当裁判

### 3.1 病灶

第 8 轮的判定是一行：

```text
if "need_user_approve" in args:
    return bool(args["need_user_approve"])
```

`need_user_approve` 是**模型自己写的参数**。于是模型给一条 `del /s /q` 标上 `false`，命令就静默执行了。这不是模型坏，是设计给错了权力——**让被判断方提供判据**。

更糟的是这条行为被写进了测试：

```text
assert Conversation._needs_user_approval("cmd_runner", {"need_user_approve": False}) is False
```

测试把漏洞当成了规格。改代码时它会拦住你，除非你同时承认"这条断言本身是错的"。

### 3.2 改法：判定搬到 `core/permissions.py`，只收紧不放松

| 规则 | 判定 | 模型能否推翻 |
|---|---|---|
| 命中危险模式（22 条） | 必问，**高危**，回车默认拒绝 | ❌ 不能 |
| 只读工具（`file_read` / `file_glob` / `file_grep` / `todo_write`） | 不问 | 可以加严（写 `true` 就照样问） |
| 只读命令（`dir` / `git status` / `type` …） | 不问 | ❌ 不能（规则认定安全，不再多问一遍） |
| 其他一切（含 `python main.py`、`npm test`、`file_edit`） | 必问 | ❌ 不能 |

危险模式覆盖：`rm -r/-rf`、`del /s|/f|/q`、`rd /s`、`format X:`、`diskpart`、`mkfs`、`dd of=`、`> /dev/sdX`、fork 炸弹、`shutdown/reboot`、`bcdedit`/`reg delete`、`chmod 777`、`chown -R`、`git push --force`、`git reset --hard`、`git clean -fd`、`curl|bash`、`taskkill/killall/pkill`、`pip uninstall`、`npm uninstall/publish`、`Remove-Item -Recurse`。

### 3.3 只读白名单为什么要排除串联符号

```
dir                    → 免确认（白名单命中，无串联符号）
dir && del /s /q x     → 必须确认（前缀是 dir，但它串联了删除）
```

只判前缀会被这一招绕过，所以 `is_safe_command()` 先检查 `| && ; > < $( ` 这些记号，命中任意一个就直接判"不是只读"。

### 3.4 高危：把"回车即同意"翻过来

第 8.2 轮就在 `wait_for_user_approval()` 里留了 `default_yes` 参数，本轮终于用上：

```text
should_execute, content = await self._ui_manager.wait_for_user_approval(
    default_yes=not decision.is_high_risk
)
```

高危操作还多打一行黄字，告诉用户危险在哪：

```
⏺ cmd_runner(rm -rf /tmp/x)
! 高危操作（递归强制删除文件）：回车将默认拒绝，确认执行请输入 y。
  ? 是否执行？  回车拒绝 · 输入 y 允许 · 或直接说你想怎么改
```

新增 `print_warning()`（黄色 `!`），和 `print_error()`（红色 `✗`）分开：一屏里两处红，用户就分不清"已经出事"和"还没出事"。

### 3.5 代价，以及为什么接受

不在白名单里的命令（`python main.py`、`npm test`、`git commit`）现在都要确认一次，纯回车即过。这确实是多出来的摩擦，但换来的是：

- 模型**没有任何手段**给自己的命令发通行证；
- 用户看到的每一条命令都经过一次显式确认，而不是"模型说安全就算安全"。

第 10 轮会做"本次会话总是允许"的记忆（按工具/命令前缀记住用户的选择），那时候摩擦就消失了。

## 四、输出上限：一个数字，一个来源

同一个数字被定义了两遍，两刀砍在同一个输出上：

| 位置 | 改前 | 实际效果 |
|---|---|---|
| `cmd_runner.MAX_OUTPUT_CHARS` | 30000 | **等于白写**——输出进历史时又被砍到 12000 |
| `conversation.MAX_TOOL_OUTPUT_CHARS` | 12000 | 真正生效的那一刀 |

难受的不只是浪费：`file_read` 读 2000 行（约 15~20k 字符）本来读全了，会在写进历史时被腰斩，模型只能反复调 `offset` 重读——**截断反而让它多花钱**。

改法：`core/limits.py` 定义唯一来源，两边 import 同一个值（默认 30000，`MAX_TOOL_OUTPUT_CHARS` 可覆盖，带 1000 的下限保护）。顺带修掉截断提示语：

```
改前：如需完整内容，请分段读取：例如 `sed -n '开始行,结束行 p' 文件`，或用 `grep` 只取你需要的部分。
改后：如需完整内容：读文件请用 file_read 的 offset / limit 分段；查命令输出请把命令写得更窄。
```

原来那句教的是 Linux 命令，在这个项目跑的 Windows `cmd.exe` 上根本不存在——模型照着做只会连续失败。

## 五、裁剪摘要：写了就要留住

`smart_context_cropper` 的 `deleted_messages_summary` 是**必填参数**，说明书里还专门要求"删除前先用一句话把结论留下来"。

但代码拿到手就扔了：

```text
result = self._history_manager.crop_message(crop_direction, crop_amount)
return result   # ← 摘要去哪了？没了
```

也就是说：模型认真写的那段摘要，从来没进过对话，被删掉的信息是真的消失。这是"参数存在但语义缺失"——比报错更难发现，因为它不报错。

现在 `crop_message()` 多了 `note` 参数，把摘要包成一条用户消息，插在**被删掉那一段原来的位置**（顶部裁剪插在系统消息后，底部裁剪插在末尾）。

顺手修掉一个同链路上的静默 bug：

| 输入 | 改前实际行为 | 原因 |
|---|---|---|
| `crop_direction="TOP"`（说明书示例就是这么写的） | **从底部删** | 枚举值是 `"top"`，`"TOP" != "top"`，一路落到 `else` 分支 |

现在先归一化（去空格、转小写）再转枚举，转不了就明确报错。同时把说明书示例改成小写，两边对齐。
