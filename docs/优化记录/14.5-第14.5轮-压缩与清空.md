## 一、为什么这两条要单开一轮

第一批四条命令（`/memory` `/resume` `/init` `/cost`）最坏的结果是"某个数字显示不对"。
这两条不一样：

| 命令 | 失败后果 |
|---|---|
| `/compact` | 历史被替换坏 → 后面每轮请求都 400 |
| `/clear` | 会话状态和文件不一致 → 恢复时把用户以为清掉的内容带回来 |

风险等级不同，混在同一批里做，回归挂了没法二分定位是哪一条引起的。

## 二、`/compact`：把"该压但没到线"这种场景补上

### 2.1 为什么需要手动压

自动压缩只在超过 80% 时动手，那是防爆炸的兜底。但有一类情况永远等不到 80%：
刚让模型试了七八种写法，过程很长、结论只有一句。这时上下文可能才 30%，
压掉之后每一轮都省，而用户对此毫无办法。

### 2.2 三个副作用，都要写进代码里

`HistoryManager.compact_now()` 返回一个统计字典，且顺手处理三件事：

| 副作用 | 不处理的后果 |
|---|---|
| **重算用量账本** | `/cost` 和状态行继续显示压缩前的占用。明明压了、数字没动，用户会以为没用——"看起来没用"比真的没用更劝退 |
| **置 `_compressed_for_current_usage`** | 紧接着的自动检查发现"还超线"，又压一次。这正是第 9 轮那个"一旦过线连压三次"的坑 |
| **前缀缓存必然失效** | 消息列表整体换了，下一轮输入按原价计费。代码里消不掉，只能由命令的提示语明说，否则用户看到 `/cost` 里花费跳涨会以为是 bug |

### 2.3 为什么用 token 而不是"条数"判断有没有效果

压缩不是纯删除——它会在原位置插一条"历史已压缩 + 摘要"的公告。
删掉 3 条、插入 1 条，条数可能只差 2；极端情况下摘要比被删内容还长：
条数变少了，token 反而更多。

用户关心的是"省了多少上下文"，不是"少了几条消息"，所以判断用估算 token：

```text
if stats["after_tokens"] >= stats["before_tokens"]:
    print("这次压缩没省下 token：摘要本身也要占长度，被删的内容太短时不划算。")
```

### 2.4 为什么给 `_compress_current_message` 加 `announce` 参数

它的第一行是 `print_info("上下文太长了，正在自动压缩…")`。自动压缩说这句是对的
（用户没主动要求，需要知道发生了什么）；但 `/compact` 是用户点名的，
再说一遍"太长了"既多余，又和他的心智冲突——他本来就嫌长才按的。

默认 `announce=True`，自动路径完全不变；命令层传 `False`，自己说提示语。

## 三、`/clear`：清空必须同时换文件

### 3.1 只清内存是不够的

旧内容还在 JSONL 里。用户下次 `--continue`、或者用 `/resume` 选中那个文件，
刚清掉的对话会原样回来——他会认为命令坏了，而且完全无法察觉是"清了内存、文件还在"。

所以 `Conversation.reset_conversation()` 做四件事：

1. 用 `SessionStore.create()` 开一个新文件（cwd 和 model 沿用当前的，
   这样它在 `/resume` 里仍然归在"本项目"下）；
2. 清空当前页；
3. 用 `add_message(build_system_message())` 把系统提示词放回去
   —— 走 `add_message` 而不是手工拼一行，顺带享受了 `normalize_message` 那层处理，
   不必再写一遍"怎么序列化"；
4. 重新估算用量，别让 `/cost` 继续显示清空前的数字。

返回 `(旧文件, 新文件)`，命令层据此告诉用户"旧会话仍在，想回去用 `/resume`"。

### 3.2 为什么不把花费一起清零

花费是"这个进程到目前为止"的真实开销。清上下文不能让已经花掉的钱消失，
清零等于骗人。清不了，就说清楚——所以 `/clear` 的最后一行是：
"累计花费不重置：/cost 显示的是本次进程的总开销。"

## 四、现在的命令表

```
/help                               列出所有命令
/memory [文件名]                     查看模型记了什么（索引与正文）
/resume                             在历史会话里选一个接着聊
/init [--global] [--force] [--here]  生成 / 更新项目记忆骨架
/cost                               本次会话的花费与缓存命中
/compact                            立刻压缩上下文（不等 80%）
/clear                              清空上下文并开一个新会话
```

注册表从 5 条变成 7 条，`/help` 自动跟着变（这正是第 14 轮用"表"而不是 if/elif 的原因）。

## 五、测试

`test/test_commands.py` 新增 18 项，重点在"断言的正确性"而不是"跑通"：

| 组 | 关键断言 |
|---|---|
| `/compact` | 条数变少、系统提示词保留、摘要确实插进历史、摘要模型只被调 1 次、输出带前后 token、提醒缓存失效、账本被重算、已压标记置位 |
| `/compact` 无可压 | 只有系统提示词时提前拦下、**没有白花一次摘要调用**（用计数器验证）、历史没被动过 |
| `/clear` | 清空前 3 条 → 后 1 条 system、换了新文件、**旧文件仍在**、新文件正好两行（header + system）、提示语提到旧会话、账本重算 |

`/clear` 的测试里特意先铺一条 system 再铺一问一答：`reset_conversation` 是先清空再放回 system，
少了这条就看不出"系统提示词被保留"这件事。
