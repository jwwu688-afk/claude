# 第 15.2 轮：取消文件工具的路径边界

> 日期：2026-11-08
> 版本：0.5.1 → 0.6.0（行为变更，不是补丁）
> 触发：用户看了 15.1 轮的分析后决定「这些查找的工具不要设置范围」

---

## 一、决定

五个文件工具（`file_read` / `file_write` / `file_edit` / `file_glob` / `file_grep`）
不再检查路径是否在工作区内，可以直接操作任意路径。
配套的 `THINKER_ALLOW_OUTSIDE` 环境变量整套删除——不是默认改成允许，是这条判断不存在了。

用户选的是"五个全放开"，不是"只读放开、写入保留"。理由和 15.1 轮查出来的根因一致：
**边界只拦 file_\*，拦不住 `cmd_runner`**，所以它对愿意绕的模型完全没有约束力，
只对守规矩的模型构成障碍。

---

## 二、删了什么

| 位置 | 内容 |
|---|---|
| `file_tools.py` | `_allow_outside()` 整个函数 |
| `file_tools.py` | `_within_workspace()` 整个函数（含第 12 轮给记忆目录开的特批） |
| `file_tools.py` | `_resolve_path()` 末尾的越界检查与那段"请设置 THINKER_ALLOW_OUTSIDE=1"提示 |
| `file_tools.py` | `file_glob` 里对 `glob` 结果的 `_within_workspace` 过滤 |
| `file_tools.py` | `file_grep` 遍历时对每个文件的 `_within_workspace` 过滤 |
| `file_tools.py` | `from core.auto_memory import is_memory_path`（只被边界特批用过） |
| `file_tools.py` | `file_read` / `file_write` 说明书里"默认只能读写工作区内"两句 |
| `system_rule.py` | 提示词里「默认只能操作工作区内路径／让用户设开关／不要用 cmd_runner 绕过」整段 |
| `.env` / `.env.example` | `THINKER_ALLOW_OUTSIDE` 配置项 |
| `test_file_tools.py` | `run_all_tests()` 入口那段"把开关钉成未放行"的环境清理 |

**留下的**（容易一起删错，特别标出来）：

- `WORKSPACE_ROOT` 还在。它现在只剩两个用途：补全相对路径、当 `file_glob`/`file_grep` 的默认搜索起点。
- `_resolve_path()` 还在，只是不再判权限。里面的 `resolve()` 不能省——`_read_files` 拿路径字符串当键支撑"先读后写"，同一个文件不同写法必须落成同一个字符串。
- `is_memory_path()` 还在 `auto_memory.py` 里，`permissions.py` 继续用它做"记忆目录免审批"。取消路径限制是"允许访问"，不等于"允许不问就写"。

---

## 三、为什么是"删掉"，不是"把默认值改成允许"

两种写法对外表现一样，但含义完全不同：

| 写法 | 后果 |
|---|---|
| 把 `os.getenv(...) == "1"` 改成 `return True` | 函数还在、分支还在、提示词还能提"越界"、后人会以为这是个可配置的开关，去改 `THINKER_ALLOW_OUTSIDE` 却发现无效 |
| 整条删掉 | 没有"越界"这个概念了，模型不会收到那句提示，也不会去想"是不是需要设置什么" |

选后者，是因为**半留的机制比没有机制更糟**：它会让人反复怀疑自己配置错了。
这也是 15.1 轮那次的教训——用户看到"路径超出工作区，请设置 THINKER_ALLOW_OUTSIDE=1"，
第一反应是"我是不是没设"，而不是"这个设计有问题"。

---

## 四、现在还剩哪些保护（实测）

取消路径限制后，风险并没有全放开——只是把把关的位置从"工具层"挪到了"权限层"：

| 操作 | 要不要审批 | 说明 |
|---|---|---|
| `file_read` 任意文件 | **否** | 读这一侧完全静默 |
| `file_glob` / `file_grep` 任意目录 | **否** | 只读 |
| `file_write` 任意路径 | **是** | 写文件默认要问，与路径无关 |
| `file_edit` 任意路径 | **是** | 同上，且还有"先读后写 + SHA1 校验" |
| `cmd_runner` 危险命令 | **是 + 高危** | 如 `del /f`，回车默认拒绝 |
| `cmd_runner` 普通命令 | 否 | 如 `dir` |

写文件那两行是重点：**"能写"和"不问就写"是两件事**。
`file_write` / `file_edit` 仍然会停在 `? 是否执行？`，用户在那一刻看着完整路径，
完全能判断"它要往 C:/Windows 里塞东西"。

真正变松的只有"读"：`file_read` 现在可以静默读盘上任意文件，包括密钥和其他项目源码。
这是这次改动的确切代价，没有别的遮掩。

## 五、验证

| 项 | 结果 |
|---|---|
| `file_glob(pattern="*简历*", path="C:\Users\Jarvis\Desktop")` | 找到 `我的简历.pdf` |
| `file_write` 写到工作区外临时目录 | 成功落盘 |
| `file_read` 相对路径 `pyproject.toml` | 仍以 `WORKSPACE_ROOT` 为基准 |
| `file_read` 读工作区外不存在的文件 | 报「文件不存在」，报不到「超出工作区」 |
| `THINKER_ALLOW_OUTSIDE=0` 时再测 | 行为完全一样（证明旧开关真失效了） |
| 7 次 `classify()` 实测 | 见上表，写入要审批、危险命令高危 |
| `test_file_tools.py` | 16/16 |
| 其余 14 个离线脚本 | 全绿 |
| 模型调用 | **0 次** |

测试里那个用例是**反向改写**的，不是删掉：

`test_workspace_boundary_switch` → `test_outside_path_allowed`。
原来断言"必须被拒绝"，现在断言"必须能用"，并额外加了一条
"把 `THINKER_ALLOW_OUTSIDE` 显式设成 0 也要能读"——这是"真的删干净了"的反证。
只删不补的话，"路径不再被拦"这个新行为没有任何测试守着，
将来谁把边界加回去，测试会一声不吭地全绿。

---

## 六、代价与遗留

**代价（明确的）**：`file_read` 读任意文件不再有二次确认。
读密钥、读别人的项目、读浏览器配置——都拦不住了。这是有意接受的。

**遗留**：`cmd_runner` 一如既往地不设防，而它比 `file_read` 危险得多（能删能改能联网）。
本轮没有碰它，因为它本来就没有路径检查，也没有"取消"可言。
如果将来要真正收紧，方向是给 `classify()` 加路径判定：

1. 命令里出现工作区外的绝对路径 → 要求审批；
2. 但要注意 `git`、`pip`、跑测试本身就会带外面的路径，不能一刀切，得先定白名单。

**另外，08.0 轮那份优化记录里写的"路径边界"实现细节现在已不适用**。
那份文档是当时的历史记录，故意不改——翻旧账时应该看到"当时是这么设计的"，
而"现在为什么不是了"由本文负责回答。
