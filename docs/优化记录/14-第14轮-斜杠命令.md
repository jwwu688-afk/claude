## 一、为什么这批命令不该发给模型

`/cost` 问"花了多少钱"——模型不知道，说了也是编。`/resume` 要切会话——那是本地文件操作。`/memory` 问"你记了我什么"——那是磁盘上的几个 markdown。

把它们当普通消息发出去，会有三重代价：多付一次输入；拿到一个编造的答案；这条命令本身还留在了上下文里，以后每轮都在为它付费。所以必须在**进历史之前**截下来。

反过来，只有纯本地能答的才配当命令。像"帮我重构这一段"这种，交给模型才是对的——命令系统不该变成第二套 if/elif 的意图路由。

## 二、拦截点：三个入口，一个函数

主 agent 有三处会等用户输入：开场、Esc 中断之后、一轮说完之后。三处各写一遍 `if text.startswith("/")`，将来加第四处必然漏。

所以收进 `Conversation._read_user_input()`：

```text
while True:
    text = await self._ui_manager.get_user_input()
    if not is_command(text) or self._task_depth > 0:
        return text
    await handle_command(text, self)
```

两个细节值得说：

**为什么命令处理完是"继续 while"，不是"返回空串"。**
`/cost` 打完用户当然还要接着说下一句。如果这里返回空串当作用户消息，模型会收到一条空消息，还要为它付一次输入费用——而这条命令问的偏偏是"我花了多少钱"。

**为什么必须 `is_command` 判断行首。**
正文里 `/` 太常见：`D:/code`、`3/4`、正则 `a|b`。只认"行首就是 `/`"，和 shell 的习惯一致。测试里专门验了 `3/4` 和 `D:/code` 不算命令。

## 三、四条命令的取舍

### 3.1 `/memory`（A1）

第 12 轮上了自动记忆之后，模型一直在往 `~/.thinker/projects/<项目>/memory/` 里写，但用户**完全看不到**。记错、记重、记了不该记的，只能自己开资源管理器翻。只写不读的记忆系统，用户没法信任它。

- 不带参数：目录、条目数、条目清单、索引全文
- 带参数：看某条的正文（扩展名可省）

带参数那条加了越界检查：`/memory ../../.ssh/id_rsa` 会被 `is_memory_path()` 挡住。命令是用户手打的，理论上不会乱来，但这条路径最终会喂给 `open()`，有检查总比没有好。

### 3.2 `/resume`（I3）

`--continue` 只能接"最近一次"，而且只能在启动时用。这条补的是"有几个会话想挑一个"和"聊到一半想换回去"。

列表只显示最近 10 个：终端一屏能看全，再多就得翻页，而翻页要引 `prompt_toolkit`——项目明确不加依赖。

选项展示用"时间 + 条数 + 首句预览"，而不是让人抄一长串文件名。这也是为什么没用现成的 `get_choice_input`：它的语义是"输入必须命中选项"，适合 `a/b/c`，不适合一整行摘要。新加的 `get_numbered_choice` 只返回下标，取消/非数字/越界一律返回 `None`——取消是正常操作，不该逼调用方写 `try/except`。

### 3.3 `/init`（M2）

`--init` 必须**启动前**敲。而人往往是聊到一半才发现"这个项目的约定该写进 THINKER.md"，这时退出重开、再进来，上下文就断了。

复用的是 `write_init_file()`，和 CLI 那条路径同一份逻辑。默认不覆盖已存在的文件——里面可能是用户手写了几百字的约定，一条命令全毁掉的代价远大于便利。

提示里补了一句容易被忽略的事实：**记忆是启动时读进系统提示词的，改完要重启 thinker 才生效**。不说的话，用户会以为改完立刻就能用。

### 3.4 `/cost`

第 6 轮加的缓存命中率只出现在每轮结束的状态行里，滚两屏就看不见了，而且那是"这一轮"的视角，回答不了"我这个下午一共花了多少"。

一个必须说清楚的点：`_record_usage` 只在接口返回 `usage.model_extra.cost` 时才累加花费。返回 0 有两种可能——真的一分钱没花，或者接口根本不报。分不清就显示 `未提供`，不能显示 `$0.00` 让人以为免费。token 和命中率是准的，这两项照常显示。

## 四、顺带做的两处抽取

`/resume` 要"换一份历史"，而 `--continue` 已经有一份几乎一样的逻辑。与其复制，不如抽出来：

| 方法 | 职责 | 谁在用 |
|---|---|---|
| `build_system_message()` | 造系统消息 | 新建会话、`--continue`、`/resume` |
| `_load_session_into_history(path)` | 读文件 → 换历史 → 补用量账本 → 换会话句柄 | `--continue`、`/resume` |

抽的理由不是"代码好看"，而是**第 13.1 轮补的那个用量估算只补在一处**。再复制一份，下次改动必然漏一边，而漏的后果是恢复长会话直接 400。

另外 `_load_session_into_history` 用"直接替换列表"而不是"清空再逐条 append"：append 会走 `add_message`，把刚从文件读出来的消息又写回同一个文件，每条存两遍，文件越滚越大。

---

## 五、本轮不做

`/compact` 和 `/clear` 会改上下文页，风险等级和这四条不一样：前者要绕过阈值强制压缩（得给 `HistoryManager` 加公开方法），后者要想清楚"只清内存还是同时换会话文件"——只清内存的话，旧内容还在 JSONL 里，下次 `--continue` 全回来，用户会认为没清干净。

留到第二步单独做，回归也要多覆盖两个点：命令不写进历史、切会话后旧文件仍可恢复。后者已经在 `test_commands.py` 里验了。
