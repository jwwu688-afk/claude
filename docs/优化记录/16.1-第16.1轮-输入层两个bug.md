# 第 16.1 轮：输入层两个 bug（首字删不掉、提示符消失）

> 日期：2026-11-08
> 版本：0.7.0 → 0.7.1
> 触发：用户实测反馈「橙色的小箭头没有了」「删除到最后一个字就无法删除」

---

## 一、现象

第 16 轮（Tab 补全）上线后，用户重启试用，报了两个问题：

1. 启动之后橙色的小箭头（输入提示符 `>`）没有了；
2. 输入内容退格删除时，删到最后一个字就删不动。

---

## 二、根因：同一行代码，两个后果

问题出在 `_read_line` 的最后一行：

```text
return input(prompt + first)      # ← 错的
```

`first` 是"为了判断要不要进自管模式"而先探走的第一个字符。
为了让屏幕上"看起来"有这个字，把它拼到了提示符后面。

**错在 `prompt` 不是输入内容。**

`input(prompt)` 的 prompt 只是**显示**用的，它不属于可编辑区。
所以：

| 后果 | 具体表现 |
|---|---|
| **删不掉** | 用户打的第一个字变成了提示符的一部分。用户按退格只能删自己输入的部分，删到那个字就卡住——这正是"删到最后一个字就无法删除" |
| **悄悄丢字** | `input()` 返回的是"从 prompt 之后读到的内容"。拼进 prompt 的那个字**根本不在返回值里**。用户输入"帮我看看"，上层拿到的是"我看看" |

第二个后果更隐蔽：用户还没发现，但模型收到的内容已经少了一个字。
而且它不会报错、不会提示，只是对话质量莫名下降。

`prompt_text()` 返回的是 `"\x1b[38;5;209m>\x1b[0m "`——橙色 `>` 加空格。
拼上用户的字之后变成 `"\x1b[38;5;209m>\x1b[0m 帮"`，屏幕上看起来"很正常"，
所以这个 bug 从截图里完全看不出来。

---

## 三、问题 1（提示符消失）的两个可疑来源

`prompt + first` 那个问题**不会**让 `>` 消失——它明明显示出来了。所以箭头消失是另一条线：

1. **`print()` 不 flush**。原代码里有一个分支：
   ```text
   if first in KEY_ENTER:
       print()
       return ""
   ```
   `print()` 走的是 `sys.stdout`，而界面其余部分走 rich 的 Console。
   `print()` 不 flush，rich 的输出可能先落地，导致用户看到的顺序是
   "输入行 → 横线 → 状态栏"，状态栏（那个橙色 `▸▸`）看起来就跑到了输入框上面，
   或者被覆盖掉了。

2. **rich 缓冲与 `input()` 抢顺序**。`input()` 直接往 `sys.stdout` 写提示符，
   如果 rich 的内容还压在缓冲里，后写的会把先写的盖住。

两处都处理了：

- `print()` 分支整个删掉（新方案里回车由 `input()` 自己处理，不需要我们插手）；
- `_draw_rule()` 画完横线和状态栏后显式 `console.file.flush()`。

**为什么用 `console.file` 而不是 `sys.stdout`**：rich 可能被重定向到别处
（测试里会换成 StringIO），刷错对象等于没刷。

---

## 四、修法：把字符塞回控制台缓冲区

`msvcrt.ungetch(char)` 是 CRT 提供的标准反向操作——"把字符推回控制台缓冲区，
下一次读取会先拿到它"。这正是这种场景需要的东西：

```text
first = read_char()
  ├── "/"          → 进自管模式（initial="/"，字符已被读走，要补回）
  ├── Ctrl+C       → 抛 KeyboardInterrupt
  ├── 方向键       → 吃掉第二个字节，当作没输入过
  └── 其余（中文/回车/退格）→ unget(first) 然后 input(prompt)
```

关键差别：**现在 `input(prompt)` 的 prompt 只有提示符**，用户的字是通过 `ungetch`
回到输入流的，所以它显示在光标位置、可以退格、也会出现在返回值里——
和后面打的字完全同权。

顺带把 `KEY_ENTER` 那个分支（`print()` + `return ""`）也删了：
回车现在同样走 ungetch，`input()` 读到回车会自己返回空串并换行，比我们手动 print 干净。

## 五、最该记下来的一条：测试断言写反了

第 16 轮的测试里有一条：

```text
check("普通字符：已读的字符合到提示符后", seen_prompts == ["> 帮"], ...)
```

**这条断言把 bug 当成了正确答案。** 测试全绿，行为是错的。

断言的是"我实现的",不是"用户想要的"。写的时候脑子里想的是"我这样设计，代码确实这样做了"，
所以通过了——而"这样设计本身对不对"根本没有被问过。

更糟的是它给了一个**虚假的安全感**：14 项断言、"首字符四个分支各自单独验"，
看起来非常严谨，却没有一条在验证"用户能不能删掉第一个字"。

修完之后测试改成：

```text
check("普通字符：结果完整、不丢字", got == "帮我看看这个文件", ...)   # 断言返回值完整
check("普通字符：第一个字被塞回缓冲区", editor.ungeted == ["帮"], ...)  # 断言字符回到输入流
check("普通字符：提示符里不含用户的字", seen_prompts == ["> "], ...)   # 断言 prompt 干净
```

三条分别对应：不丢字、可编辑、提示符不被污染。

**教训**：断言要写"用户视角的可观察结果"（返回值完不完整、提示符干不干净），
不要写"我的实现细节长什么样"（`prompt` 拼上了什么）。
后者只会固化当时的选择，包括错误的选择。

新增的关键断言：

- 普通字符 → `ungeted == ["帮"]`，`input()` 收到的 prompt 是 `"> "`（不含用户的字）；
- 回车 → 也是塞回后走 `input()`，不再有 `print()`；
- 方向键 → 两个字节都吃掉，**不往缓冲区塞半个键**（否则屏幕上出乱码）；
- `unget` 失败 → 退化成老办法，但断言"至少没把这个字丢掉"。

## 七、代价与遗留

- **`ungetch` 依赖 Windows 的 CRT**。非 Windows 上 `available` 为 False，走原 `input()`，
  功能不受影响（只是没有 Tab 补全）。
- **仍然无法在自动化测试里验真机**。`isatty()` 在管道里永远是 False，
  所以本轮所有验证仍然基于"假编辑器 + 替换 builtins.input"。
  真实键盘行为只能靠用户实测——上一轮就是漏了这一环。
- **提示符消失的根因无法 100% 确认**。我做的是"把两个可疑来源都堵掉"：
  删掉不 flush 的 `print()`、补上显式 flush。如果重启后还有问题，需要用户描述
  是"完全没有 `>`"还是"`>` 位置不对"，两者的排查方向不同。
