## 一、为什么单开一个 13.1，而不是直接进第 14 轮

这三处都不是"缺功能"，而是"功能已经在，但在真实场景下会打折"。它们的共同点是：**短会话、顺利路径下完全看不出来**，只有用久了才会撞上。

按 ROADMAP 第六节的判断标准，它们属于第一条「是不是阻断日常使用」——只是被第 13 轮的成果盖住了。放在第 14 轮里一起做，会和 slash commands 的改动混在同一个提交里，出问题时不好二分定位。

## 二、补丁一：`--continue` 恢复了一个"没有账本的会话"

### 2.1 症状

`thinker --continue` 接着上次聊，如果上次已经聊到上下文 80%，**第一次请求就可能 400**：

```
Error code: 400 - context_length_exceeded
```

### 2.2 原因

第 13 轮的恢复路径只做了一件事——把消息列表换掉：

```python
self._history_manager.messages_history[-1] = [system_message] + restored
```

但"要不要压缩"的判据在账本上：

```python
def _requires_compression(self) -> bool:
    if self._compress_threshold and self.history_token_usage:   # ← 空列表在这里短路
        ...
    return False
```

恢复时 `history_token_usage` 是空的（新建的 HistoryManager 从没记过账），于是**无论历史多长，一律判"不用压"**。整份历史原样发出去，撞上限就 400。

讽刺的是：短会话恢复没问题，偏偏"最需要接着聊的长会话"最容易崩。

### 2.3 解法：恢复完立刻补一条估算

精确用量只有接口返回才知道，但压缩判断必须发生在发请求**之前**——鸡生蛋。所以只能估，而估算只需要回答"大概在不在阈值附近"。

估算口径按字符分两段，而不是一个统一系数：

| 内容 | 系数 | 依据 |
|---|---|---|
| 中文 / 中文标点 / 全角符号 | 1 token / 字 | 中文在主流分词器里通常 1 字 1 token |
| ASCII、代码、命令输出 | 0.28 token / 字符 | 约 3.5 字符 1 token |

为什么不用 0.5 一把梭：这个项目的上下文里既有中文注释，又有大段代码和 `dir` 输出。统一按 0.5 算，纯中文低估一半（可能 400），纯代码高估一倍（白压一次）。

**宁可估高，不可估低**：估高最多多触发一次压缩，代价是一次摘要调用的钱；估低会撞 `context_length_exceeded`，整轮对话直接结束。

另外两个容易漏的点也补进去了：

1. **`tool_calls` 的参数**。一次 `file_edit` 的 `new_string` 可能有几千字符，它不在 `content` 里。只算正文会严重低估——而"改文件的会话"恰恰最容易撑爆上下文。
2. **每条消息 4 token 的格式开销**。role、分隔符、结构包装都要占位，几十条攒起来也是几百。

### 2.4 效果

```python
estimated_tokens = self._history_manager.seed_usage_from_messages([system_message] + restored)
```

恢复界面上会多一句：`已恢复上次会话：N 条消息（按字符估算上下文约 X token）`。这个数字是估的，但足以让人提前判断"这次接上会不会立刻触发压缩"。

## 三、补丁二：工具炸了，界面却是绿的

### 3.1 症状

工具内部抛异常（文件不存在、命令超时、磁盘满），屏幕上仍然是成功的样子，模型却收到一句"运行工具时出错"。

### 3.2 原因

`ToolManager.run_tool` 里有一层兜底：

```python
try:
    return await tool.act(**kwargs)
except Exception as e:
    return f"运行工具 '{tool_name}' 时出错：{str(e)}"
```

看起来"更稳"，实际有三个后果：

| 后果 | 说明 |
|---|---|
| 调用方的失败分支成了死代码 | `Conversation._execute_tool` 也有一层 `try/except`，异常在这里就被吃掉，那一层永远走不到 |
| 界面永远显示成功 | `_execute_tool` 只有进了 `except` 才会传 `success=False`，所以用户看到的始终是绿色的结果 |
| 模型缺少判断依据 | 它只拿到一句"出错"，没有异常类型，很难判断该换参数还是换工具 |

第三点尤其要命：这个项目是教学向的，**"工具失败 = 给模型一条失败消息"** 是 agent 自我纠错的主线（见 `_execute_tool` 的注释）。而这层吞异常恰好把主线掩盖掉了——读者会以为失败路径根本没实现。

### 3.3 改法

`run_tool` 只负责"找工具 → 调用"，不负责兜错：

```python
tool = self.tools.get(tool_name)
if tool is None:
    available = "、".join(sorted(self.tools)) or "（无）"
    raise KeyError(f"找不到工具 '{tool_name}'。当前可用：{available}")
return await tool.act(**kwargs)
```

找不到工具也从"返回一句中文"改成抛 `KeyError`，理由同上：调用方需要知道这是失败，而不是拿到一句长得像正常结果的话。顺带把可用工具清单带回去，模型下次照着清单挑，不用继续猜名字。

### 3.4 验证

用假工具跑了一遍（不发任何请求）：

```
✓ 工具异常已抛出: RuntimeError 磁盘满了
✓ 未知工具抛 KeyError，提示带可用清单
✓ 界面收到: [('boom', False)]
```

## 四、补丁三：两个测试脚本从来没跑通过

项目约定测试是"独立脚本 + 最后打印 🎉"，没有 pytest 兜底，所以脚本本身写错也不会有人发现。

| 脚本 | 问题 | 为什么一直没暴露 |
|---|---|---|
| `test_full_conversation.py` | `conv.messages = [...]` 给只读 property 赋值，必抛 `AttributeError` | 报错信息是 "can't set attribute"，看着像环境问题而不是测试写错 |
| `test_streaming_with_tools.py` | `tool_manager.get_tools_description()` 漏了 `await`，拿到的是协程对象 | 这脚本要真调模型（花钱），平时没人跑 |

修的时候还牵出两个连带问题：

1. **`DisplayManager` 缺省属性**。`print_streaming_content()` 用到 `_stream_mode` / `_body_started`，而它们只在 `start_stream_display()` 里赋值。不走 start 就直接喂内容 → `AttributeError`。已在 `__init__` 里给出安全默认值（`plain` + 未开始），并把"想了多久"的计算加上 `_stream_start` 保护——否则会算出几十亿秒。
2. **退出时的 MCP 噪声**。`test_full_conversation` 通过后仍会打一行
   `[MCP] 获取工具列表失败：（已跳过该服务器）`。真实原因是收尾时后台任务被取消，异常消息为空，被当成故障。现在加了 `MCPClient.is_closing`，关闭期间直接跳过；真实失败也补上异常类型，不再是"冒号后面什么都没有"。

`pyproject.toml` 的 `requires-python` 同时从 `>=3.8` 改成 `>=3.9`。代码里已有 `tuple[bool, str]`、`list[ClientSession]` 这类运行时求值的内置泛型注解，3.8 上导入即失败。声明一个跑不起来的下限，比不声明更坑人——照着装的人只会以为是自己环境坏了。

## 五、顺带修的一处配置冲突

仓库自带的 `.env.example` 里 `MAX_TOOL_OUTPUT_CHARS=12000`，而 `core/limits.py` 的默认值是 `30000`，注释里还明确写着：

> 兜底上限必须 >= 任何一个业务上限，否则业务上限就是假的。

`file_read` 一次最多读 2000 行，正常代码文件约 3~6 万字符。按 12000 截断，**一次正常读文件就会腰斩**，模型只能反复带 `offset` 重读——本来是为了省钱，结果更贵。

本地 `.env` 已按 30000 配置。`.env.example` 保持原样未动，是否需要改回 30000 留给下一轮决定（它是提交进仓库的文件，改动会影响所有人）。
