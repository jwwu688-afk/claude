# 第 31 轮：`/mcp` 状态面板

> 日期：2026-11-12
> 版本：0.10.2（未动版本号，与第 26~30 轮保持一致）
> 触发：配了 MCP 之后想知道「到底哪个连上了」，现在只能去翻启动日志
> 教训：**「配置里有什么」和「实际连上了什么」是两份数据；只展示其中一份，用户就会在错误的地方找问题**

---

## 一、一句话方案

会话内加一条 `/mcp`，读出**当前进程**的 MCP 连接状态，一行一个服务器：

```text
· MCP 服务器 4 个（已连接 1，失败 1，跳过 2）
✔ weather · 2 个工具
✗ bad · 连接失败 · FileNotFoundError: [WinError 2] 系统找不到指定的文件。
! remote · 已跳过 · 类型 http（本版本只支持 stdio）
! nocmd · 已跳过 · 缺少 command
· 配置文件：C:\Users\Jarvis\.thinker\mcp.json
```

绿勾 = 连上，红叉 = 连失败，黄色感叹号 = 配置阶段就被跳过。状态靠符号和颜色区分，不靠读文字。

---

## 二、为什么不复用 `thinker mcp list`

| | `thinker mcp list`（终端） | `/mcp`（会话内） |
|---|---|---|
| 读什么 | 配置文件 | 当前进程已建立的连接 |
| 回答 | 我配了什么 | 哪些真的连上了 |
| 数据来源 | 严格读一次 JSON | `MCPClient` 的内存状态 |
| 失败原因 | 看不到（未知字段照原样打印） | 连接异常原文 |

两者会不一致，**而不一致本身就是信息**：文件里配了 3 个、`/mcp` 显示 2 个已连接 + 1 个失败，那个失败的就是当前要修的东西。只做 `list` 的话，用户会拿着配置文件反复核对了半天——文件完全正确，问题在运行时。

这也是为什么 `/mcp` 不做 `add/remove`：配置改动走终端命令、改完重启（理由见第 30 轮文档第七节）。

## 三、五种状态

`MCPClient.status_snapshot()` 返回 `[{name, state, detail}]`，`state` 只有这五个值：

| 状态 | 什么时候 | 显示 |
|---|---|---|
| `connected` | 握手成功 | ✔ 名字 · N 个工具 / 已连接，正在取工具清单… / 已连接，但取工具清单失败 |
| `failed` | 启动子进程或握手抛异常 | ✗ 名字 · 连接失败 · 异常原文 |
| `connecting` | 连接阶段还没结束，这条还没出结果 | · 名字 · 连接中… |
| `idle` | 连完了却既没成功也没失败 | ! 名字 · 没有连接，也没有失败记录 |
| `skipped` | 配置加载阶段就丢了 | ! 名字 · 已跳过 · 原因 |

两个容易忽略的点：

- **`connected` 里还分三种**。连上 ≠ 有工具：`list_tools` 可能失败（服务器实现了握手但没实现工具列举），也可能还没跑完。这三种混成一句"已连接"，用户就会去查服务器启动参数，而真正的原因在工具列举。
- **`idle` 正常不该出现**。留这个状态并显示出来，是因为"既没连上也没失败"只能意味着有段代码漏记了——静默跳过等于把 bug 藏起来（第 16.1 轮的教训）。

## 四、数据是怎么串起来的

以前 `MCPClient` 只有一个 `self.sessions`（纯列表），只记"连上了几条"，丢了"哪一条是谁"。所以第一步是把连接结果按名字建索引：

| 字段 | 谁填 | 内容 |
|---|---|---|
| `connections` | `MCPClient._connect_all` | 名字 → 会话（握手成功才写） |
| `failures` | `MCPClient._connect_all` | 名字 → 异常（带类型名，空消息异常也有线索） |
| `tool_names` | `ToolManager._register_mcp_tool` | 名字 → 工具名列表（`list_tools` 成功后回填） |
| `tool_errors` | `ToolManager._register_mcp_tool` | 名字 → `list_tools` 的失败原因 |
| `skipped` | `MCPConfig._load_config` | 名字 → 跳过原因（与启动日志同一套文案） |

`/mcp` **只读**这些字段，自己不发起任何连接、不 await 任何信号。原因很实际：配了 `npx` 形式的服务器，首次启动要下载包，可能十几秒；命令要是等它连完才输出，用户会以为卡住了。所以拿到"此刻"的状态就打印，没出结果的显示"连接中…"，再敲一次就是新的。

## 五、顺手清掉的东西

- **`MCPClient.get_sessions()` 删除**。它返回纯会话列表，调用方拿不到名字，正是这一轮要解决的问题的根源。职责并入 `get_connected()`（名字 → 会话，同样可按序遍历）。原位置留一段注释说明它去哪了，免得按旧代码搜的人到处找。
- **`self.sessions` 删除**。`connections` 是有序字典，遍历顺序仍等于配置文件顺序，原来"按序处理"的用法一字不用改。
- **`ToolManager` 的失败日志补上服务器名**。原来是 `获取工具列表失败：xxx（已跳过该服务器）`——多个服务器时根本看不出是哪个跳过了。

## 六、验证

`python test/test_mcp_status.py` —— 20 条断言，全部用假对象，不连服务器：

- 五种状态各自判对（含 `connected` 的三个细分：有工具数 / 清单未回填 / 取清单失败）；
- 跳过项排在正常项之后，且带原因；
- 命令输出走对通道（成功绿、失败红、跳过黄），并带上配置文件路径；
- `/mcp add foo` 会被引到 `thinker mcp add foo`，而不是拼成 `add add foo`。

真实连接冒烟（本地 weather / calculator，不调模型）：

```text
· MCP 服务器 2 个（已连接 2）
✔ weather · 2 个工具
✔ calculator · 1 个工具
```

再拿一份临时配置塞进「不存在的可执行文件 + http 类型 + 缺 command」三条，四种状态一次全显示正确，且工具表里原本的 11 个内置工具没受影响。

回归：`test_mcp_cli.py` 49/49、`test_compress_boundary.py` 37/37。

## 七、没做的事

- **不做实时刷新**。`/mcp` 是一次快照，不会持续监听"某条连接断了"。要做就得在 UI 层加一个定时器，会跟输入重绘抢终端，收益不大。
- **不显示工具清单详情**。只给数量。想看某个服务器具体提供什么，问模型"你有哪些工具"更直接；命令里铺一屏工具名反而挤掉了状态。
- **不做 `/mcp reconnect`**。重连要动 AsyncExitStack 里的会话，而它绑在后台任务上（anyio 要求同任务内关闭），临时插一条很容易把工具表搞成一半新一半旧。要重连就重启。
