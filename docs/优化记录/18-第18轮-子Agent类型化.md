# 第 18 轮：子 Agent 类型化（从一类到四类）

> 日期：2026-11-09
> 版本：0.8.0 → 0.9.0
> 触发：子 agent 只有一种 `general-purpose`，工具无法限定、模型无法覆盖
> 教训：**"只有一类"不是数量问题，是"没有选择"——它逼着所有杂活共用同一套权限**

---

## 一、改前：一条硬编码的人设

第 8.1 轮把 `task` 的说明书修好之后，机制是通的：

```text
list_types() → ["general-purpose"]
subagent_type 校验 → 取 prompt → start_task() → 新开一页 → 跑完交回最后一条
```

但池子里只有一条，而且写死在 `subagent_manager.__new__` 里。由此带来三个问题：

1. **权限只能全有全无**。派"只读搜索"的活也只能给它全部工具（含 `cmd_runner`、
   `file_write`），靠提示词劝它别改文件——它只要有一次不听话，文件就被改了。
2. **模型不能分开**。`get_completion_stream` 里是无条件
   `request_params["model"] = self.model`，"派个便宜模型去搜代码"这条路直接堵死。
3. **加类型要改结构**。想多一种 agent，就得在「管理器 + 工具 + 界面」三处各抄一遍。

## 二、改后：四种内置，一个能写、三个只读

| 类型 | 工具 | 职责 |
|---|---|---|
| `general-purpose` | 全部（除 `task`） | 兜底：能查、能改、能跑命令 |
| `explore` | `file_glob` / `file_grep` / `file_read` | 东西在哪 |
| `plan` | 同上 | 该怎么改（产出分步方案） |
| `code-reviewer` | 同上 | 哪里有问题（按严重度给意见） |

后三个的工具完全一样，区别在**产出物**：

- `explore` 交结论（在哪、谁调用谁）；
- `plan` 交方案（现状 / 改动点 / 影响面 / 风险 / 步骤）；
- `code-reviewer` 交问题清单（必须改 / 建议改 / 可忽略）。

合成一个会退化：模型会倾向于只描述、不判断。三种活的心智模型本来就不同。

**三个只读类型的白名单只有三个工具，而这三个都在 `READ_ONLY_TOOLS` 里，
所以它们干活时一次审批弹窗都不会有**——这是本轮最大的体感收益：
主 agent 派 `explore` 翻十几个文件，用户不会被打断十几次。

### 为什么不从文件加载

中间实现过一版：`.thinker/agents/*.md`（项目级）+ `~/.thinker/agents/*.md`（用户级），
带 frontmatter 解析、三级覆盖、坏文件告警、`/agents` 重扫。后来整套删掉了。

理由：

1. **需求是"所有人都能用的一套"**。内置四个已经覆盖日常，不需要每人再维护一份。
2. **三层加载带来的概念比功能多**：优先级、同名覆盖、来源标注、坏文件隔离、
   编码、改完要重扫——这些都要维护，而维护定义的只有一个人。
3. **目录不存在时它本来就不生效**，等于代码里留着两条永不执行的路。
   更糟的是：看到 `USER_AGENTS_DIR` 的人会以为"我可以放 md"，然后去找一个
   实际不存在的入口。

代价说清楚：**加第五种类型要改代码**（在 `builtin_agents.py` 加一个 `AgentSpec`）。
好处是没有"我改了为什么没生效"这类问题。

## 三、三个关键决定

### 3.1 白名单三层，缺一层就有洞

| 层 | 位置 | 作用 |
|---|---|---|
| 清单层 | `ToolManager.get_tools_description(allow=...)` | 模型**看不到**越权工具 |
| 执行层 | `Conversation._is_tool_allowed()` | 模型硬调也**执行不了**，理由里带可用清单 |
| 说明书层 | `Task._tool_description()` | 只说实际有哪几个类型、各自什么工具 |

只做第一层不够：模型可能凭上一轮清单、或凭训练习惯写出一个工具名。
只做第二层不够：它能看见选项就会一直试，白烧两轮往返。
第三层是给主 agent 做决策用的——它需要知道"派给 explore 够不够"。

### 3.2 模型覆盖走 request，不改全局状态

```python
request = {"messages": ..., "tools": ...}
if agent is not None and agent.model:
    request["model"] = agent.model
```

`APIClient` 两处读取顺序改成「显式传参 > request 里的 > 全局」。
为什么不直接改 `self._api_client.model`：那是全局状态，子 agent 结束后还得改回来，
中途异常就永久改了主 agent 的模型；走 request 字段只对这一轮生效，天然没有还原问题。

### 3.3 子 agent 只拿自己的提示词

`build_system_prompt()` = 人设正文 + 三行环境（cwd / 系统 / 日期）+ 边界声明。

不灌 `PromptManager` 的完整系统提示词，原因两条：

1. 白烧 token——子 agent 的任务通常很窄，一份长提示词比任务本身还贵；
2. 越权——它看到「可以 /memory」「可以写 THINKER.md」会以为自己也有这些权责。

Claude Code 也是同一套：子 agent 只拿自己的提示词 + 基本环境，不拿完整系统提示。

## 四、两个必须绕开的坑

1. **`todo_write` 会串**。待办存在工具实例上，而实例在 `ToolManager` 单例里只有一份。
   子 agent 一调就把主 agent 的清单覆盖了，状态行提醒也跟着错。
   → 现在三个只读类型的白名单里都没有它；以后加类型也别给。
2. **审批不区分主/子**。`_execute_tool` 的审批分支只看工具名和命令，不看当前是谁。
   所以"让子 agent 零弹窗"唯一可靠的办法是白名单里根本不给要审批的工具，
   而不是在提示词里劝它别用。

## 五、已知边界

| 边界 | 说明 |
|---|---|
| 白名单是**工具粒度**，不是命令粒度 | 给了 `cmd_runner` 就等于给了全部命令。所以三个只读类型一律不给它 |
| 加类型要改代码 | 在 `builtin_agents.py` 加一个 `AgentSpec` 常量。这是去掉目录机制的代价 |
| 类型之间不能并行 | `ToolManager` / `Conversation` / `HistoryManager` 全是单例，见 ROADMAP #10 |
| 子 agent 不能再派活 | 三道闸：白名单剔 `task`、说明书不给、执行层拦截。Claude Code 允许嵌套 3 层，我们不 |
