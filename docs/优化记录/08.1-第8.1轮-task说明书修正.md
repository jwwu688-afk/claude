## 一、现场

用户在真机上只输入两个字：

```
> 你好

🤖 Please confirm if you want to execute the tool call:
   Tool: task, args: {'description': '回复用户的问候',
                      'prompt': '用户向你打招呼说"你好"。请用 task 工具启动 greeting-responder agent。',
                      'subagent_type': 'general-purpose'}
> no
⏺ 你好！有什么可以帮你的吗？
```

一句寒暄触发了一次完整的子 agent 派活申请。`args` 里那句"请用 task 工具启动 greeting-responder agent"尤其奇怪——项目里根本没有这个 agent。

## 二、根因：三层叠加

| 层 | 事实 | 出处 |
|---|---|---|
| 1 | 说明书末尾有一段 few-shot 示例，输入正是「用户："你好"」，输出是「助手：我用 task 工具启动 greeting-responder agent」 | `task.py` 原 155-160 行 |
| 2 | 说明书开头声明的类型表只有 `general-purpose`，登记表里也只有它 | `task.py` 原 139 行、`subagent_manager.py` 原 57 行 |
| 3 | 使用说明第 6 条鼓励"描述里写了应当主动使用，就尽量主动用上" | `task.py` 原 155 行 |

模型面对「示例说要 greeting-responder、类型表里只有 general-purpose」的矛盾，做了一个折中：类型填 `general-purpose`，把示例里的助手台词塞进子任务 prompt。它不是在编，是在做 in-context 复制。

**为什么"你好"是最强触发**：few-shot 示例的输入与用户输入**一字不差**时，模型几乎不会考虑其他路径。这不是概率问题，是提示词的构造问题。

另一个证据说明这段当初抄过来没校对：`<example_agent_descriptions>` 的闭合标签写成了 `</example_agent_description>`（少了 s）。

## 三、顺带暴露的两个隐患

1. **就算按了 yes，这一趟也是白跑。** 子 agent 拿不到 `task` 工具（`conversation.py:538` 排除 + `task.py` 第二道闸门），它收到"请用 task 启动 greeting-responder"只会撞墙，最后随便回一句。用户付出的是一整页上下文 + 至少两轮往返，换来一个"你好"的回复。
2. **说明书承诺了做不到的事。** 原第 1 条写"能并行就并行，性能最好"，但 `Conversation` 是单例 + 一页消息栈，多个 task 调用只能依次执行（第 8 轮遗留 D6）。骗模型的结果是它一次发好几个 task，然后干等。

## 四、改了什么

| # | 改动 | 位置 |
|---|---|---|
| 1 | 删掉 `code-reviewer` / `greeting-responder` 两段示例，以及错误的闭合标签 | `task.py` `_tool_description()` |
| 2 | 类型表改为从登记表动态生成（`_types_block()`） | `task.py` 新增方法 |
| 3 | "不要用"清单补三条：打招呼/寒暄/闲聊/简单附和、单轮问答、解释概念或写一小段代码 | `task.py` |
| 4 | 删掉"鼓励主动使用"的第 6 条，把"能并行"改为"依次执行" | `task.py` |
| 5 | 类型不存在时返回可用清单，不再抛 `ValueError` | `task.py` 新增 `_unknown_type_message()` |
| 6 | 登记表增加 `description` / `tools` 两张说明表 + `list_types()` / `describe()` | `subagent_manager.py` |
| 7 | `json_schema()` 里 `subagent_type` 的候选值也改为动态拼接 | `task.py` |

关键的 3 条代码：

```python
# task.py —— 类型表不再手写
def _types_block(self):
    lines = []
    for prompt_type in self._subagent_manager.list_types():
        purpose, tools = self._subagent_manager.describe(prompt_type)
        lines.append(f"- {prompt_type}：{purpose}（可用工具：{tools}）")
    return "\n".join(lines) if lines else "- （当前没有登记任何类型，请不要使用这个工具）"

# task.py —— 类型不对时把清单交回去，而不是抛异常
if subagent_type not in self._subagent_manager.list_types():
    return self._unknown_type_message(subagent_type)

# subagent_manager.py —— 登记时就带上"给主 agent 看的说明"
def register_subagent_prompt(self, prompt_type, prompt, description="", tools="全部"):
    self._system_prompt_map[prompt_type] = prompt
    self._description_map[prompt_type] = description
    self._tools_map[prompt_type] = tools
```

第 6 条为什么重要：原来"有哪些类型"这件事有三个副本——说明书里手写一份、`get_subagent_prompt` 的字典一份、`ValueError` 提示里一份。现在只有登记表一份，以后加 `code-reviewer` 只需在 `__new__` 里多登记一行。

说明书长度从约 1 600 字符降到 **764 字符**（含那段约 900 字符的示例）。这段文字每轮都随 `tools` 字段发给模型，属于缓存块的一部分，省的不只是首轮的钱，还省了模型读它的注意力。

## 五、验证

新增 `test/test_task_description.py`，11 项全过：

| 用例 | 断言什么 |
|---|---|
| ① 已登记类型都出现 | 登记了却没写进说明书，模型不知道能填什么 |
| ② 说明书无幽灵类型 | `greeting-responder` / `code-reviewer` 一个都不许出现（本次 bug 的回归） |
| ③ 无字面命中的招呼语 | 「你好」「谢谢」「您好」不许出现在工具描述里 |
| ④ 正例/反例两节都在 | 只有反例，模型会过度保守 |
| ⑤ 不承诺并行 | 「能并行就并行」不许出现；必须写「依次执行」 |
| ⑥ 未知类型返回清单 | 返回字符串，含"不存在"+ 全部可用类型 |
| ⑦ 空类型返回清单 | 同上 |
| ⑧ 空 prompt 被拦 | 防止子 agent 收到空白任务 |
| ⑨ 新类型自动出现 | 临时登记一个假类型，说明书和参数说明同步更新，测完还原 |
| ⑩ 参数候选值与登记表一致 | `json_schema` 不能再手写 |
| ⑪ 说明书变短 | < 1 400 字符且不含 `<example>` 块 |

过程中测试自己抓到一次我写错的地方：我在「不要用」清单里举例写了「"你好""谢谢""好的"」——虽然是反例，但仍是把这三个字送进了模型每轮都能读到的工具描述里。已改成"打招呼、寒暄、闲聊、简单附和（比如道谢或应答）"，一个招呼语都不留。
