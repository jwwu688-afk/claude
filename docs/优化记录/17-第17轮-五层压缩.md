# 第 17 轮：上下文五层压缩

> 日期：2026-11-09
> 版本：0.7.2 → 0.8.0
> 触发：上下文接近上限时只有一条路——调摘要模型。要么花钱，要么让模型忘事
> 教训：**"压力多大，就用多重的手段"比"一到线就上最贵的手段"更省钱，也更不容易失忆**

---

## 一、改前：只有一跳到底

原来的 `auto_messages_compression()` 逻辑很直：

```text
用量 > 80%  →  _compress_current_message()  →  删最老一轮 + 调摘要模型
```

两个问题：

1. **贵**：只要过 80%，每压一次就发一次请求。一个长任务压十次，就是十次额外调用。
2. **粗**：明明只超了一点点（81%），也要动最重的手术——删消息 + 摘要。
   而 81% 完全可以用"零成本、无损"的手段降下来。

第 6 轮的 L1（工具输出进门掐到 30000 字符）只在写入那一刻管用，管不了
"对话本身变长"。

## 三、每层的关键决定

### L2 Snip：为什么要"保头 3 + 保尾 47"

`KEEP_FIRST=3` / `KEEP_RECENT=47` 这两个数是从 Claude Code 的 `snipCompact` 抄来的经验值。

- **头** = 所有 system + 第一个 user。前者是规则，后者是"最初要解决什么问题"。
  这两样丢了，模型会开始做别的事，而且自己意识不到跑偏了。
- **尾** = 最近 47 条。这个长度大约覆盖"当前正在推进的子任务"的完整链路
  （读文件 → 改代码 → 跑测试 → 看报错），再往前往往已经是上一个任务了。

中间删掉后插一条公告（user 身份，模型对 user 说的接受度最高）。

**最容易出事的地方是刀口**：如果切在 `assistant(tool_calls)` 和它的 `tool` 结果之间，
下一次请求直接 400。所以切之前过一道 `align_top_cut()`，命中 tool 就把刀口往前挪到
它的 owner。宁可多留几条，也不能把一对拆开。

### L3 Microcompact：只折"重跑能拿回一样结果"的

一刀切地折工具结果会出人命：把 `file_write` 的结果折成"需要时重新运行"，
模型照做一次，文件就被重复改了一遍。

判据放在工具类自己身上（`is_repeatable`），压缩层不维护第二份白名单——
加新工具时只改一处。`HistoryManager` 通过 `set_repeatable_checker()` 注入查询函数，
**没注入时一律返回 False（保守）**：宁可多留 9000 字，也不能误折一次写操作。

另外两道限制：`> 8000 字符`才折（小的折了省不下空间）、最近 3 条不折
（模型正在依据它们做下一步判断）。

### L4 投影：只换视图，不动数据

投影规则：system 全保留 + 最近 3 轮完整 + 更早的只留 user 的目标文字，折叠成一条骨架。

它和 L2/L3/L5 有本质区别：**底层 `messages_history` 一字不动**，只有发请求那一刻
`get_projection()` 返回一份压缩视图。所以随时可以 rewind 回完整历史。

落地位置也特殊：`auto_messages_compression()` 里 `tier == 3` 这一支是**空实现**，
真正生效点在 `Conversation._get_messages_with_cache_mark()`
（`should_use_projection()` 为真时取投影）。看起来像"没写完"，其实是设计：
压缩链管"要不要动存储"，发请求链管"这一轮给模型看什么"。

上界是开区间：`>= 0.95` 必须退场，交给 L5。否则摘要永远等不到触发，
上下文会一直接近爆掉却没人兜底。

### 阈值为什么走环境变量

`SNIP_THRESHOLD=0.85` / `MICRO_THRESHOLD=0.90` / `COLLAPSE_THRESHOLD=0.95`，
默认值写死在 `history_manager.__init__`，可用 `.env` 覆盖。理由和
`COMPRESS_THRESHOLD` 一样：不同模型的上下文窗口和"有效上下文"差很多，
80% 对 200k 窗口是 160k，对 32k 窗口只有 25k，写死一个数必然有一边不合适。

## 四、已知边界（不是 bug，但要知道）

1. **消息少于 50 条、占用落在 `[0.80, 0.85)` 时，L2 剪不动也不会降级。**
   这一轮等于没压，要等占用涨到 0.85 由 L3 接手。留在 83% 不会爆（还有 17% 余量），
   所以没有改成"本层无效就往下试"——爬层会让"83% 就调摘要模型"的老问题回来。
2. **L3 依赖注入。** 没有注入 `repeatable_checker` 的环境（比如单测、脚本直调），
   L3 一条都不会折。这是安全方向，不是漏实现。
3. **投影与 L5 互斥。** `>= 0.95` 时投影自动退场，那一轮给模型看的是摘要后的存储，
   不是投影。
