## 一、现象

`/resume` 切到旧会话，问了一句"我刚刚问了什么"，模型正常回答，然后直接红字：

```
✗ 发生系统错误：Object of type ChatCompletionMessageFunctionToolCall is not JSON serializable
```

堆栈指向：`add_message` → `session.append_message` → `_write_line` → `json.dumps`。

---

## 二、根因：一行代码，两个层次的问题

`core/conversation.py` 在组装 assistant 消息时，把 SDK 返回的 `tool_calls` **对象**直接塞进了字典：

```text
assistant_message = {
    "role": "assistant",
    "content": response_message.content,
    "tool_calls": response_message.tool_calls,   # ← pydantic 对象，不是 dict
}
```

而这个字典会被立刻落盘（第 13 轮加的"每条消息即时写 JSONL"），`json.dumps` 不认识 pydantic 对象，于是抛 `TypeError`。

### 为什么现在才炸

两个条件同时成立才会触发：

1. **模型真的申请了工具。** 没有 `tool_calls` 时该字段是 `None`，序列化毫无问题。
2. **会话落盘已经启用。** 第 13 轮之前消息只在内存里，对象不会经过 `json.dumps`。

所以它是一个"新功能叠在旧数据上的经典塌方"：第 13 轮加落盘时看不出问题，因为它只在"用工具"时才被触发；而一旦触发，断点在**模型已经答完、工具还没执行**的那一刻——用户看到半截回答加一段红字，最容易被理解成"模型出错了"，其实是存档层崩了。

### 第二个问题：同一份历史有两种形态

内存里 `tool_calls` 是对象，从 JSONL 读回来是字典。第 9 轮修压缩裁剪时就为此写了一堆兜底（`history_manager._role` / `_tool_calls` 的注释里明写着"字典和对象两种形态都支持"）。每加一处读取点，就要多写两条分支。

---

## 三、修法：在唯一入口上统一形态

新增 `normalize_message()` 和 `_tool_call_to_dict()`，在 `Conversation.add_message()` 的第一行调用：

```text
def add_message(self, message):
    message = normalize_message(message)   # 转成可序列化的纯数据
    self._history_manager.add_message(message)
    ...
```

三个设计点：

| 决定 | 理由 |
|---|---|
| 放在 `add_message`，不放在 `_run_one_iteration` | 这里是**所有**消息进入历史的唯一入口。在某一类消息上单独处理，下次换个地方塞进对象又会漏 |
| 优先用 `model_dump()`，手写映射只作兜底 | pydantic 自己知道哪些字段该带；将来 SDK 加字段也不会漏。手写映射在拿不到 `model_dump` 时才用，那时候"字段少一点"也比"整条消息存不进去"强 |
| **不原地修改**传入的字典 | 调用方构造完 `assistant_message` 还会用它；原地改会让"存进历史的那份"和"调用方手里那份"悄悄变成两个版本，极难排查 |

### 存档层再加一道兜底

`SessionStore._write_line` 原来只捕 `OSError`（磁盘满、无权限），这次补了 `TypeError`：

```text
except TypeError as e:
    print(f"[会话存档] 这条消息没能写入（{type(e).__name__}: {e}）。"
          f"当前对话继续，但 --continue 会缺少这一条。", file=sys.stderr)
```

三个取舍：

- **只跳过、不写"残缺版"**：`assistant(tool_calls)` 和后面的 `tool` 结果是成对的，写一半出去恢复时会 400。少一条消息只是"恢复时少一件事"，写坏配对照"恢复后直接不能用"。
- **这条要打印，而 OSError 不打印**：磁盘满是环境问题，用户自己知道怎么办；这条是代码缺陷，不说就永远没人修。写 `stderr` 是为了不打断 rich 正在画的正文区域。
- **不吞成静默**：静默失败会让"会话少了内容"这件事在几天后才被发现，那时候根本查不出是哪一轮丢的。

---

## 四、附带收益

内存和磁盘的形态统一了：`tool_calls` 在**任何地方**都是字典。于是：

- 发给接口的消息是标准 OpenAI 格式（之前塞的是 pydantic 对象，靠 SDK 自己宽容才没出事）；
- `history_manager` 里那些"对象/字典都支持"的分支不再是必需路径，只是兼容旧数据的保险；
- 恢复会话时不再需要"读回来再转换"这一步。

## 五、测试

| 组 | 验的是什么 |
|---|---|
| 对象 → 字典 | 用真实 SDK 类型构造 `ChatCompletionMessageFunctionToolCall`，逐字段核对；最关键一条是"能被 `json.dumps` 序列化"——那就是改前崩的行 |
| 不原地修改 | 转换后入参里的元素仍是原对象 |

| 端到端 | `add_message` → JSONL → 读回：三行都是合法 JSON，工具名与参数完好，内存里也是字典 |
| 兜底 | 塞一个 `set` 字段：不崩、`stderr` 有告警、坏消息不落盘、后续消息照常写 |
