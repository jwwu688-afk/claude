# 第 16 轮：斜杠命令的 Tab 补全

> 日期：2026-11-08
> 版本：0.6.1 → 0.7.0
> 需求：「优化一下斜杠命令，我通过 tab 键可以自动补全」

---

## 一、为什么必须自己实现

`input()` 是个黑盒：它把一行文字**一次性**交给你，中间按了哪些键你完全不知道。
要在 `/cos` 后面按 Tab 补成 `/cost`，必须在**按键级别**接管输入。

标准库没有可用的替代：

| 方案 | 为什么不行 |
|---|---|
| `readline` 模块 | 只有 Unix 有，Windows 上是空的 |
| `pyreadline3` | 要加依赖，而 `THINKER.md` 写明"保持零依赖" |
| `prompt_toolkit`／`textual` | 同上，而且那是重构整个界面，不是一个补全功能该付的代价 |

`msvcrt` 是 Windows 自带的，`EscWatcher` 从第 13 轮起就在用它读键盘。这里沿用同一套。

---

## 二、关键取舍：只在"行首是 `/`"时接管

这是本轮最重要的设计决定。

**如果无条件接管所有输入**，就要自己处理中文输入法：组字期间的按键、候选框、上屏时机、
双宽字符的退格……每一个都是独立的坑。而用户这台机器上**绝大部分输入是中文**。
为了给 `/cost` 补全，去承担整条中文输入链路的风险，不值。

**所以改成先探一个字符**：

```text
读第一个字符
  ├── "/"        → 进入自管模式（有 Tab 补全）
  ├── 回车       → 返回空串，不进 input()
  ├── 普通字符   → 交回 input()，把已读的字符合到提示符后面（屏幕上无缝）
  └── 功能键/退格 → 丢弃，从头用 input()
```

代价只有一次按键读取，而普通对话（含全部中文输入）走的是**完全没变的那条老路**。

第 3 种情况需要注意：`input(prompt + first)` 会把已读的字符显示在提示符后面，
用户看到的是 `❯ 帮`，然后接着打——视觉上和一次性输入没有区别。

---

## 三、自管模式的实现要点

### 键值（Windows 控制台实测）

| 键 | 值 | 备注 |
|---|---|---|
| 回车 | `\r` 或 `\n` | 两种都要认 |
| 退格 | `\x08` | **不是** `\x7f`，和 Unix 不一样 |
| Tab | `\t` | |
| Ctrl+C | `\x03` | 抛 `KeyboardInterrupt`，保持 `input()` 的语义 |
| Esc | `\x1b` | 清空当前行 |
| 方向键/F 键 | `\x00` 或 `\xe0` + 键码 | 是**两字节**，必须把第二个也吃掉 |

最后一条容易漏：不处理的话，方向键的后半个字节会被当成普通字符插进输入里，屏幕上出现乱码。
这种 bug 只在按了方向键时才出现，测的时候很容易漏掉。

### 退格与双宽字符

擦掉一个字符的标准三步是 `"\b \b"`（退一格、画空格、再退回来），不需要 ANSI 控制码。

但这只对 ASCII 成立——中文占两列，退格一次只退一列，硬擦的结果是残留半截字符。
所以 `_redraw` 分两条路：纯 ASCII 原地替换，含中文就换行重画。
屏幕上会多一行旧的，但绝不会错位——**多一行比乱码好**。

### 补全的三种情况

和 shell 的习惯保持一致：

| 情况 | 行为 |
|---|---|
| 没有匹配 | 响铃（`\a`），什么都不改 |
| 只有一个匹配 | 直接补全，**并自动补一个空格** |
| 多个匹配 | 先补到最长公共前缀；已到公共前缀则列出候选 |

自动补空格的理由：`/cos` 补成 `/cost` 之后，用户接下来十有八九要输参数
（`/memory`、`/init` 都基本带参数用）。但判断条件必须是"补全结果本身是一条完整候选"，
不能用 `len(matches)==1`——`/c` 补成 `/c`（多个候选的公共前缀）时加空格，
用户就被卡在 `/c ` 上，再也打不出 `/clear` 了。

## 四、测试抓到的真 bug

`resolve_completion` 最初的写法是：

```text
if len(candidates) == 1: return candidates[0], False
```

看起来没问题，实际漏了**前缀过滤**：输入 `/q` 按 Tab，如果候选恰好只有 `/cost` 一条，
就会被补成 `/cost`——而 `/q` 和 `/cost` 根本没有前缀关系。

这个 bug 的隐蔽之处：

- 不会崩、不会报错、不会响铃；
- 用户只会看到自己打的字**突然被改写**成一个没想要的命令，然后按回车执行它；
- 真实触发条件是"注册表里恰好只有一条命令"或"补全源只返回了一条"，
  在当前 7 条命令下永远碰不到——但功能一旦扩展就会踩上。

修法是在最前面加一行过滤：`matches = [c for c in candidates if c.startswith(text)]`。

**这条是"写测试才发现的"，不是"读代码看出来的"**——因为读的时候，`len(candidates)==1`
这个条件看起来很合理。

## 五、降级与逃生

| 情况 | 行为 |
|---|---|
| 非 Windows（无 `msvcrt`） | `available=False`，直接走 `input()` |
| stdin 不是终端（管道/CI/重定向） | 同上。逐字符读在非终端环境会直接卡死 |
| 补全源抛异常 | 响铃，**已输入的内容不丢** |
| `completer=None`（授权提问、选会话编号） | 完全走老路，一个字符都不读 |

绝不能让"补全"本身成为启动失败的原因——这是从 `EscWatcher` 继承下来的原则。

| 项 | 结果 |
|---|---|
| `test_tab_completion.py` | **48/48** |
| 其余 16 个离线脚本 | 全绿 |
| 模型调用 | **0 次** |

48 项分五组：补全计算（6）、候选来源（13）、首字符四个分支（11）、按 Tab 的实际输出（14）、环境探测（1）。
其中"首字符分支"那组最关键——它决定普通对话会不会误入自管模式，
所以四个分支（`/`、普通字符、回车、功能键）各自单独验，还加了两条"完全走老路"的断言。

## 八、没做的事与已知限制

- **不做行内光标移动**。补全只需要行尾追加和退格；加左右移动就要维护光标列、
  处理中文双宽、处理终端自动换行时的视觉换行——都是独立的坑，和补全无关。
  真需要时（插话队列那一轮）再一起做。
- **不补参数**，只补命令名。`/memory ` 之后没有候选。
  代价是用户要自己记文件名；收益是这一轮不需要跨层读 `auto_memory` 的目录。
- **没有历史记录**（上下键翻上次输入）。当前上下键被忽略。
- **补全源每次按 Tab 都重新取一次**。7 条命令的开销可以忽略，不改。

**待用户实测**：`available` 取决于 `sys.stdin.isatty()`，而自动化测试跑在管道里永远是 False。
所以"补全在真实终端能不能用"这件事，本轮**只能用假键盘验证逻辑，无法验证真机**。
如果重启后按 Tab 没反应，最可能的原因是终端环境判断有问题，请直接反馈现象。
