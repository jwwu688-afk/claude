# 第 36 轮：测试收尾（统一入口 + 三个"假绿"脚本）

日期：2026-11-14
版本：0.13.0（不升版本，只收尾）

## 起因

准备宣布收尾时，按 README 里给的办法批量跑了一遍：

```bash
for f in test/*.py; do python "$f" > /dev/null || echo "失败：$f"; done
```

结果是**全绿**——34 个脚本一个都没报错。但把输出留下来看，有 3 个脚本其实在自己打印失败：

```
test_conversation_loop.py  ❌ 测试失败（已通过 5/7）：'Conversation' object has no attribute '_hooks'
test_file_tools.py         ❌ 测试失败（已通过 15/16）：内置工具应该是 4 个旧的 + 5 个新的，实际 10
test_p0_fixes.py           ❌ 测试失败（已通过 0/8）：同一份用量应该只压 1 次，实际压了 0 次
```

也就是说：**这 3 条路径已经很久没有真正被验证过了，而回归一直显示"全绿"**。这比直接挂更危险——挂了你至少知道；假绿会让你在一个"以为有测试保护"的地方静默退化。

这暴露了两个叠加的毛病：

1. **退出码不可信**：这些脚本的运行器是"一个大 try 包住整个 for 循环"，失败时只 `print("❌ …")` 就正常结束，退出码仍是 0。
2. **第一个用例挂掉，后面全不跑**：大 try 一抛异常就跳出循环，剩下 6~7 条根本没执行，屏幕上却写"已通过 0/8"，看起来像"8 条全挂了"，实际是"只测了 1 条"。

## 三个脚本各自的过期原因

三个都不是产品缺陷，是断言/脚手架没跟上实现。

### 一、`test_conversation_loop.py`：空壳对象缺属性

`AttributeError: 'Conversation' object has no attribute '_hooks'`。

这个文件用 `Conversation.__new__(Conversation)` 造"空壳"对象（刻意不走 `__init__`，避免连 MCP、读密钥）。第 32 轮给工具链加了 PreToolUse / PostToolUse 两个 hook 点，`_handle_tool_calls()` 里会走 `self._hooks`；空壳对象上没这个属性，于是在"工具调用链"那条用例上直接炸。

修法：补一个 `NoopHooks` 替身（永远放行），**不用真的 `HookRunner()`**——它 `__init__` 会读 `~/.thinker/hooks.json`，开发机上真配了 hook 就会去跑用户的脚本（甚至可能拦掉 `file_read`），测试结果取决于"谁的机器"。

补的过程中又露出两个同源问题：`_session`（hook payload 要读 session_id，`getattr(self._session, "id", "")` 只能兜住 `.id`，兜不住 `self._session` 本身不存在）和假 `FakeHistory` 缺 `get_current_messages()`（第 25 轮统一了读取入口）。两个都在 `make_conversation()` / `FakeHistory` 里补齐，将来别人拿这套脚手架驱动别的路径不会再撞同一个坑。

### 二、`test_file_tools.py`：工具数写死 9

`内置工具应该是 4 个旧的 + 5 个新的，实际 10`。

后来加了 `smart_context_cropper`，清单变成 10 个，断言从此每次都失败。

改法：9 → 10，**仍然写死总数**，没有放宽成 `>= 9`。这条用例存在的意义就是"工具清单被人无意中加减时立刻报警"——多一个会改变模型的工具选择，少一个会让模型报"没这个工具"。放宽成范围等于把警报关掉。

### 三、`test_p0_fixes.py`：对话太短，压根没有东西可压

`同一份用量应该只压 1 次，实际压了 0 次`，屏幕上一句"没有可压缩的较早对话"。

用例只造了 2 轮（4 条正文）对话，而 L5 摘要压缩保留最近 `COMPACT_KEEP_RECENT=10` 条。4 条全在保留窗口里，"边界之前"是空的，压缩链直接返回 `nothing_to_compress`，摘要器一次都不会被调用。

改法：造到 6 轮（12 条正文 + 1 条 system），边界之前稳定有可压内容。第二条断言（"新用量到来后允许再压一次"）同理也需要新对话——真实场景里不存在"一条新消息没来就又压一次"，所以两次压缩之间补 4 轮。

## 新增 `test/run_all.py`

一条命令跑完全部，并给出"通过 / 假绿 / 失败"汇总。四个设计点：

**双重判定**。退出码非 0 算失败；退出码 0 但输出里出现 `❌` 或"测试失败"，判为"假绿"，同样算失败，并在报表里单列、附一句修法。这正是这次踩到的坑。

**刻意不把 `Traceback` 当失败标记**。`test_full_conversation.py` 通过时也会打一段 anyio 的 traceback（见下面"遗留"），按 Traceback 判定会把通过误判成失败。

**子进程隔离**。每个脚本都改全局状态：单例（`Conversation` / `HistoryManager` / `ToolManager`）、环境变量、临时工作区。import 进同一个进程跑，前面的会污染后面的，出现"单独跑能过、批量跑就挂"这种最难查的问题。子进程天然隔离，代价只是启动时间。

**超时兜底**。默认 300 秒/个，超时记为失败并标"超时"，而不是把整个回归挂在那里等键盘或等 MCP 连接。

顺带把三个脚本的运行器统一改成"每条用例单独 try + 失败返回 1"：一条挂了不影响其余，退出码也能真实反映结果。

## 遗留（不阻断收尾）

`test_full_conversation.py` **通过时**末尾会打一段 anyio 的
`Attempted to exit cancel scope in a different task`——MCP stdio 客户端在事件循环收尾阶段被关闭导致。功能没坏，但看起来像挂了红字。根治要改 `shutdown()` 里 MCP 关闭的时序（关闭动作必须和启动动作在同一个 task 里），属于下一阶段。

## 为什么不上 pytest

依赖表里至今只有 openai / dotenv / mcp / rich / anthropic / httpx。测试的价值在"谁都能一条命令跑起来"，为此引入一个测试框架 + 插件生态，和"零依赖"的取舍不划算。手写脚本 + 一个 100 行的汇总器，足够覆盖这个规模。
