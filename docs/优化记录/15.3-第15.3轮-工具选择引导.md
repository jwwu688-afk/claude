# 第 15.3 轮：让模型用 file_glob，而不是 dir /s

> 日期：2026-11-08
> 版本：0.6.0 → 0.6.1
> 触发：用户第二次问「为什么这里查找文件用的不是 file_grep 而是 cmd_runner」

---

## 一、现象：边界删了，模型还是用 shell

用户说「帮我查找一下我的简历」，模型连发 6 条 `cmd_runner`：

```text
dir /s /b  C:\Users\Jarvis\Desktop\*简历*  ... *resume* *CV* 2>nul | sort
dir /s /b C:\Users\Jarvis\Downloads\*简历* ...
dir /s /b D:\*简历* 2>nul | sort | findstr /i /v node_modules ...   ← 超时 30 秒被杀
dir /s /b C:\Users\Jarvis\Documents\*.pdf ...
dir /b C:\Users\Jarvis\Desktop\*.pdf
$skip = @('node_modules',...); Get-ChildItem -Path D:\ ...            ← 语法错误
powershell -NoProfile -Command "$skip=@(...); ... -like *\$_*"        ← 又一处语法错误
```

**先排除了"没重启"这个可能**：会话 `20261108-154549` 的启动时间是 15:45:49，
它的 system 消息里含「可以操作任意路径」「不要从盘符根目录开始递归」——
已经是第 15.2 轮之后的新提示词。所以不是缓存问题，是真的没照做。

---

## 二、查到的三个原因

### 1. `cmd_runner` 的说明书自己教了用 `dir`

原文第 2 条：

```text
2. 目录检查：
   - 如果命令会新建目录，先确认父目录存在且位置正确（可用 file_glob，或用 `dir` 查看）
```

这是**一份授权**。模型读到"`dir` 可以查看目录"，而 `dir` 是它训练数据里最熟的写法，
于是下次要"找文件"时直接调 `dir /s`。同一件事在说明书里给两条路，模型只会挑更熟的那条。

### 2. `file_glob` 的说明书还在暗示"有范围"

原文：

```text
- ** 表示"任意层子目录"，例如 **/*.py 会找出工作区里所有 Python 文件。
```

第 15.2 轮已经把边界删了，但"工作区"这三个字还留在说明书里。
模型读到的信号是"这个工具只能在项目目录里用"，而简历在桌面——它当然不选。

### 3. 说明书没回答模型真正的问题：**path 该填什么**

`file_glob` 的说明书只有 4 行，举的例子全是 `**/*.py` 这种"已知项目结构"的写法。
而模型面对的是"不知道文件在哪"。它想到的办法是"扫几个常见的根"，`dir` 一条命令能同时扫多个目录，
`file_glob` 一次只能给一个 `path` —— 于是它选了能"一次干完"的那个。

这一点是真实的能力差异，不能只靠"你应该用 file_glob"解决，得告诉它**怎么拆**。

### 4. 篇幅不对称（次要但真实）

`cmd_runner` 的说明书有几百行（含整套 git 提交、PR 创建流程），`file_glob` 只有 4 行。
长说明在注意力里的权重天然更大。

## 三、改了什么

| 位置 | 改动 |
|---|---|
| `cmd_runner.py` 说明书 | 删掉「或用 `dir` 查看」，只留 `file_glob` |
| `file_glob` 说明书 | 整个重写：去掉"工作区"、加"什么时候用"、加"path 该填什么"、给出可直接照抄的调用示例 |
| `system_rule.py` 提示词 | 新增一条：用户说"找某个文件"时直接用 `file_glob`，**不要**用 `dir /s` / `Get-ChildItem -Recurse` / `find`；并说明"分几次调用不会更慢" |
| `cmd_runner.py` 代码 | 新增 `_looks_like_file_search()` + 结果末尾追加引导（见下） |

### 为什么还要在代码里加一层

前三项是"事前"约束——模型不一定读进去，这次就是证据（它加载了新提示词却照样用 shell）。
而**工具结果是它每一轮必读的**。所以加了一层"事后"反馈：

```text
---
[thinker 提示] 上面这条命令做的是"按文件名查找"，这类事情有专用工具，不必拼 shell：
  file_glob(pattern="**/*关键词*", path="C:/Users/用户名/Desktop")
它支持任意路径和 ** 递归，只读工具还会并发执行（几个目录可以同时搜），
比递归扫盘快，也不会因为超时被杀掉。下次遇到"找某个文件"请直接用它。
```

三个设计点：

1. **追加，不拒绝**。拒绝会让模型以为工具坏了，转而用更奇怪的方式绕——第 15.1 轮的
   cmd_runner 绕过工作区边界就是这么发生的。
2. **判据写得窄**：只认递归或带通配符的列目录、`find -name`、`where /r`。
   普通 `dir`（"看看这个目录有什么"）不加提示——提示一多就变噪音，然后被忽略。
3. **实现上包了一层薄壳**：`act` 里原本有 5 个 return 分支，逐个改等于抄五遍。
   改成 `act` 算完结果再决定要不要加尾巴，主体逻辑留在 `_execute`。

## 四、实测：说明书里推荐的写法到底多快

既然要让模型"先搜常见目录"，得先确认这个建议本身站得住：

| 调用 | 耗时 | 结果 |
|---|---|---|
| `**/*简历*` + `C:/Users/Jarvis/Desktop` | **0.00s** | 1 个 |
| `**/*简历*` + `D:/google` | **0.01s** | 4 个 |
| `**/*简历*` + `C:/Users/Jarvis`（整个用户目录） | **18.8s**（冷缓存）/ 5.9s（热缓存） | 9 个 |
| `dir /s /b D:\*简历*`（模型那次） | **>30s，超时被杀** | 无 |

所以说明书写的是「**先搜桌面、下载、文档这几个常见目录，每个毫秒级；别一上来就递归用户根或盘符根**」——
这是有数据支撑的，不是拍脑袋。

顺带验了一个"看起来该有的优化"：把 `AppData`、`Temp` 加进忽略目录能不能加速。
**不能**——5.87s → 5.89s，只是少返回一个结果。所以没加，避免用正确性换不来性能。

## 六、没做的事

- **没有拦截**。`dir /s` 仍然能跑通，只是末尾多一行建议。真要禁，得在 `classify()` 里
  对递归查找命令强制审批——但那会误伤"用户就是想列一下整个目录"的正常需求，
  而且和 15.2 轮"不设限制"的决定方向相反。
- **没有给 `file_glob` 加多目录参数**。让 `path` 支持列表确实能一条命令扫多个根，
  但那要改 schema、改实现、改测试，而"分几次调用"已经够了（并发是 15 轮做的）。
  如果后面发现模型仍然因此选 shell，再考虑。
- **没有动 `file_grep`**。用户两次都说成 `file_grep`，但找文件名和搜文件内容是两件事，
  说明书里一直写着两者的分工，这次没改。

**一个待观察项**：这轮改的是"引导"，不是"强制"。模型（`spark-x2.6`）下次会不会照做，
需要用户重启后实际问一次才知道。如果它还是用 `dir /s`，说明提示词这条路对这个模型不够，
届时再考虑在 `classify()` 里加硬约束。
