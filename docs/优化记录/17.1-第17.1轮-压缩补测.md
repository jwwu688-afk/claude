---

## 一、为什么必须补

五层压缩是"错了也不报错"的典型：

- L2 刀口切在 `assistant(tool_calls)` 和 `tool` 之间 → 下一次请求 400，
  但现场指向的是 API 参数错误，不是压缩；
- L3 折了有副作用的工具结果 → 模型重跑一次，文件被重复改，**没有任何报错**；
- L4 浅拷贝泄漏 → 存储被悄悄改写，等换接口或要 rewind 才发现；
- 档位串了 → 该走 L3 的时候调了摘要模型（白花钱），或该走 L5 时只做了投影（没降下来）。

这四类错误的共同点：当场不炸，事后难归因。所以断言要钉在"最容易错的那一下"。

## 二、用例设计：只看可观测量

不看内部 `tier` 变量，只看四个用户能观察到的结果：

| 观测量 | 说明哪一层 |
|---|---|
| 消息条数减少 | L2（整条删） |
| 条数不变、文本变短 | L3（只折单条） |
| 存储不变、投影开关打开 | L4（只换视图） |
| 摘要器被调用的次数 | L5（唯一花钱的层） |

这样即使以后重写实现，只要行为不变，测试就还成立——而不是把"我这次怎么写的"
固化成正确答案（第 16 轮那条 `seen_prompts == ["> 帮"]` 就是反面教材）。

`test/test_five_layer_compress.py`，19 条：

| 组 | 用例 |
|---|---|
| L1 | 短输出原样、超长留头留尾+省略说明、恰好等于上限不截断 |
| L2 | 不足 50 条不剪、保头保尾剪中间、**刀口不拆工具对**、剪后重算账本 |
| L3 | 未注入 checker 保守不折、只折"较早+可重复+>8000"、最近 3 条与写操作保留、小输出不折 |
| L4 | 窗口 `[0.90,0.95)` 三边界、投影不改存储、留目标去细节 |
| 路由 | 0.80 不压 / 0.82→L2 / 0.87→L3 / 0.92→L4 / 0.96→L5 / 同用量不重复压 / 新用量可再压 |

"刀口不拆工具对"这条是特意构造的：每轮 3 条时 `len = 3R+1`，`tail_start` 恒落在
assistant 上；末尾追加一条 user 把偏移改成 `3R+2`，刀口就正好压到一条 tool 上。
构造不出来就在用例里显式断言（"构造失败"），不让它悄悄退化成一条无效用例。

假摘要器用 `async def fn(msgs)` 注入，签名和真的完全一致，压缩链分辨不出来——
**全程零请求、零花费**。

## 三、抓到三个问题

### 1. 真 bug：L4 投影会偷偷写存储

```python
# 改前
system_messages = [msg for msg in early if _role(msg) == Role.SYSTEM]
# 改后
system_messages = [copy.deepcopy(msg) for msg in early if _role(msg) == Role.SYSTEM]
```

`get_projection()` 的文档写着"返回一份深拷贝出来的新列表，和 `messages_history`
完全解耦"，但列表推导**只复制了列表，元素还是原字典**。

触发链很具体：

```text
占用落 [0.90, 0.95)
  → _get_messages_with_cache_mark() 取投影
  → prompt_cache_enabled 为真（Anthropic 接口 / 模型名含 claude）
  → 给投影里的 system 打 cache_control
  → 实际改的是 messages_history 里的原始 system 消息
```

后果分两段：

- 当下看不出问题，`cache_control` 只是个额外字段，Anthropic 认它；
- 哪天换成不认这个字段的接口（OpenAI 官方），历史里残留的 `cache_control`
  会变成 `Unrecognized request argument` → 400，而且报错位置和压缩毫无关系。

这正是"L4 应该是只读"被破坏的样子。修法是深拷贝，代价是每次请求多复制 1~2 条
system 消息（几百字），可忽略。

### 2. 两个老测试早已失效，没人发现

五层压缩改了行为，但老断言还按"过 80% 就调摘要"在写：

| 文件 | 原构造 | 现在落到哪 | 结果 |
|---|---|---|---|
| `test_history_compress.py` 用例 2/3 | 170000 / 204800 = **0.83** | L2，7 条消息剪不动 | 什么都不发生 → 断言失败 |
| `test_p0_fixes.py` | 900 / 1000 = **0.90** | L4（本来就不调模型） | 摘要器 0 次 → 断言失败 |

修法不是改断言，而是**把用量推到 0.96**（L5 档），让用例回到它本来要验证的语义：
"删最老一轮 + 摘要"和"同一份用量只压一次"。断言语义一个字没动。

### 3. 失败也返回 0：假绿

`test_history_compress.run_all_tests()` 原来是：

```python
except Exception as e:
    print(f"❌ 测试失败: {e}")
    traceback.print_exc()      # 到此为止，进程退出码仍是 0
```

所以上面两个失败，用"看退出码"的方式批量跑，全都被算成通过——
上一轮那句"21 个脚本全绿"就是这么来的。已补 `sys.exit(1)`。

顺带把批量跑法改成**同时看退出码和输出内容**（`grep -E "❌|测试失败|Traceback"`），
因为项目里还有别的脚本是同样写法，不能指望它们都立刻改。

## 四、一个边界，决定不改

**消息 < 50 条、占用落在 `[0.80, 0.85)` 时，L2 剪不动，这一轮等于没压。**

看起来像"该降级到 L3"。不降级的理由：

1. 83% 不会爆（还有 17% 余量），下一轮用量更新后占用涨到 85% 就由 L3 接手；
2. "本层无效就往下试"会把"83% 就调摘要模型"的老问题请回来，
   而分层的全部意义就是**成本可预测**；
3. 真正的解法不是爬层，而是等 L2 具备"消息少但每条很大"场景下的手段——
   那属于 L3 的职责范围，不是 L2 该抢的。

已写进 `THINKER.md` 的「已知的坑」，避免以后被当成 bug 去"修"。
