## 一、现象

用户在 `PS C:\Users\Jarvis>` 下启动 thinker，执行 `/init`：

```
✔ 已生成项目记忆：C:\Users\Jarvis\THINKER.md
```

项目其实在 `D:\code\thinker`。生成的文件里还写着：

```
## 技术栈

- （没检测到常见的项目标志文件，请手动补充）
```

它连"这里不是项目"都说了，只是没人拦。

---

## 二、根因：不是 bug，是"以 cwd 为项目根"没有兜底

整套设计里，**启动时的 cwd 就是项目根**，一共四处依赖它：

| 依赖点 | 用 cwd 干什么 | 在主目录启动的后果 |
|---|---|---|
| `core/prompt/memory.py` | 从 cwd 向上 6 层找 `THINKER.md` | 找到（或生成）家目录那份 |
| `core/auto_memory.py` | cwd 转成 slug 当记忆目录名 | `~/.thinker/projects/C--Users-Jarvis/memory` |
| `core/session.py` | 写进会话 header 的 `cwd` | `/resume` 按项目过滤时找不到它 |
| `tools/file_tools.py` | `WORKSPACE_ROOT = cwd` | **改不到 D:\code\thinker 里的任何文件** |

最后一条是最疼的：模型会一直回"路径超出工作区，如需访问请设置 THINKER_ALLOW_OUTSIDE=1"，
而用户以为自己只是在正常聊天。

现场证据（两个会话的 header 都是家目录）：

```
2026-11-07T21:36:57 | C:\Users\Jarvis   （7 条消息）
2026-11-08T09:41:36 | C:\Users\Jarvis   （1 条消息）
```

### 一个反直觉的发现：`.env` 反而不受影响

`THINKER.md` 里原来写着「启动必须在项目根目录，`.env` 是相对 cwd 读的」——这句是错的。

实测：

| 启动方式 | cwd | `.env` 是否加载 |
|---|---|---|
| `thinker`（console script → 真实 .py 文件） | 任意目录 | ✅ 加载（python-dotenv 跟着**包所在目录**向上找） |
| `python -c "..."` | 任意目录 | ❌ 不加载（`-c` 没有 `__file__`，dotenv 退化成从 cwd 找） |

所以从家目录启动照样能连上模型，只是项目相关的四样东西全指错了地方。
这也解释了为什么这个坑不容易被察觉：**对话能用，只有"记忆"和"改文件"错**。

## 三、修法：在门口提醒，在写盘处拦截

### 3.1 启动时一句话（`main._warn_if_home`）

```
  ! 当前在用户主目录启动。
    项目记忆、会话归属、文件工具的工作区都会以这里为根，
    它改不到别的盘里的项目文件。要处理某个项目，先 cd 过去再启动。
```

为什么放在欢迎框**下面**而不是框里：框里固定三行（标题、模型、目录），
加一行会把它撑高、标题不再垂直居中——第 10 轮调那个框调了很久，不破坏它。

### 3.2 `/init` 与 `--init` 的守卫

主目录里执行 `/init` 现在会直接拒绝：

```
✗ 当前目录是用户主目录：C:\Users\Jarvis
· 在这里生成的 THINKER.md 会成为所有「从主目录启动」的会话的项目记忆，
· 而它描述的不是任何具体项目。请先 cd 到项目目录再执行 /init。
· 确实要写在这里，请加 --here。
```

三个设计点：

1. **两条路径必须一致**。`/init` 和命令行 `--init` 用同一个守卫。
   只在一边拦的话，用户在 CLI 被拦、进会话又能写，会更糊涂。
2. **只拦"项目"这一档**。`--global` 写的是 `~/.thinker/THINKER.md`，
   本来就跟着人走、不跟项目走，在主目录里执行它完全正当。
3. **留 `--here` 逃生口**。少数人确实拿主目录当工作区，
   不该因为一条提示就把路堵死；但这个动作必须显式。

### 3.3 为什么判据是"主目录"，不是"看起来不像项目"

后者会误伤：新建的空目录、只有一个脚本的目录、刻意在某个子目录里局部工作的场景，
都"不像项目"但完全合理。主目录是唯一一个「在这儿生成 THINKER.md 几乎肯定错了」的位置，
误报率最低。

宁可少提醒，也不要让用户学会无视警告——一条天天误报的提示，很快就没人看了。

## 五、它还会连带把测试搞挂

删这个文件之前先发现了一件有意思的事：`test_memory.py` 有 4 项失败。

原因是 `discover()` 从**当前目录**向上找 6 层 `THINKER.md`。Windows 的临时目录是
`C:\Users\<你>\AppData\Local\Temp\xxx`，向上第 4 层正好是 `C:\Users\<你>`——
于是家目录那份 THINKER.md 成了所有临时目录的"祖先项目记忆"：

| 失败项 | 原因 |
|---|---|
| `discover 返回空列表` | 本该为空，却返回了家目录那份 |
| `load 返回空字符串` | 同上，加载到了内容 |
| `正文没超过上限太多` | 多出来的正是家目录那份 |
| `没有『项目记忆』标题` | 系统提示词里凭空多了一节 |

这也解释了为什么这类错误"看着没事"：它不报错，只是**悄悄多一份记忆**。
任何放在 `C:\Users\<你>` 下面的项目都会继承它。

删掉文件后 13 个离线脚本全绿（`test_memory` 恢复 40/40）。

## 七、后续：CLI 入口已删除（2026-11-08，第 14.6 轮）

本文写的守卫当时同时加在两条路径上：会话内的 `/init` 和命令行的 `thinker --init`。
后来决定**只保留 `/init`**，CLI 那条路已经删掉，理由有三条：

1. 两份守卫、两份提示文案、两套测试，改一处迟早漏另一处；
2. "必须退出对话才能建记忆"本身是没必要的限制——人往往是聊到一半才想起来；
3. `write_init_file` 才是真正的逻辑，删掉 CLI 分支不影响它。

现在 `thinker --init` 会打印一行迁移提示后退出（不是静默忽略，否则旧习惯会掉进对话里，
看起来像"卡住了"）。所以本文第三节里"两条路径必须一致"那条设计约束，现在自然满足了。
