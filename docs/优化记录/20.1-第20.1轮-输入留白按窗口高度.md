# 第 20.1 轮：输入留白按窗口高度动态计算

> 版本 0.10.0 内的补丁（不改版本号）
> 起因：18.6 轮默认 2 行、18.8 轮调到 4 行，**两次真机反馈都是"只能往上滚一点点、回不到提问那一行"**。

---

## 一、前两轮为什么没解决

18.6 引入"输入行下方留 N 行空白 + 光标上移"的做法，当时的判断是"留白 N 行 = 能往上滚 N 行"，所以给了 2 行。
18.8 收到"滚不动"的反馈后，把 2 调到 4，判断是"数值不够大"。

两次都错在同一个地方：**把留白当成一个可以调大小的参数，而不是去算它到底该多大。**

4 行在 30 行的窗口里只占 13%，用户往上滚两格就到顶；而在 60 行的高窗口里 4 行更是杯水车薪。同一个数字在不同窗口下体感完全不同——这说明它本来就不该是个固定值。

---

## 二、真正的机制

conhost 的滚动条范围约等于：

```
可滚动范围 ≈ 缓冲区内已写过的总行数 − 一屏高度
```

两个推论：

1. **对话内容不足一屏时，这个差值接近 0。** 刚启动 thinker、只聊了两句，往上滚几乎一动就到顶。这不是留白不够，是**缓冲区里根本没有多余的行可滚**。往下留 N 行空白，等于把总行数抬高 N 行，也就把可滚范围抬高 N 行——这是滚动式终端里唯一能凭空撑出滚动余量的办法。

2. **留白行数同时也是"光标还在视口内时能往上滚几行"。** conhost 在程序一有输出时会把视口拉回光标所在行。往上滚时只要光标还在视口内，打字就不会被拽回底部；滚过留白行数，敲第一个字就会弹回底部。这是终端行为，不是 bug。

所以留白的合理值应该跟着窗口高度走，而不是拍一个常数。

---

## 三、改动

```python
raw = os.getenv("THINKER_INPUT_PADDING")
if raw is None:
    # 没配置：按当前窗口高度给半屏，矮窗口至少 8 行
    n = max(8, self._term_rows() // 2)
else:
    try:
        n = int(raw)
    except ValueError:
        n = max(8, self._term_rows() // 2)   # 写错了也按窗口算，不中断输入
```

| 项 | 行为 |
|---|---|
| 不设环境变量 | `max(8, 视口行数 // 2)`：30 行窗口 → 15 行；16 行窗口 → 8 行 |
| 设 `THINKER_INPUT_PADDING=0` | 关闭留白，回到"输入贴最后一行" |
| 设 `THINKER_INPUT_PADDING=20` | 以它为准，想滚更远自己调 |
| 设成非法值（`两行`） | 回退到按窗口计算，不抛异常 |

新增 `LineEditor._term_rows()`：

```python
@staticmethod
def _term_rows() -> int:
    try:
        return max(10, shutil.get_terminal_size(fallback=(80, 24)).lines)
    except Exception:
        return 24
```

三个设计点：

- **每次实时取**，和 `_term_cols` 一致。用户可以随时拉高/拉矮窗口，留白跟着变才不会"换了窗口尺寸就滚不动"。
- **单独包一个方法**，是为了让测试能覆盖它注入固定行高（`ScriptedEditor._term_rows`），不依赖跑测试那台机器的窗口大小。这一条是 18.6/18.8 两轮测试没抓出问题的直接原因——旧测试只断言"输出了 4 个换行"，机器窗口多大都过。
- **`fallback=(80, 24)` 与 `max(10, ...)` 是兜底**：输出被重定向、拿不到真实尺寸时按 24 行算，绝不因为取尺寸让输入层崩掉。

## 四、测试

`test/test_line_wrap.py`：19/19 通过（新增 2 条，改 2 条）。

| 用例 | 验证 |
|---|---|
| `test_bottom_padding_default` | 注入 20 行窗口 → 断言留 10 行（不再死盯 4） |
| `test_padding_scales_with_window` | 40→20、16→8、24→12 三组，确认跟随窗口且有 8 行保底 |
| `test_padding_env_overrides_window` | `THINKER_INPUT_PADDING=3` + 40 行窗口 → 用 3，不再按窗口算 |
| `test_bottom_padding_can_be_disabled` | 收紧成 `assert out == "\n"`：关掉后连上移指令都不许漏 |

最后一条原来写的是"`\x1b[2A` 不在输出里、开头不是 `\n\n`"，那是**看着实现写断言**——换个 N 就失效。改成断言整个输出恰好等于回车自己写的那一个换行，语义不依赖具体行数。

## 五、代价（明确写出来，免得以后当 bug 报）

- 留白会占屏幕下方空间，输入行看起来"浮"在屏幕中间偏上。
- 某轮只有一行输出时，底部会残留几行空白。
- 想要"输入行贴底 + 历史无限滚"，只能进备用屏幕（alternate screen）做全屏 TUI。滚动式终端做不到两者兼得——这是形态决定的，不是实现没做好。

---

## 六、验证方式

真机确认的判据（这三条都成立才算修好）：

1. 刚启动 thinker、只聊一两句，滚轮能往上滚约半屏，能看见欢迎框。
2. 滚到上方后直接打字，屏幕不弹回底部。
3. 拉高窗口后重启，留白明显变多（30 行窗口约 15 行）。

运行环境仍是 conhost（独立 PowerShell），PyCharm 集成终端不作为判据——它不是真终端，滚动行为本来就不同。
