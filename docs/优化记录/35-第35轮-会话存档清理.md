# 第 35 轮：会话存档清理（`/clean`）

日期：2026-11-13
版本：0.12.3 → 0.13.0

## 起因

`~/.thinker/sessions/` 只增不减，这一条从第 13 轮就挂在 ROADMAP 的遗留清单里（I4）。实测用户机器的状态：

```
6 个 .jsonl，共 1.6 MB
其中 20261110-205956-3d27.jsonl 一个就 1.45 MB（那个 805 条的长会话）
```

6 个不算多，但规律很清楚：一个长会话 1.5 MB，攒一年就是几百 MB。用户唯一的处理办法是手动进目录删——既要记得路径，又要自己判断"哪个能删"，很容易把正在聊的那个也删掉。

## 为什么默认是"压缩"而不是"删除"

会话记录是这个工具**唯一的外部记忆**。用户过两个月想翻回来看"上次那个报错是怎么解决的"，靠的就是这些文件。

JSONL 是纯文本，gzip 之后通常只剩 8%~15%。用这点空间换"一条都不丢"，明显比省下那 1.5 MB 划算。

所以 `/clean` 的选项顺序是：

```
1. 压缩归档（数据不丢，/resume 里仍然看得到）
2. 删除（不可恢复）
```

删除不是没有——有些人就是不想留。但它必须由用户主动选，而且选完还要再确认一次（第二次也用编号选择，不用 `y/n`：`y` 太容易顺手敲）。

## 五个设计决定

### 一、"旧"按 mtime 判，不按文件名里的时间

文件名是会话**创建**时间，mtime 是最后一次写入。按创建时间算的话，一个开了三天还在用的会话会被判成"三天前的旧会话"压起来——那恰好是用户最舍不得的那份。会话是越聊越长的东西，最后活动时间才代表它还有没有人用。

代价：复制文件、从备份恢复会重置 mtime，让老会话看起来是新的。对清理来说这个方向的错误是安全的（少清一个），可以接受。

（注意这和 `list_sessions` 的排序口径**相反**——那边按文件名排，因为 mtime 被重置会让老会话排到最前面，`--continue` 就接错地方。两个地方用两套判据是有意的，各自服务不同的问题。）

### 二、压缩必须"临时文件 + 原子替换"

顺序是：

```
读原文 → 写 xxx.jsonl.gz.tmp → os.replace 成 xxx.jsonl.gz → 删原文
```

直接往目标名写的话，压缩途中断电就留下半个 `.gz`，而原文件已经删了——那才是真的数据没了。现在任何一步崩掉，原文都还在。

### 三、解压（resume 归档会话）之后要删掉归档

不然同一个会话会以 `.jsonl` 和 `.jsonl.gz` 两份同时存在，`list_sessions` 把它列两次，用户选哪个都会困惑。

数据没丢——全在新解出来的 `.jsonl` 里；等它再次变旧，`compress_sessions` 会重新压一份。

顺序同样重要：**先写成功，再删归档**。反过来就是"归档没了、新的还没写完"。

### 四、归档文件禁止追加

`SessionStore._write_line` 用的是 `open("a")`。往 gzip 文件里追普通文本，得到的是一个从中间开始就坏掉的文件——连它前半段都解不出来，等于把整份历史毁了。

gzip 确实支持"多成员追加"（`gzip.open("at")`），但一旦某次写到一半崩了，整个归档都读不了；而且"边聊边压"本身没有收益。

所以正常路径是 `open_archive` 先解压。万一解压失败（磁盘满、目录只读），`_write_line` 里还有一道防线：检测到路径是 `.gz` 就直接拒写并打一行 stderr。宁可丢这一轮的新存档，也不能把旧历史一起弄坏。

### 五、压不下来就撤销

实测发现的：一个 263 B 的会话压成 gzip 是 262 B——只省 1 字节。因为 gzip 光头部固定开销就二十来字节。

这不是理论情况，"开一次、问一句就退出"的小会话很常见。所以压缩后要比较大小：

```python
if after >= before:
    target.unlink()      # 把刚写的归档删掉
    report["skipped"] += 1
    continue             # 原文留着
```

留着这种归档没有任何好处：空间没省、`/resume` 还要多一步解压。命令层会把 skipped 的数量报出来，否则用户会奇怪"为什么还有几个没变成 .gz"。

## 改法

**`core/session.py`**

| 新增 | 作用 |
|---|---|
| `_is_archive(path)` | 认出 `.gz`。抽出来是因为"怎么算归档"有三处要一致（读文本、列表展示、压缩时跳过） |
| `_read_text(path)` | 整份读成文本，自动按后缀走 `gzip.open`。读失败（含 `EOFError` / `BadGzipFile`）统一返回空串 |
| `_session_files(directory)` | "什么算会话文件"的唯一出处，同时认 `.jsonl` 和 `.jsonl.gz` |
| `usage_report(days=30)` | 只读统计：总数、总占用、已归档数、旧会话清单 |
| `compress_sessions(paths)` | 压缩 + 撤销 + 失败汇总 |
| `delete_sessions(paths)` | 只删不确认（确认在命令层） |
| `open_archive(path)` | 解压复活，非归档原样返回 |

改动：`_read_session` / `count_messages` / `list_sessions` 三处读盘入口全部改走 `_read_text` 和 `_session_files`；`_write_line` 加归档拒写。

**`core/commands.py`**

- `cmd_clean`：统计 → 说明 → 编号选择 → 压缩/删除（删除再确认）。
- `cmd_resume`：选中归档会话时先 `open_archive` 解压。

**为什么确认放在命令层、不放在 session 层**：会话层不该知道终端长什么样。"怎么问、问几次"是交互设计；测试直接调 `delete_sessions` 删临时文件，不用造一堆假回答。

## 顺带修：`/cl` 不再是唯一匹配

加 `/clean` 之后，Tab 补全里 `/cl` 从"唯一匹配 `/clear`"变成"两个候选、补到公共前缀 `/clea`"。`test_tab_completion` 里那条断言当场变红——**不是补全坏了，是数据变了**。

改法：拆分。`/cl` 验"补到公共前缀 `/clea`"，另用仍唯一的 `/ag` 验"唯一即补完"。原意（唯一匹配直接补上）没丢。

## 没做

- **不做自动清理**。启动时静默删/压历史是灾难性的设计：用户不会知道发生了什么，只会在某天发现"我的会话怎么没了"。宁可让他敲一次 `/clean`。
- **不按项目过滤**。会话目录是平铺的，`/clean` 按时间清，不分项目。按项目清会带来一个新问题：同一个项目里"想留的和想删的"往往同岁，时间反而是更好的判据。
- **归档不藏起来**。`ls ~/.thinker/sessions` 里 `.gz` 和 `.jsonl` 混着排，看起来有点乱，但"看得见"比"藏起来"重要——用户应该知道自己的历史还在。

## 35.1 补丁：列会话时只读第一行

做完 `/clean` 之后发现一个被自己加重的问题：`list_sessions(cwd)` 要判断"这条会话是哪个项目开的"，而 cwd 记在 header 里、header 就是文件第一行——但原来的做法是对每个文件调 `load()`，**整份读进来逐行解析**，只为取开头一百来字节。

一个 1.5 MB 的会话，一次 `/resume` 就整份读一遍。加了归档之后更贵：`.jsonl.gz` 要先解压整份才能拿到第一行，等于压缩省下的磁盘，每次列会话又解压回来。

改法：新增模块级 `read_header(path)`，普通文件 `readline()` 一行、归档用 `gzip.open().readline()`（gzip 是流式压缩，读第一行只需要解出开头那个块，几十 KB，不是整个文件）。

实测（本机 6 个会话，其中一个是 1.45 MB）：

| | 耗时 |
|---|---|
| 改前（每个文件读全量） | 13.6 ms |
| 改后（每个文件读第一行） | **1.0 ms** |

按"100 个会话、平均 500 KB"推，改前约 230 ms、改后约 17 ms——差别就从"能感觉到"变成了"感觉不到"。

三个边界都补了用例：

- 归档也能读出 header（不能因为压缩了就认不出项目）；
- 坏归档返回空字典、不抛（沿用 `_read_text` 的口径）；
- **第一行不是 header 时返回空字典**——老版本文件、手改过的文件都可能这样。硬当成 header 的话，按 cwd 过滤会漏会话，那种 bug 比慢更难发现。

注意这里只验正确性。"不读全量"是设计目标，不能直接断言（只能测耗时，而耗时在别的机器上不稳，会变成假失败）。
