## 二、逐项详情

### 1. 上下文压缩崩溃（`history_manager.py`）

**现象**：对话长到 80% 上下文时，程序抛出 `AttributeError: 'dict' object has no attribute 'role'`，整个对话中断。

**原因**：三种压缩相关的方法都按「对象」的方式读角色：

```text
# 改前（3 处）
return [i for i, msg in enumerate(messages) if msg.role == Role.USER]
system_messages = [msg for msg in messages[:idx] if msg.role == Role.SYSTEM]
system_messages = [msg for msg in messages[:user_index] if msg.role == Role.SYSTEM]
```

但真实会话里存的是字典（`{"role": "user", "content": [...]}`），字典没有 `.role` 属性。之所以一直没被发现，是因为单元测试用的是自定义的 `MockMessage` 类，恰好有 `.role`。

**改动**：新增统一读取函数，三种形态都能用（真实字典 / 测试对象）。

```text
# 改后：新增 history_manager.py:267 附近
@staticmethod
def _role_of(message) -> any:
    if isinstance(message, dict):
        return message.get("role")
    return getattr(message, "role", None)
```

三处调用全部替换为 `self._role_of(msg)`。同时顺手修了压缩公告的消息结构：

```text
# 改前：content 是字符串，和其他消息的"内容块列表"结构不一致
compression_notice = message_class(role=Role.USER, content="[Previous ...]")

# 改后：真实场景下统一为内容块列表；测试对象形态仍保留字符串，避免兼容性问题
if isinstance(first, dict):
    compression_notice = {"role": Role.USER, "content": [{"type": "text", "text": notice_text}]}
else:
    compression_notice = type(first)(role=Role.USER, content=notice_text)
```

**验证**：用真实字典消息构造 4 条消息 + 人为喂一个超阈值的用量，压缩不再抛异常，且系统消息与最新提问都保留。

**行为变化**：压缩功能从「一用就崩」变成「可以正常工作」。

### 2. 子 agent 出错不再杀掉整个程序（`conversation.py`）

**现象**：让子 agent 去查东西，中间任何一个工具抛异常，整个命令行直接退出，主对话上下文全部丢失。

**原因**：

```text
# 改前 conversation.py start_task()
except Exception as e:
    self._ui_manager.print_error(...)
    traceback.print_exc()
    self._task_depth -= 1
    sys.exit(1)          # ← 进程直接结束
```

而且这里还有第二个隐患：出错后没有把「子任务那一页消息」收掉，历史栈会错位（下次再派活就指错页）。

**改动**：

```text
# 改后
except Exception as e:
    self._ui_manager.print_error(f"System error occurred during running task: {e}")
    traceback.print_exc()
    self._task_depth -= 1
    self._discard_current_chat()      # 新增：把这页消息丢掉，保证栈对齐
    return f"Task failed: {e}"        # 把错误当结果交回主 agent
```

新增方法 `_discard_current_chat()`（`conversation.py:158`），只在「确实还有一页待收」时才 pop，同时把用量记录一起 pop 保持对齐。

**验证**：`_discard_current_chat` 在只有一页时不会误删主对话；子任务失败后主 agent 能继续对话。

**行为变化**：子 agent 失败不再退出程序，而是把 `Task failed: ...` 交给主 agent，由它决定重试或换方案。

### 3. `cmd_runner` 的 timeout 参数生效 + 不再阻塞（`tools/cmd_runner.py`）

**现象**：
- 模型传 `timeout=120`，命令还是在 30 秒被掐断（因为代码里写死了 `timeout=30`，形参根本没用上）。
- 命令执行期间整个界面卡住、不刷新——因为用的是同步 `subprocess.run`。
- 命令失败但错误输出为空时，只返回 `"Error: "`，模型完全不知道发生了什么。

**改动**：

| 改动点 | 改前 | 改后 |
|---|---|---|
| 执行方式 | `subprocess.run(..., timeout=30)` 同步阻塞 | `await asyncio.create_subprocess_shell(...)` 异步 |
| 超时 | 写死 30 秒 | 使用 `timeout` 参数，并夹在 1 秒 ~ 600 秒之间 |
| 超时清理 | `process.kill()` 只杀 shell | `taskkill /F /T` 杀整棵进程树（Windows） |
| 输出编码 | 一律 UTF-8 | 先试 UTF-8，再试系统默认编码（中文 Windows 是 GBK） |
| 输出长度 | 无限制 | 超过 30000 字符则保留头 60% + 尾 40%，中间标注省略字符数 |
| 空错误输出 | `Error: ` | `Error: command exited with code N` |

关键代码（`cmd_runner.py:48` 起）：

```text
process = await asyncio.create_subprocess_shell(
    command, stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE)
stdout_bytes, stderr_bytes = await asyncio.wait_for(process.communicate(), timeout=timeout)
```

**这里踩到一个坑（值得记录）**：一开始只调 `process.kill()`，实测 `timeout=1` 却等了 **7.34 秒**才返回。原因是「shell 执行」形成了 `我们 → cmd.exe → python.exe` 三层，`kill()` 只杀掉 cmd.exe，底下的 python 还占着输出管道，`communicate()` 要一直等它自然结束。改用 `taskkill /F /T /PID` 杀掉整棵树后，耗时降到 **1.48 秒**。

新增三个辅助方法：`_kill_process_tree()`、`_decode()`、`_truncate()`；并把 `30 / 600 / 30000` 三个魔法数字提取为模块常量 `DEFAULT_TIMEOUT / MAX_TIMEOUT / MAX_OUTPUT_CHARS`（`cmd_runner.py:21` 附近）。

**行为变化**：命令执行不再卡界面；长命令不会莫名 30 秒被杀；超长输出不会把上下文撑爆；中文输出不再乱码。

### 4. MCP 配置容错（`tools/mcp_client/server_config.py`）

**现象**：没建 `~/.thinker/mcp.json` 的人，启动 `thinker` 直接报 `FileNotFoundError`，连内置工具都用不了。

**原因**：`MCPConfig.__init__` 在配置缺失时抛异常，而这个对象在 `ToolManager` 创建时就被 new 出来，异常一路冒到启动阶段。

**改动**：全部改成「打印一行提示 + 跳过」，降级但不崩溃。

| 场景 | 改前 | 改后 |
|---|---|---|
| 文件不存在 | 抛 `FileNotFoundError` | 提示后用空配置继续 |
| JSON 语法错误 | 抛 `JSONDecodeError` | 提示后跳过外部工具 |
| 最外层不是对象 | `AttributeError` | 提示后跳过 |
| 缺少 `command` | 抛 `ValueError`（连带 `args` 为空也报错） | 跳过该服务器；`args` 允许为空 |
| 单个服务器配置写错 | 整份配置全废 | 只跳过这一个 |

**验证**：三种配置文件（不存在 / 坏 JSON / 混合配置）分别构造，均不抛异常；正常服务器能加载，不支持的 `sse` 类型被跳过。

**行为变化**：没有外部工具也能正常启动，只是少了那几个 MCP 工具。

### 6. 子 agent 结论返回纯文本（`history_manager.py:214`）

**现象**：主 agent 收到的子任务结果是 `[{'type': 'text', 'text': '任务完成了...'}]` 这种 Python 代码字符串，带着一堆噪音，既浪费 token 又干扰理解。

**原因**：

```text
# 改前
response = task_messages[-1]["content"]   # content 是列表，直接 return
return response
```

**改动**：新增 `_content_to_text()`，把内容块列表里的文字抽出来拼成纯文本；顺手加了「这一页为空」的保护，避免越界。

```text
# 改后
if not task_messages:
    return ""
return self._content_to_text(task_messages[-1])
```

**验证**：返回 `'任务完成了，结论是：目录里没有 .tmp 文件'`，不含 `{'type'` 噪音。

### 7. 权限默认值调整（`conversation.py:351`）

**改动**：

```text
# 改前
need_user_approve = args.get('need_user_approve', False)
# 改后
need_user_approve = args.get('need_user_approve', True)
```

**说明**：这只是「失败时更安全」的兜底，**不是真正的权限系统**。原始设计里「要不要问用户」完全由模型自己填，模型漏写或故意写 `false`，危险命令就会静默执行。真正的权限规则（命令白名单、危险命令黑名单、工作区路径边界）放在后续轮次。

**行为变化**：模型没给这个字段时，会先问用户，而不是直接执行。

### 8. 拆掉循环依赖（`core/__init__.py`、`tools/__init__.py`）

**现象**：`import tools.tool_manager` 直接报

```
ImportError: cannot import name 'ToolManager' from partially initialized module 'tools.tool_manager'
```

只有从 `main.py` 进入才不报——也就是说，任何独立脚本、测试、工具想单独用 `ToolManager` 都会被绊住。（这一条是在本轮做验证时实际撞到的。）

**原因**：两个包的 `__init__.py` 都「一导入包就立刻加载子模块」：

```text
# 改前 core/__init__.py
from .conversation import Conversation
# 改前 tools/__init__.py
from .tool_manager import ToolManager
```

于是 `tools.tool_manager → core.history → 触发 core 包初始化 → conversation → reminder → 又要 tools.tool_manager`，此时后者还没执行完，类还不存在。

**改动**：两个 `__init__.py` 都改为惰性导入（PEP 562 的模块级 `__getattr__`），把加载推迟到真正访问的那一刻。

```text
# 改后 tools/__init__.py
__all__ = ['ToolManager']

def __getattr__(name):
    if name == 'ToolManager':
        from .tool_manager import ToolManager
        return ToolManager
    raise AttributeError(f"module 'tools' has no attribute '{name}'")
```

`from tools import ToolManager` 和 `from core import Conversation` 的写法完全不受影响。

**验证**：`import tools.tool_manager` 成功；`core.Conversation` / `tools.ToolManager` 均可正常取到；工具仍加载 7 个。

### 9. 测试脚本可以独立运行（`test/test_history_compress.py`）

**现象**：这个脚本原来跑起来必然失败，输出 `❌ 测试失败:` 且没有任何断言信息。

**原因**：`HistoryManager` 是单例，5 个用例共用一个实例，前一个用例塞进去的消息会留到后一个用例里，导致条数、用户消息数量全部对不上。

**改动**：新增 `fresh_manager()` 辅助函数，每个用例开头重置单例。

```text
def fresh_manager(model_max_tokens=100, compress_threshold=0.8):
    HistoryManager._instance = None
    HistoryManager._initialized = False
    return HistoryManager(model_max_tokens=model_max_tokens, compress_threshold=compress_threshold)
```

5 处构造全部替换为 `fresh_manager(...)`，文件头注释同步更新为「已修复」状态。

**验证**：5 个用例全部通过（改前必失败）。
