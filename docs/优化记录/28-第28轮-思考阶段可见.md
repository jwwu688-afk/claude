# 第 28 轮：推理模型"思考 191 秒"时，界面上看得出它在动

日期：2026-11-11
版本：0.10.2（未发版）

## 现象

用户截图：一行 `Thought for 191s`，下面是 `●` 加一个 `.`，光标在那儿闪。原话是
「就好像是系统卡住了，有没有什么办法让我能看到系统的状态不是卡住了」。

191 秒不是一个可以"再等等看"的长度。而这 191 秒里，界面没有任何可见变化。

## 为什么看不到东西

推理模型（这里的 `spark-x2.6`，还有 GLM、DeepSeek-R1 这一类）分两段返回：

```
阶段一 reasoning_content:  "让我先看看这个报错…"   ← 思考，可能几分钟
阶段二 content:            "问题是 xxx，改法如下"   ← 真正的回答
```

而 `get_completion_stream` 只认 `delta.content`：

```python
if chunk.choices[0].delta.content:
    yield content_chunk
```

`reasoning_content` 不是 OpenAI 标准字段，SDK 不认，被塞进 `delta.model_extra`，
代码从来没读过它。于是整段思考在**客户端看来等同于"没有数据"**——
可实际上网络一直在传 chunk，只是我们一个字都没往外送。

首字到达那一刻才打印 `Thought for 191s` 并进入正文。在此之前屏幕上只有 spinner
（`⠋ 正在思考 (191s)`），一行小字，在 conhost 里还容易被宽度补齐的空白淹没。

## 改法

1. **`api_client`**：从 `delta.model_extra` 里读 `reasoning_content`，有就
   `yield ThinkingChunk(len(...))`——只带字数，不带原文。
2. **`ThinkingChunk`**：单独的类型。为什么不用字符串：
   思考内容一旦混进 `full_content`，下一次请求会把模型的内心独白当成"它说过的话"
   发回去，上下文暴涨、模型还会被自己的思考带偏。用类型区分，调用方一眼能看出
   这是心跳。
3. **`conversation`**：收到 `ThinkingChunk` 就 `note_thinking(chars)` 然后 `continue`，
   不进正文、不进历史。
4. **`DisplayManager.note_thinking`**：累加计数，spinner 每帧读它。
5. **`build_spinner_frame`** 新增 `thinking_chars` 参数，文案变成：

```
⠸ 正在思考 (7s)                      ← 拿不到 reasoning 时，和原来一样
⠸ 正在推理 1.2k 字 · 47s             ← 推理模型：字数每秒在涨
⠇ 正在推理 8.6k 字 · 3m11s
```

顺带把秒数改成 `3m11s`：原来写 `191s`，用户还得自己换算成"三分多钟"。

## 为什么这样就"不像卡死"

转轮只能证明"程序在转"，数字才能证明"数据在进来"。
思考字数涨一档 = 又收到了一段 reasoning chunk = 连接还活着、模型还在推进。
这比任何静态提示都直接。

## 验证

离线，用假的 chunk 序列跑 `get_completion_stream`：

```
思考心跳 chars = 8
思考心跳 chars = 3
正文 = '答案'
正文 = '是42'
最终消息 content = '答案是42'      ← 思考内容没有混进正文
```

帧渲染（伪 tty，1.2 秒 12 帧）：

```
⠸ 正在推理 1.2k 字 · 0s
⠇ 正在推理 120.0k 字 · 10m00s     ← 最长 29 列，未超过补齐宽度 40
```

## 还没覆盖的一种情况

**正文已经开始之后又长时间静默**（模型说完一句、又回去想）。这时 `●` 和正文已经
写在屏幕上了，再插 spinner 会覆盖正文；用 `\x1b7`/`\x1b8` 保存恢复光标在 conhost
上不可靠（本项目第 10 轮已经因为类似的重绘方式留下过残影）。
所以这一轮只修「首字之前的长思考」——也就是截图里这 191 秒的情况。
如果之后在正文中间也频繁遇到长静默，再单独设计方案。
