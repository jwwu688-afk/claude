| 31 | `/mcp` 状态面板 | 区分"配置里有什么"和"实际连上了什么"：五态（已连接 / 取清单 / 取清单失败 / 连接失败 / 连接中 / 跳过）。见 `docs/优化记录/31-…` |

| 33 | 四档工作模式 | default / plan / accept / auto；权限从两态改成 `allow / ask / deny` 三态；plan 在清单层与执行层双重拦截，子 agent 的允许集取交集。见 `docs/优化记录/33-…` |
| 34 | 压缩落盘与 resume 重建 | 压缩后往会话文件追加 `compaction` 记录（`keep_from` + 摘要），`/resume` 不再重复压一遍；会话列表显示压缩后条数（标「（压缩后）」）。见 `docs/优化记录/34-…` |

**现在的 Thinker 已经能**：连续多轮对话、调工具改文件、按占用比例分五层压缩上下文（前四层零成本）、按类型把活派给不同权限的子 agent（只读类型零审批）、按项目记规矩、跨会话积累经验、崩溃后接着聊、用四档模式控制"这一轮能不能动手"（plan 下先出方案）、在生命周期节点挂 shell（改完文件自动格式化 / 跑测试）、用 `thinker mcp` 管外部工具、压缩结果落盘所以 `/resume` 不再重压一遍。

**还不能**：中途插入新指令而不打断（生成期间打的字会被吞）、子 agent 并行执行、联网查资料、会话文件自动清理。

| 1b | **Slash commands（第二步）** | 手动 `/compact`、`/clear` 清空上下文 | ✅ 第 14.5 轮已完成 |

两批都做完了（第 14 轮当时 7 条，现在 12 条：后续又加了 `/agents` `/mode` `/mcp` `/model` `/skills`）。第一批只读、第二批动历史页——分批的价值在最后应验了：`/clear` 的"换文件"语义如果和只读命令混在一起，回归里那几条断言根本不会被写出来。详见 `docs/优化记录/14-…` 和 `14.5-…`。

### P1 —— 直接影响成本和速度

| # | 项 | 为什么现在 | 成本 |

### P3 —— 成本高或收益靠后

| # | 项 | 推迟原因 | 成本 |
|---|---|---|---|
| 7 | **插话队列** | 原判断「得引入 prompt_toolkit 或自管行编辑」**已过时**：16.2 轮输入层就整行自管了，`esc_watcher` 的后台线程也已在跑，它的文件头注释里明确留了「以后改成把非 Esc 字符塞进队列」的口子。所以成本从「大」降到「中」。建议只做**排队版**：生成期间能打字、回车入队，本轮工具全部执行完后作为下一条 user 消息发出（Claude Code 就是这个行为）；真正打断 API 流不做 | 中 |
| 8 | **WebFetch / WebSearch** | 现在只能搜本地，很多任务确实做不了，但增量信息靠用户贴也行 | 中 |
| 9 | **重试退避** | 429/5xx 现在一次失败就走非流式兜底，能用但不够优雅 | 小 |
| 10 | **并行 subagent** | **必须先去掉单例**。`ToolManager`/`Conversation`/`HistoryManager` 全是单例 + 类属性，硬并行会互相踩 | 大 |
| 11 | **会话文件清理** | 现在只增不减，攒久了要手动删（`I4`） | 小 |

## 六、判断优先级的标准

排序不是凭感觉，按这三条依次判断：

1. **是不是阻断日常使用**——能不能打断、崩溃会不会丢工作，这类是地基。
2. **是不是每轮都在付费**——上下文浪费、多余的串行等待，做一次省一辈子。
3. **有没有依赖前置**——单例没拆就别谈并行，权限没做就别谈 Plan mode。

反之，下面这些信号说明**不该现在做**：

- 需要引入新依赖才能做（项目刻意保持轻量）
- 收益只体现在"别人有我也要有"，自己用不到
- 做完之后还要再改一次架构——先改架构
